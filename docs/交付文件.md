# 交付文件

這份文件說明怎麼讓 SDLC 的產物變成要交給客戶的正式文件：挑出這個專案要交哪些、流程怎麼逐節更新、怎麼盤點與檢查。

先講結論：

- 要交哪些由你決定。工具給型錄與建議，你確認後才寫進 `.claude/teams/deliverables.json`。
- 沒有交付設定時，流程完全不變：不產生、不檢查、不多派 agent。
- 每個小節記著原料來源。原料改了而內文沒動，那一節就是「過期」。
- 這是輔助功能：閘門（save_run、publish、merge_gate）不讀它的輸出，壞掉也不擋流程。

## 型錄

內建型錄在 `.claude/teams/deliverables/catalog.json`，分八組、56 種文件：

| 組 | 例子 |
|---|---|
| 專案管理 | 專案計畫書、進度週報、會議紀錄、變更紀錄、結案報告 |
| 需求 | 需求規格書、業務規則文件、使用者故事清單、需求追溯矩陣 |
| 分析設計 | 功能規格書、系統架構設計書、資料庫設計文件、API 規格書、批次作業設計文件、畫面規格 |
| 開發 | 開發環境與建置說明、第三方元件與授權清單、功能開發紀錄 |
| 測試 | 測試計畫、測試案例、測試報告、使用者驗收紀錄 |
| 上線 | 版本說明、交付摘要、部署手冊、還原計畫 |
| 維運與移交 | 維運手冊、使用者操作手冊、教育訓練教材、移交文件 |
| 合規 | 弱點掃描報告、滲透測試報告、個資與隱私評估、安全審查紀錄 |

每種文件標一個來源類型：

| 來源 | 意思 | 例子 |
|---|---|---|
| `auto` | 可以從 SDLC 產物產生 | 需求追溯矩陣、測試報告、資料庫設計文件 |
| `assisted` | 工具給範本與原料，人補內容 | 專案計畫書、維運手冊、教育訓練教材 |
| `external` | 外部證據，只檢查有沒有附 | 弱點掃描報告、滲透測試報告 |

型錄只是可選的清單與預設內容。交付設定裡可以改寫任何欄位，也可以加型錄沒有的文件。

## 設定要交哪些

在對話裡用 `/agent-workflow:deliverables`，或直接跑：

```bash
python3 .claude/teams/tools/deliverables.py configure --preset outsourced              # 從情境組合開始
python3 .claude/teams/tools/deliverables.py configure --suggest                        # 依 repo 實況建議
python3 .claude/teams/tools/deliverables.py configure --import 合約交付清單.txt         # 對照合約或客戶給的清單
python3 .claude/teams/tools/deliverables.py configure --add db-design --remove weekly-report
```

- **情境組合**：黑客松（`hackathon`）、概念驗證（`poc`）、內部工具（`internal-tool`）、委外專案（`outsourced`）、維運移交（`ops-handover`）。組合寫在型錄的 `presets`，可以自己加。
- **依 repo 實況建議**：有 migration 才建議資料庫設計文件；有 API 定義檔或用過 `public_api` 才建議 API 規格書；有排程或 job 才建議批次作業設計文件；有畫面元件或用過 `ui` 才建議畫面規格。每個建議與不建議都附理由。
- **匯入清單**：一行一項，用型錄的標題與別名對應。對不到的列出來，由你決定；加 `--custom-unmatched` 才會新增成自訂文件。
- **沒確認不寫入**：上面的指令只印提案。確認後在同一個指令加 `--write --by <確認的人>` 才寫入。
- 寫入後跑 `deliverables.py init` 建文件骨架與總目錄（已有的檔不動）。

設定也可以寫在 `methodology.json` 的 `deliverables`（要 `enabled: true`）。專案有 `deliverables.json` 時以那一份為準。內建 profile 的 `deliverables` 只是範例，預設不啟用。

### 每份文件的欄位

| 欄位 | 意思 |
|---|---|
| `id` | 型錄的文件 id；型錄沒有的就是自訂文件 |
| `title`、`group`、`sections` | 標題、分組、小節（改寫型錄的預設） |
| `source` | `auto`、`assisted`、`external` |
| `sources` | 原料：相對目標 repo 的 glob |
| `on` | 哪類改動會影響它：改動分類（`code`、`test`、`doc`、`migration`、`manifest`）、`mod:<modifier>`、`path:<glob>`、`stage:<段>`、`recipe:<名>`、`event:<事件>` |
| `section_on` | 某個小節只在特定改動時更新 |
| `design_sections` | design.md 要先留的小節 |
| `depth` | `full` 或 `summary` |
| `when` | `run`（每次交付更新受影響的小節）、`milestone`（只在里程碑）、`close`（只在結案） |

整份設定另有 `show_approvers`（核准紀錄要不要寫核准者名字，預設不寫）、`dir`（文件放哪，預設 `docs/deliverables`）、`repo`（原料的基準）、`banned_terms_file`（禁用字清單，一行一個正規式）、`privacy_allow`（可以出現的字串，例如對外的客服信箱）。

`dir` 要在 tpm-writer 寫得到的目錄裡（`guard.config.json` 的 `writer_dirs`，預設 runs_dir、briefs_dir、`docs/`）。放在別處時，把它加進 `writer_dirs`。

## 流程怎麼用它

| 段 | 做什麼 |
|---|---|
| design | 資料包工具把「design.md 要有哪些小節」放進 args，派工單要求 spec-author 照抄標題；和這次無關的小節寫「這次沒有變動」，不省略也不編內容 |
| deliver | 資料包工具依這次的改動檔、modifiers、recipe 算出受影響的文件與小節。多派一個 tpm-writer：只改列出的小節，另寫 `<run_dir>/deliver/交付摘要.md` |
| deliver 存檔後 | `awf.py done` 自動跑 `deliverables.py sync`：交付摘要與核准紀錄併進功能開發紀錄、寫需求追溯矩陣、記錄各小節的來源 |

- `when` 是 `milestone` 或 `close` 的文件，一般 run 只在閘門提示「受影響但這次不動」。要更新時跑 `deliverables.py affected --run <run_dir> --milestone`。
- 碰到新領域（例如第一次出現 migration、但設定裡沒有資料庫設計文件）時，只在 deliver 段提示「建議加進交付設定」，不會自動加。
- 需求追溯矩陣、功能開發紀錄由工具寫，不派 agent。外部文件不由流程產生。

## 來源標記與過期

每個小節標題下一行是來源標記：

```markdown
## 資料表與欄位
<!-- awf:source specs/**/design.md; **/migrations/** -->
```

- 標記只寫路徑。各來源檔的雜湊記在 `.claude/teams/deliverables.state.json`，team agent 寫不到。
- `sync` 只記錄內文改過的小節。原料改了、內文沒動，那一節就保持過期；只改空白不算改。
- 內容確實不用改時，由人決定：`sync --run <run_dir> --reviewed <文件id>#<小節>`。
- 實際比對的來源是「文件層級的 `sources` 加上標記」：標記只能加，刪掉或改成對不到檔的 glob 都躲不過過期判定。
- 只改空白、標點或全形半形不算改寫。
- `awf.py done` 的自動同步只記這次受影響清單上的小節；清單外的小節內文改了，會列成「清單外改動」交人，人看過後用 `--reviewed` 記錄。同步完會再跑一次 `check`，問題列在輸出裡。

## 盤點與檢查

```bash
python3 .claude/teams/tools/deliverables.py status [--run <run_dir>]   # 齊全、過期、缺原料、等人補
python3 .claude/teams/tools/deliverables.py check [--run <run_dir>]    # 有問題 exit 1；帶 --run 時原料取自那個 run 的目標 repo
python3 .claude/teams/tools/deliverables.py matrix --run <run_dir> --stdout   # 只看追溯矩陣
python3 .claude/teams/tools/deliverables.py export    # 有 pandoc 就轉 docx
```

| 狀態 | 意思 |
|---|---|
| 齊全 | 小節都寫了，來源都是最新的；外部文件已附檔 |
| 過期 | 有小節的原料改了，或寫了還沒記錄來源 |
| 缺原料 | 自動文件還沒產生，也找不到原料 |
| 等人補 | 人補的文件還有小節沒寫；外部文件還沒附 |

`check` 只檢查交付設定裡列的文件，項目有：

- 檔頭（id、title、group、source）與檔名一致。
- 過期小節。
- 禁用字：讀 `banned_terms_file`，命中只印行號，不印內容。
- 隱私字串：電子郵件、本機路徑與暫存目錄、金鑰與 token、密碼的值、內部 agent 名稱、內網位址與主機（localhost、`*.internal`、`*.corp`…）、run 目錄名稱。比對前先把全形轉半形、去掉零寬字元與 HTML 實體，也抓拆成兩行的。命中只印種類與行號。`sync` 寫入前也掃，命中就不寫。
- 失效連結。
- 總目錄（`README.md`）和交付設定一致；不一致跑 `deliverables.py index`。

## 需求追溯矩陣

每條驗收條件一列：條件、需求／Story、spec 小節、驗證指令、結果、證據、commit（指令與證據裡的路徑只留檔名）。資料取自這個 run 的 `design.json`（子任務的 `acceptance`、`spec_refs`、`story_ids`）與 `test.json`（逐條驗收結果）。缺一環（沒有 spec 小節、沒有指令或證據、沒通過）時，該列的「缺的環節」會寫出來，`sync` 與 `matrix` 也會印出來。同一個 run 重跑只會換掉自己那一段。

## 守門

- team agent 只能跑 `deliverables.py status`、`check`、`affected`。包在 `bash -c`、`eval`、`pwsh -Command` 裡也照同一套規則；經 `xargs` 這類程式執行、看不到子指令時當成寫入。`configure`、`init`、`index`、`sync`、`matrix`、`export` 只由主 session 跑。
- team agent 不能寫 `deliverables.json` 與 `deliverables.state.json`（都在 `.claude/teams/` 底下），也不能寫 run 目錄的 `archive/`。
- 已知限制：hook 是輔助，不是信任邊界。用內嵌程式拼出路徑字串（例如 `'.claude/te' + 'ams'`）寫狀態檔擋不到；狀態檔被改或被刪，最多讓小節顯示錯的狀態，不影響閘門。
- tpm-writer 可以寫交付文件與交付摘要。
