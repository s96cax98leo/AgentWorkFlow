# 系統設計方法（SA／SD）

內建 profile 的系統分析（SA）與系統設計（SD）依 [System Design Primer](https://github.com/donnemartin/system-design-primer)（Donne Martin，CC BY 4.0）的思路。本文是我們依它整理的做法與檢查清單，用自己的話改寫，細節與例子請看原文。

方法寫在 profile 的 `stages.design.system_design`，是**預設 profile 的範例**，不是模版寫死的規定。要換方法或關掉，改專案的 `.claude/teams/methodology.json`，設成 `null` 就不套用。見 [`自訂與擴充.md`](自訂與擴充.md)。

## 在 SDLC 的哪裡

| 段 | 做什麼 | 誰檢查 |
|---|---|---|
| plan（SA） | intent 寫用例、限制、假設與量級：誰在什麼情境用、輸入輸出、使用者數、請求率、資料量、讀寫比、延遲與可用性目標。數字要有出處，沒有就標成假設。只寫問題空間，不寫解法 | plan 段的 skeptic |
| design（SD） | 照下面四步寫設計文件的「系統設計」節，第一行寫這次是功能層還是系統層，以及判斷理由 | design 段多派一個 skeptic，用 `system-design` lens 檢查 |

## 四個步驟

1. **用例、限制與假設**：把 intent 的 SA 結果帶進來，補上設計需要的數字。系統層要做量級粗估，例如尖峰 QPS、每月新增的儲存量、頻寬。
2. **高階設計**：列出主要元件與資料流，可以畫圖或條列，每個選擇都附理由。
3. **核心元件**：
   - API：REST 或 RPC、錯誤碼、冪等、分頁。
   - 資料模型與 schema：選 SQL 或 NoSQL 的理由、索引。
   - 元件內部的流程。
4. **擴展與取捨**：依第 1 步的限制找出瓶頸。每個取捨都要寫選了什麼、放棄了什麼、為什麼。

## 功能層與系統層

**每個需求都要做 SD**，深度依有沒有系統面決定：

| | 什麼時候 | 至少要寫 |
|---|---|---|
| 功能層 | 每個需求 | 第 1、3 步，加上和這次改動相關的第 4 步取捨（一致性、快取、非同步、失敗與重試、安全）。規模小可以精簡，但不能跳過；不適用的項目寫一句理由 |
| 系統層 | 新服務、新資料儲存、跨服務呼叫、對流量／延遲／可用性有要求、資料量會成長 | 四步都完整：第 1 步附量級粗估，第 4 步逐項檢查下面的主題 |

## 第 4 步的檢查主題

- **基本取捨**：
  - 效能 vs 擴展性：單一請求很快，不代表負載加倍時也撐得住。
  - 延遲 vs 吞吐量：目標通常是在可接受的延遲下，把吞吐量做到最大。
  - 可用性 vs 一致性：網路分區時只能在一致（CP）與可用（AP）之間選一個，要寫出選了哪個、為什麼。
- **一致性模式**：弱一致、最終一致、強一致，寫明每份資料用哪一種。
- **可用性模式**：
  - failover：主備（active-passive）或雙主（active-active）。
  - 複製。
  - 用數字表達可用性：幾個 9，串接的元件會把可用性往下乘。
- **入口與流量**：
  - DNS、CDN：push 或 pull。
  - 負載平衡：L4 或 L7、水平擴展。
  - 反向代理。
- **應用層**：微服務的切分理由、服務發現。
- **資料庫**：
  - 複製：主從或多主。
  - federation、分片、反正規化、SQL 調校。
  - SQL 還是 NoSQL：key-value、document、wide column、graph 各適合什麼。
- **快取**：
  - 放在哪一層：client、CDN、web server、資料庫、應用層。
  - 更新策略：cache-aside、write-through、write-behind、refresh-ahead。
  - 失效方式。
- **非同步**：訊息佇列、任務佇列、back pressure（佇列滿了怎麼辦）。
- **通訊**：TCP 或 UDP、RPC 或 REST，以及逾時、重試、冪等。
- **安全**：輸入驗證、最小權限、傳輸與儲存加密。

粗估時可參考原文附錄的「2 的次方表」與「每個工程師都該知道的延遲數字」。

## skeptic 的 system-design lens 會找什麼

- 每一步都有寫嗎？功能層或系統層的判斷對嗎？有系統面卻只做功能層，算問題。
- 第 1 步的數字有出處，或有標成假設嗎？
- 每個取捨都寫了放棄什麼嗎？
- 常見的漏洞：
  - 單點故障。
  - 沒說明一致性模型。
  - 沒處理失敗、重試或冪等。
  - 快取沒有更新與失效策略。
  - 同步呼叫鏈過長。
  - 佇列沒有 back pressure。

發現的問題和其他 lens 一樣列在 design 閘門，由決策者決定要修改（`sdlc-design-revise`）還是接受。
