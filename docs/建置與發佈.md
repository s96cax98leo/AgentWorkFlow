# 建置與發佈

`awf` 是 AgentWorkFlow 的單一執行檔，原始碼在 `crates/`。這份文件說明怎麼自己建置、發佈時執行檔怎麼進 `plugin/bin/`，以及目前的限制。

## plugin/bin 裡有什麼

| 檔案 | 用途 |
|---|---|
| `awf` | POSIX sh 啟動器。macOS、Linux、Git Bash 用它。 |
| `awf.cmd` | Windows 的啟動器（cmd、PowerShell 用它）。 |
| `awf-<平台>-<架構>` | 五個平台的執行檔，發佈前才 commit。 |
| `checksums.json` | 每個執行檔的 sha256，加上建置當時的原始碼雜湊。 |

啟動器只做一件事：挑出這台機器該用的執行檔，把參數與 exit code 原樣轉過去。它不放任何邏輯。

### 五個平台的檔名

| 平台 | Rust target | 檔名 |
|---|---|---|
| macOS（Apple 晶片） | `aarch64-apple-darwin` | `awf-darwin-arm64` |
| macOS（Intel，含 Rosetta 底下的終端機） | `x86_64-apple-darwin` | `awf-darwin-x64` |
| Linux x64 | `x86_64-unknown-linux-gnu` | `awf-linux-x64` |
| Linux arm64 | `aarch64-unknown-linux-gnu` | `awf-linux-arm64` |
| Windows x64 | `x86_64-pc-windows-msvc` | `awf-windows-x64.exe` |

這張表寫在 `crates/xtask/src/dist.rs` 的 `TARGETS`。`cargo xtask check-launchers` 會核對啟動器挑的檔名和它一致。

## 自己建置

你需要 Rust（版本下限見根目錄 `Cargo.toml` 的 `rust-version`）與一個 C 編譯器（內建的 SQLite 要編譯）。

```bash
cargo build --release          # 產物在 target/release/awf（Windows 是 awf.exe）
target/release/awf --version   # 印出 awf <版本> (source <原始碼雜湊>)
```

要讓 plugin 用你建的這一個，設環境變數 `AWF_BIN`：

```bash
export AWF_BIN="$PWD/target/release/awf"        # macOS、Linux、Git Bash
```

```powershell
$env:AWF_BIN = "$PWD\target\release\awf.exe"    # PowerShell
```

有設 `AWF_BIN` 時，兩個啟動器都直接執行它，不再看平台。它指的檔不存在時，啟動器印一行訊息並回 exit 127。

想要和發佈版同樣的檔名，用 `dist`：

```bash
cargo xtask dist                                 # 本機平台，輸出到 target/dist/
cargo xtask dist --target x86_64-apple-darwin --out /tmp/awf-dist
```

`dist` 建的是本機平台時，會跑一次 `--version`，確認編進去的原始碼雜湊和現在的原始碼相同。

## 原始碼雜湊

`awf --version` 印的雜湊，是 `crates/` 底下所有 `.rs` 與 `Cargo.toml`、根目錄 `Cargo.toml`、`Cargo.lock` 的 sha256 前 16 碼。算之前先把路徑排序、把 CRLF 換成 LF，所以三個作業系統算出同一個值。

算法只有一份，在 `crates/xtask/src/source_hash.rs`。`crates/awf/build.rs` 把它編進執行檔，`cargo xtask checksums` 用它核對。改了任何一個 Rust 原始檔，雜湊就會變，舊的執行檔就算過期。

## 發佈前的流程

執行檔只在發佈前 commit 一次。平常的 commit 不帶執行檔。

1. 確認要發佈的 commit 已經在 GitHub 上，而且 CI 是綠的。
2. 在 GitHub 的 Actions 頁手動執行 `ci` workflow（Run workflow），或推一個 tag。`dist` job 會在五個 runner 上各建一個執行檔，`dist-bundle` job 把五個收齊、寫好 `checksums.json`，整包上傳成名為 `plugin-bin` 的 artifact。
3. 下載 `plugin-bin`，把裡面的五個執行檔與 `checksums.json` 放進 `plugin/bin/`。
4. 補回執行權限（artifact 不保留檔案權限）：

   ```bash
   chmod +x plugin/bin/awf-darwin-* plugin/bin/awf-linux-*
   git add plugin/bin
   git update-index --chmod=+x plugin/bin/awf-darwin-arm64 plugin/bin/awf-darwin-x64 plugin/bin/awf-linux-x64 plugin/bin/awf-linux-arm64
   ```

5. 核對：

   ```bash
   cargo xtask checksums --check --require-all
   cargo xtask check-launchers
   ```

   第一個指令確認五個檔都在、sha256 和 `checksums.json` 相同、`checksums.json` 記的原始碼雜湊等於現在的原始碼，並實際執行本機平台的那一個，看它印的雜湊。
6. commit。這個 commit 只能有 `plugin/bin/` 的執行檔與 `checksums.json`。只要同一個 commit 還改了任何 Rust 原始檔，原始碼雜湊就對不上，要重跑第 2 步。

CI 自己不 commit、不 push。執行檔進版控這一步一定由人做。

### checksums 指令

```bash
cargo xtask checksums                       # 只印出內容，不寫檔
cargo xtask checksums --write               # 寫 plugin/bin/checksums.json
cargo xtask checksums --check               # 核對；目錄裡沒有執行檔時印「還沒有發佈用的執行檔」並通過
cargo xtask checksums --check --require-all # 發佈前用：五個缺一就失敗
cargo xtask checksums --dir <目錄> …        # 換一個目錄
```

`checksums.json` 的格式（鍵排序、縮排 2、結尾換行）：

```json
{
  "files": {
    "awf-darwin-arm64": "<sha256>"
  },
  "source": "<原始碼雜湊>"
}
```

每次 push，CI 的 `rust` job 都跑 `checksums --check`。開發期間 `plugin/bin/` 沒有執行檔，這一步直接通過。發佈之後有人改了原始碼卻沒重建執行檔，這一步就會失敗。

## 啟動器的檢查

```bash
cargo xtask check-launchers
```

這個指令不需要真的執行檔。它在暫存目錄放啟動器的副本與假的執行檔，再用假的 `uname` 模擬各個平台，核對：

- 每種 `uname` 組合挑到對的檔名（含 Git Bash、MSYS、Cygwin）。
- 參數原樣傳到（空白、引號、空字串、`*`、換行），exit code 原樣傳回。
- 經符號連結呼叫、以名字經 PATH 呼叫、`AWF_BIN`。
- 執行檔不存在、平台不支援時印一行訊息並回 exit 127。
- `awf` 通過 `sh -n`（有裝 dash、shellcheck 時也用它們檢查）、不超過 40 行、有執行權限。
- `awf.cmd` 的行尾是 CRLF、只有 ASCII、只用 cmd 內建指令、提到的檔名對得上檔名表。

在 macOS 與 Linux 上，`awf` 會實際執行，`awf.cmd` 只做靜態檢查。在 Windows 上反過來：`awf.cmd` 實際執行，`awf` 只做靜態檢查。

## 已知限制

- **執行檔沒有簽章。** CI 的檢查抓得到兩件事：執行檔過期（原始碼改了卻沒重建），以及檔案損壞或被換掉卻沒更新 `checksums.json`。它證明不了執行檔確實由這份原始碼建出：有寫入權限的人可以同時換掉執行檔與 `checksums.json`，執行檔印的雜湊也只是它自己宣稱的值。信任來自「誰能 commit 到這個 repo」與 review，不是來自這些檢查。不放心的人請自己建置並設 `AWF_BIN`。
- **macOS 的 Gatekeeper。** 透過 git 或 plugin 安裝拿到的檔通常不帶隔離標記，可以直接執行。用瀏覽器下載的檔會被擋，要自己移除隔離標記或自己建置。
- **musl 的 Linux（例如 Alpine）。** 啟動器照樣挑 `awf-linux-*`，這兩個檔連結 glibc，在 musl 上通常跑不起來。請自己建置並設 `AWF_BIN`。
- **glibc 版本。** Linux 的執行檔需要的 glibc 版本取決於 CI 建置用的 runner（x64 在 ubuntu 22.04、arm64 在 ubuntu 24.04）。更舊的發行版請自己建置。
- **Windows arm64。** 沒有原生版，兩個啟動器都挑 `awf-windows-x64.exe`，靠 Windows 的 x64 模擬執行。
- **`awf.cmd` 的訊息是英文。** cmd 用主控台的字碼頁讀批次檔，非 ASCII 的內容在某些字碼頁會讓指令解析出錯，所以這個檔只用 ASCII。
- **其他平台**（FreeBSD、32 位元、riscv 等）沒有執行檔。啟動器會印「不支援這個平台」並回 exit 127，請自己建置並設 `AWF_BIN`。
