# 開發模式總覽

這份文件說明 AgentWorkFlow 的整套工作方式。細節分散在其他文件，這裡只講「為什麼這樣做」與「各部分怎麼接起來」。

## 1. 核心想法

- **主 session 就是執行者，也是唯一和決策者對話的人。** subagent 平行做事、交回結構化的結果；主 session 整理、問決策者、記錄閘門、執行不可逆的動作。
- **先 plan、後動手。** 任何事件（開發、簡報、上游變動、會議……）都先列計畫：事件類型、要跑的 workflow、args、預計派幾個 agent、有哪些不可逆動作。決策者核准後才開始。
- **做事的人和驗收的人分開。** implementer 不驗自己的成果，verifier、reviewer、skeptic 只讀、只看證據，不採信作者的自述。
- **成果寫成檔案，交接只傳路徑。** 長內容在 agent 之間轉述會失真，所以每個 agent 把成果寫進 run 目錄或目標 repo，信封只放路徑、摘要與證據。
- **不可逆的事只有人能決定。** push、開 PR、寫上游、刪資料、對外寄送，一律停下來等決策者當下同意，agent 本身沒有這些權限。

## 2. 三層結構

| 層 | 放在哪 | 內容 | 誰維護 |
|---|---|---|---|
| plugin | `plugin/`（安裝到 Claude Code） | agent 定義、skill、slash command、hook | 本模版，所有專案共用 |
| 專案設定 | 目標專案的 `.claude/`、`CLAUDE.md`、`.mcp.json`（或 `.mcp.json.example`） | 硬規則 `rules.md`、守門設定 `guard.config.json`、workflow、schema、工具、golden-set | `init.py` 產生，之後專案自己調 |
| run 紀錄 | 目標專案的 `{{RUNS_DIR}}/<YYYYMMDD>-<事件>-<短名>/` | 每次執行的信封、筆記、證據、`run.json` | 每次執行時產生 |

workflow 放在專案層，是因為 Workflow 工具只讀專案的 `.claude/workflows/`。

## 3. 兩類工作

**開發需求**走 AI-native SDLC，五段、四個閘門：

```
plan ──[閘門1 intent 核准]──> design ──[閘門2 spec＋plan 核准]──> build ──> test ──[閘門3 結果確認]──> deliver ──[閘門4 推送／PR]
```

詳見 [`ai-native-sdlc.md`](ai-native-sdlc.md)。

**其他事件**走 `event-*` workflow，共通骨架是：

```
拆工或固定角度 → 平行處理 → skeptic 反駁 → writer 寫文件 →（必要時）自我驗收
```

事件裡發現要寫程式的工作，不在事件流程裡做，而是產出 intent 草稿，回到 SDLC 的 plan 段。詳見 [`事件處理.md`](事件處理.md)。

## 4. 閘門

閘門是決策者核准的節點。做法：

1. 每段 workflow 跑完，主 session **在對話裡**列出這段的重點：產出檔、skeptic 的質疑、所有 `open_questions`、建議與理由。不能只依賴工具狀態（見踩坑手冊「計畫被記為已核准但決策者沒看到」）。
2. blocking 的問題用選項式提問（AskUserQuestion），選項照信封裡的 `options`，每個選項附代價。
3. 決策者回覆後，**照字面讀**：「核准」才是核准；「調整一下 X」是要修改，不是核准。
4. 核准後記錄：
   ```bash
   python3 .claude/teams/tools/save_run.py approve <run_dir> <stage> --by "<誰，附核准內容摘要>" --at <ISO 時間>
   ```
5. 下一段的派工單會註明「依已核准的閘門派出，run.json 有紀錄」，讓 subagent 知道授權來源。

## 5. 派工與交接

- **派工單自足**：目標、依據檔、硬規則、驗收、回覆格式都寫在派工單裡，subagent 不需要看主 session 的對話就能做。範本見 [`agent-協作規則.md`](agent-協作規則.md)。
- **信封**：每個 agent 以 JSON 信封回報（`status`、`summary`、`artifacts`、`evidence`、`confidence`、`open_questions`、`derived_work`、`payload`）。Workflow 裡由 schema 強制，Agent 工具派出時由 `check-envelope` hook 驗證。
- **派工方式三選一**：
  - **Workflow 工具**：固定流程、要平行、要 schema 驗證時用。缺點是跑到一半不能等人輸入，所以每段 SDLC 一支 workflow，閘門由主 session 處理。
  - **Agent 工具**：敏感流程、需要逐段確認、或 Workflow 會誤轉授權時用（見踩坑手冊）。plugin 的 agent 帶命名空間，`subagent_type` 寫 `{{AGENT_NS}}<agent 名>`（預設 `agent-workflow:dev-implementer` 這種形式）。
  - **Agent Teams**（實驗功能）：多個 teammate 互相挑戰時用，例如 `team-debate`。

## 6. 決策者的介面

- **推播手機**：需要決策時用 PushNotification 推到決策者手機，決策者可以直接在手機回覆。推播內容要能單獨讀懂：哪個 run、哪一段、要決定什麼、選項。
- **選項式提問**：不問開放式問題，列 2–3 個選項與代價，可以標建議並附理由，但不替決策者決定。
- **不自編任務編號**：任務編號由 `{{TASK_AUTHORITY}}` 發。agent 發現的衍生工作寫進信封的 `derived_work`，只列不編號。

## 7. 守門：規則怎麼被強制

| 規則 | 強制方式 |
|---|---|
| 不推上游、agent 不 push、不 merge | `guard-bash` hook |
| 不碰 `{{FORBIDDEN_REPOS}}`、角色只寫自己的範圍 | `guard-paths` hook |
| 信封格式與語意（有 blocking 問題不能 done 等） | Workflow schema＋`check-envelope` hook＋`schemalib` |
| 文件不寫工時、不寫內部編號、署名行 | `check_rules.py` |
| 閘門核准紀錄 | `save_run.py` |
| 輸出語言 | `rules.md` 強規則＋派工單重申（目前無法機械檢查，靠多層重申） |

只靠提示限制寫入不夠：權限層先把寫入工具拿掉，腳本層再加保險，提示是第三層。

## 8. 一次 run 的目錄長什麼樣

```
{{RUNS_DIR}}/20260101-sdlc-export-csv/
├── run.json                 # 事件、目標、需求、各段狀態與核准紀錄（by、at、note）
├── research-*.md            # plan 段各調研角度的筆記
├── plan.json、design.json…  # 各段 workflow 回傳的信封（save_run.py stage 寫入並驗證）
├── <子任務>/                 # 需要實測的子任務各一個證據目錄
│   ├── README.md            # 證據表：項目｜證據檔｜結果；最後列「沒做的」
│   ├── 01-build.log、02-up.log…   # 依步驟編號的指令輸出
│   └── s01-*.png…           # 依順序編號的截圖
├── deliver/review.md        # 審查發現
├── pr-description.md        # PR 說明草稿
└── 執行紀錄.md               # 產出、驗證、跟計畫不同之處、刻意沒做的事、未能確認、衍生工作
```

證據的原則：每個結論都能回查到檔案或可重跑的指令；沒做到的事明寫「沒做的」，不要留白讓人以為做了。
