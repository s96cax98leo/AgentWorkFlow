# 自動合併信任模型

本文說明 AgentWorkFlow 怎麼讓 agent 有條件地合併 PR、各層防線分別擋什麼，以及啟用前要做的設定。決策脈絡見 [`adr-agent-auto-merge.md`](adr-agent-auto-merge.md)。範例一律用虛構的「示範客戶 ACME」（fork `acme-fork/app`、上游 `acme-up/app`）。

模版只管工作流程，不綁開發規範：需求怎麼寫、驗證怎麼做，由需求來源 adapter 與團隊自己的驗證決定（見〈需求來源 adapter〉）。

## 1. 信任邊界

| 層 | 元件 | 擋什麼 | 可信程度 |
|---|---|---|---|
| 伺服器端（真正的邊界） | GitHub ruleset、綁定 gate App 的 required check `agent-merge-gate/decision`、CODEOWNERS | 沒有通過 gate 的合併、直接推 main、改 gate 與設定不經人核准 | 高：client 端怎麼繞都過不了 |
| 確定性層 | `merge_gate.py`（從受保護的 base 執行）、`publish.py`、`save_run.py` 的政策判定 | 需求對照不一致、驗證未全過、head SHA 不符、高風險路徑、超過每日上限、凍結中；推送前的機敏值與分支檢查 | 中高：只看結構化輸入，不會被 PR 說明說服 |
| 角色層（輔助） | `plugin/hooks/guard.py`（Bash 與 PowerShell）、agent 的提示 | agent 與主 session 的誤操作：核准、越權合併、寫守門設定與稽核紀錄、推上游 | 低：client 端減速帶，可被其他 shell、其他工具或同名身分繞過 |

結論：**hook 只是輔助，伺服器端才是邊界。** 沒有完成第 2 節的 ruleset 與 App 設定前，不要啟用 `auto_merge`。

## 2. ruleset 基準線（目標 repo 的 main）

在目標 repo 的 Settings → Rules → Rulesets 新增一條，套用到預設分支：

1. **Require a pull request before merging**
   - 自動合併通道（只限 fork、最低風險等級）：required approvals 設 0，由 gate check 把關。
   - 開 Dismiss stale pull request approvals when new commits are pushed、Require approval of the most recent reviewable push。
   - 開 Require review from Code Owners（見第 4 節）。
2. **Require status checks to pass**
   - 加入 `agent-merge-gate/decision`，來源選 **gate App**，不要選 any source。任何有 write 權限的身分都能設 status，只有綁來源才有意義。
   - 開 Require branches to be up to date before merging；有用 merge queue 時，gate 也會在 `merge_group` 重跑。
3. **Do not allow bypassing the above settings**：bypass list 留空，admin 也不例外。
4. **Restrict updates**：只有 merger App 與人能更新 main；開 Block force pushes、Restrict deletions。
5. Actions 設定維持「不允許 GitHub Actions 建立或核准 pull request」。

CI 範本 `scaffold/.github/workflows/agent-merge-gate.yml.tmpl` **預設不複製**（沒有 gate App 時它會讓每個 PR 失敗）；完成本節與第 3 節的設定後，用 `init.py --with-merge-gate` 重跑，才會複製成目標專案的 `.github/workflows/agent-merge-gate.yml`。它用 `pull_request_target` 在 base 脈絡執行，**從受保護的 base 分支 checkout gate 與設定**，PR 只當資料（`git diff`），不執行 PR 自帶的 gate。工作區不是目標 repo 本身時（`REPOS_DIR` 有值），要把 `.github/workflows/agent-merge-gate.yml`、`.claude/teams/tools/merge_gate.py`、`schemalib.py`、`schemas/` 與 `guard.config.json` 一起放進目標 repo 的 main。

## 3. GitHub App 身分

用兩個由組織擁有的 GitHub App，不用個人 token：

| App | 權限 | 用途 |
|---|---|---|
| gate App | Checks: write、Pull requests: read、Contents: read | CI 用它回報 `agent-merge-gate/decision`；ruleset 綁它當來源 |
| merger App | Contents: write、Pull requests: write | steward 的 `gh pr merge` 以它的身分執行；也是 restrict updates 白名單裡唯一的機器身分 |

**merger App 的身分必須和 PR 作者不同。** GitHub 不允許對自己開的 PR request changes（端到端演練實測）：publish.py 用誰的身分開 PR，steward 就不能用同一個身分退回。PR 由人或另一個 App 開、steward 用 merger App 退回；做不到時，steward 退回只能留言加轉 draft。

ADR 與本文要寫明：App 擁有者、私鑰保管人、撤銷人、事故聯絡人。私鑰外洩時先撤銷 App 安裝，再輪換金鑰。CI 需要的設定：`vars.AGENT_GATE_APP_ID`、`secrets.AGENT_GATE_APP_PRIVATE_KEY`、`vars.AGENT_MERGER_BOT`（merger App 的 bot 帳號；gate 只採信它貼在 PR 的輸入留言）。

## 4. CODEOWNERS 管守門設定

在目標 repo 的 `.github/CODEOWNERS` 加：

```
/.claude/teams/guard.config.json   @acme-org/maintainers
/.claude/teams/tools/              @acme-org/maintainers
/.claude/hooks/                    @acme-org/maintainers
/.github/                          @acme-org/maintainers
```

搭配 ruleset 的 Require review from Code Owners，`auto_merge` 的任何變更（開關、白名單、風險上限、授權人）都必須經人核准的 PR。client 端也有對應的擋法：agent 一律不能寫 `guard.config.json`、`merge-audit.jsonl`、`publish-audit.jsonl` 與凍結檔；`auto_merge` 啟用後，主 session 也不直接改 `guard.config.json` 與稽核紀錄。merge_gate 也把改到這些路徑的 PR 一律判 escalate。

## 5. 設定鍵（`.claude/teams/guard.config.json`）

```json
"protected_branches": ["main", "master"],
"auto_merge": {
  "enabled": false,
  "repos": {"acme-fork/app": "low"},
  "merger_role": "agent-workflow:dev-merge-steward",
  "merge_method": "squash",
  "freeze_writers": ["agent-workflow:tpm-writer", "agent-workflow:dev-release-watcher"],
  "daily_cap": 5,
  "upstream_authorized_by": {},
  "freeze_file": "_tpm/runs/auto-merge.freeze.json",
  "small_lines": 100, "large_lines": 400, "large_files": 20,
  "carry_verdict_on_rebase": false
},
"requirements": {"source": "json", "path": "", "command": "", "id_pattern": ""}
```

- `repos`：白名單，值是該 repo 允許自動合併的最高風險等級（low／medium／high）。冷啟動期只開 low。
- `merger_role`：比對 hook 輸入的完整 `agent_type`。沒有命名空間的同名 agent（例如專案 `.claude/agents/dev-merge-steward.md`）或其他 plugin 的同名 agent 一律擋。設定值沒寫命名空間時自動補 `agent-workflow:`。
- `merge_method`：steward 的 `gh pr merge` 必須帶對應旗標（`--squash`／`--merge`／`--rebase`）。
- `small_lines`、`large_lines`、`large_files`：merge_gate 的風險分級門檻（可選）。
- `carry_verdict_on_rebase`：預設 false，head 一變就 hold，要重跑對照與驗證。設 true 時，PR rebase 後 gate 會自己用 git 算 patch-id（`git diff $(git merge-base <base> <sha>) <sha> | git patch-id --stable`），對照、驗證、審查當時的 commit 和目前 head 的 patch-id 相同，才沿用原本的結果，並在 `reasons`、`carried` 記一筆。patch-id 不同、算不出來（例如 CI 的 checkout 裡沒有 rebase 前的 commit）、沒給 `--base-sha` 時一律 hold。
  - **風險**：patch 相同不代表在新 base 上行為相同（base 的其他改動可能影響這個 PR）。required checks 仍然以目前 head 為準，但驗證報告不會重跑。所以這是放寬，要團隊明確開啟，冷啟動期不建議開。
- **放寬閘門一律 escalate**（內建，不能關）：merge_gate 遇到兩種情況會交人會簽，agent 不能自己決定放寬：
  - diff 改到測試、lint、型別或覆蓋率設定（jest／vitest／playwright／cypress／karma config、`pytest.ini`、`tox.ini`、`.coveragerc`、`.nycrc`、`codecov.yml`、`.eslintrc`、`eslint.config.*`、`tsconfig*.json`、`.flake8`、`ruff.toml`、`mypy.ini`、`.golangci.yml`、`.rubocop.yml`、`phpunit.xml`、`.stylelintrc`）。
  - diff 新增壓制註解（`eslint-disable`、`@ts-ignore`、`@ts-nocheck`、`@ts-expect-error`、`# type: ignore`、`# noqa`、`pragma: no cover`、`istanbul ignore`、`c8 ignore`、`//nolint`、`NOLINT`、`@SuppressWarnings`、`rubocop:disable`）。
- `requirements`：需求來源 adapter，見第 10 節。

## 6. hook 的放行條件（`guard.py` 的 `merge_refusal()`）

`gh pr merge` 只在以下條件**全部**成立時放行（Bash 與 PowerShell 一樣）：

1. `auto_merge.enabled` 為 true。
2. 完整 `agent_type` 等於 `merger_role`。
3. 指令是 `gh pr merge`（API 合併一律不放行），沒有 `--admin`，不含指令替換或變數展開。
4. repo 在 `auto_merge.repos` 白名單內，不在 forbidden_paths。
5. 帶 `--match-head-commit <40 字元 SHA>`，並帶 `merge_method` 對應的旗標。
6. `<runs_dir>/merge-audit.jsonl` 裡同 repo、PR、head_sha 的最後一筆紀錄是 `decision: merge`。
7. 上游 repo 要在 `upstream_authorized_by` 有有效的授權人（未過期）。
8. 沒有凍結（第 8 節）。

steward 另外可以在白名單 repo 上做：`gh pr review --request-changes`、`gh pr comment`、`gh pr ready --undo`。`--approve` 永遠擋，任何人都一樣；主 session 與其他 agent 仍不能合併；`dev-release-watcher` 的 gh 寫入（含 `gh run rerun`）一律擋。

## 7. 上游授權流程

上游第一版不做自動合併。我方決策者不能代上游授權。要開放某個上游 repo 時：

1. 查上游的 CONTRIBUTING 與 AI 政策；明文要求人在迴圈裡的，不開放。
2. 取得上游維護者的書面授權：連結、範圍（哪些路徑、哪個風險等級）、到期日。
3. 上游 org owner 安裝我方的 gate App 與 merger App，並在上游設同樣的 ruleset 基準線。
4. 經 PR＋CODEOWNERS 把授權寫進設定：

```json
"upstream_authorized_by": {
  "acme-up/app": {"by": "示範客戶 ACME 上游維護者", "link": "https://example.invalid/acme-up/app/discussions/1", "scope": "docs/ 與 tests/，low", "expires": "2027-06-30"}
}
```

5. 授權撤銷或到期：hook 與 gate 立即擋（`expires` 過期即失效）；從設定移除該項也走 PR。

## 8. 凍結與 revert

- **凍結旗標**：`auto_merge.freeze_file`，預設 `<runs_dir>/auto-merge.freeze.json`，內容 `{"frozen": true, "reason": "…", "merge_shas": [...], "proposal": "<revert 提案路徑>", "lift_when": "<解除條件>"}`。
- **誰寫**：`event-post-merge` 偵測到 main CI 在合併後轉紅、歸因到合併 commit 時，由 `freeze_writers`（預設 tpm-writer）用 Write 寫入。hook 只允許寫入 `frozen: true` 的內容，不允許 Edit、不允許寫 `frozen: false`，Bash 也不能動它。
- **效果**：檔案存在而且 `frozen` 不是 false（讀不懂也算凍結）時，hook 不放行 steward 的合併，`merge_gate.py` 一律判 hold。steward 仍可退回 PR。
- **合併後讀回**：`gh pr merge` 回報成功時，merge queue 或 auto-merge 可能只是排隊。steward 合併後一律用 `gh pr view --json state,mergedAt,mergeCommit` 讀回，填進 merge-decision 的 `merge_state`（merged／queued／not_merged）。`sdlc-merge` 只在 `merged` 時回報已合併；`queued` 時回傳 `queued: true`，不重派合併，也不產出 followup。
- **flaky 判準**：watcher 不 rerun。同一個 SHA 有失敗也有成功的 run 才算疑似 flaky；同一個 SHA 連續兩次、或連續兩個 commit 以同樣的測試失敗，就是真失敗。steward 遇到 required check 失敗一律照 gate 判 hold，疑似 flake 時寫進 followup，由人決定要不要重跑一次。
- **revert**：watcher 只寫 revert 提案，不 revert、不 push。由人決定並合併 revert PR（主 session 可以用 `publish.py` 開 revert 分支的 PR，合併仍由人做）。
- **解凍**：由人刪除凍結檔或改成 `frozen: false`，並在 run 紀錄寫明理由。

## 9. 稽核紀錄

`<runs_dir>/merge-audit.jsonl`（`merge_gate.py` 每次判定 append 一行）：

| 欄位 | 意思 |
|---|---|
| `timestamp` | 判定時間（ISO 8601） |
| `repo`、`pr`、`head_sha` | 判定對象；hook 依這三個欄位找最後一筆 |
| `decision` | merge／hold／escalate |
| `reasons` | 理由清單 |
| `risk_tier` | low／medium／high |
| `followups` | 不一致轉成的新需求（requirement_id、expected、actual、adjustment） |
| `carried` | 沿用 verdict 的紀錄（`carry_verdict_on_rebase` 開啟、patch-id 相同時才有） |
| `requirements_source` | 需求來源 adapter 與路徑 |
| `gate_version` | gate 版本 |

`<runs_dir>/publish-audit.jsonl`（`publish.py` 每次執行 append 一行）：`timestamp`、`repo`、`branch`、`base`、`head_sha`、`run`、`stage`、`decision`（published／pushed／dry-run／refused）、`reasons`、`pr_url`、`dry_run`。

本機 jsonl 只是 hook 的依據與快取；權威紀錄是 GitHub 上 gate App 寫的 check run。

## 10. 需求來源 adapter

`merge_gate.py` 與 steward 用同一份設定 `requirements` 取得需求清單，正規化成 `[{"id", "text", "source"}]`：

**json**：需求清單檔（陣列，或 `{"requirements": [...]}`）。

```json
"requirements": {"source": "json", "path": "specs/acme-export/requirements.json"}
```

```json
[{"id": "REQ-1", "text": "匯出按鈕下載 CSV", "source": "示範客戶 ACME Story"}]
```

**command**：團隊自己的腳本（從 issue、Story、PRD 轉出），stdout 輸出同上格式；執行時帶 `AWF_REPO`、`AWF_PR`、`AWF_HEAD_SHA`。

```json
"requirements": {"source": "command", "command": ["python3", "scripts/reqs_from_issue.py"]}
```

**spec-md**：內建的範例 adapter，逐行用 `id_pattern` 抓 ID。只是示範，不是規範。

```json
"requirements": {"source": "spec-md", "path": "specs/acme-export/spec.md", "id_pattern": "^\\s*[-*]\\s+\\*\\*(AC-\\d+)\\*\\*"}
```

沒設定或讀不到需求清單時，gate 一律判 hold。

## 11. 推送：`publish.py`

無人值守時，推分支與開 PR 由主 session 呼叫確定性工具，不交給 agent：

```
python3 .claude/teams/tools/publish.py push --repo-dir repos/app --branch feature/acme-export \
    --run _tpm/runs/20261024-sdlc-acme-export --title "示範：匯出 CSV" --body-file _tpm/runs/20261024-sdlc-acme-export/pr.md
```

它只推 `fork_repo` 的功能分支（`allowed_branch_prefixes`，不是 `protected_branches`），remote 指向上游就拒絕；推送前掃 diff 的金鑰樣式與 `--secrets-file` 的機敏值；要求 run.json 的 deliver 段已核准（政策核准時重跑 `save_run.policy_violations`）；最後 `gh pr create --repo <fork>`。hook 只看得到 `python3 …/publish.py`，所以主 session 呼叫時放行，`tpm-*`／`dev-*` 執行它一律擋。伺服器端的 ruleset 仍禁止直接推 main。

## 12. 啟用前檢查清單

- [ ] 只開我方 fork；上游沒有書面授權與 App 安裝前不開。
- [ ] 目標 repo 已設第 2 節的 ruleset（Do not allow bypassing、restrict updates、綁 gate App 的 required check）。
- [ ] gate App 與 merger App 已建立，擁有者、撤銷人、事故聯絡人已寫進 ADR。
- [ ] 已用 `init.py --with-merge-gate` 放入 `.github/workflows/agent-merge-gate.yml`（init 預設不放），它已在 main，並且在一個測試 PR 上跑出 `agent-merge-gate/decision`。
- [ ] 確認主 session 不會合併：`auto_merge.enabled` 為 true 時，即使 `main_session_github_rules` 設成 false，hook 也擋主 session 合併、核准與直接 push 受保護分支；使用者既有的「主 session 直接合併」習慣要先改掉。
- [ ] CODEOWNERS 涵蓋 `guard.config.json`、`.claude/teams/tools/`、`.claude/hooks/`、`.github/`。
- [ ] `requirements` 已設定，`merge_gate.py check` 在示範 PR 上能讀到需求清單。
- [ ] merge 與 release 脫鉤：合併到 main 不會自動發佈、部署或打 tag。
- [ ] 合併後訊號存在（main CI），`event-post-merge` 能讀到。
- [ ] `repos` 只開 low，`daily_cap` 設保守值。
- [ ] 以上都由人確認後，經 PR＋CODEOWNERS 把 `auto_merge.enabled` 改成 true。

本機 hook 不是安全邊界；本模型不宣稱達到 SLSA L4 或任何合規等級。
