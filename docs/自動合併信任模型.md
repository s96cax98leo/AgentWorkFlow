# 自動合併信任模型

本文說明 AgentWorkFlow 怎麼讓 agent 有條件地合併 PR、各層防線分別擋什麼，以及啟用前要做的設定。決策脈絡見 [`adr-agent-auto-merge.md`](adr-agent-auto-merge.md)。範例一律用虛構的「示範客戶 ACME」（fork `acme-fork/app`、上游 `acme-up/app`）。

模版只管工作流程，不綁開發規範：需求怎麼寫、驗證怎麼做，由需求來源 adapter 與團隊自己的驗證決定（見〈需求來源 adapter〉）。

## 1. 信任邊界

| 層 | 元件 | 擋什麼 | 可信程度 |
|---|---|---|---|
| 伺服器端（真正的邊界） | GitHub ruleset、綁定 gate App 的 required check `agent-merge-gate/decision`、CODEOWNERS | 沒有通過 gate 的合併、直接推 main、改 gate 與設定不經人核准 | 高：client 端怎麼繞都過不了 |
| 確定性層 | `awf merge-gate`（從受保護的 base 執行）、`awf publish`、`awf save-run` 的政策判定 | 需求對照不一致、驗證未全過、head SHA 不符、高風險路徑、超過每日上限、凍結中；推送前的機敏值與分支檢查 | 中高：只看結構化輸入，不會被 PR 說明說服 |
| 角色層（輔助） | `awf hook` 的守門規則（Bash 與 PowerShell）、agent 的提示 | agent 與主 session 的誤操作：核准、越權合併、寫守門設定與稽核紀錄、推上游 | 低：client 端減速帶，可被其他 shell、其他工具或同名身分繞過 |

結論：**hook 只是輔助，伺服器端才是邊界。** 沒有完成第 2 節的 ruleset 與 App 設定前，不要啟用 `auto_merge`。repo 本身的安全政策與漏洞回報方式見 [`SECURITY.md`](../SECURITY.md)。

### 1.1 hook 是減速帶，可以被繞過

hook 在使用者的電腦上執行，靠解析指令字串判斷要不要擋。它擋得住常見的誤操作，但擋不住刻意繞過。下面幾類字串比對擋不住（實測過）：

- **事先設好的別名**：先前設好的 `gh alias`、shell alias 或函式，呼叫時看不出底下是 `gh pr merge` 或 `git push`。
- **拆碎或編碼後再執行**：把檔名、指令拆成多段字串、用 base64 等編碼，或寫進腳本檔再執行，hook 只看得到「執行某個腳本」。
- **間接讀機敏檔**：`cp .env` 到別的檔名再讀、`source` 之後用 `env` 印出、用直譯器的 `open()` 讀檔。
- **用直譯器打 API**：Python、Node 等直譯器跑腳本檔，直接呼叫 GitHub API 合併或核准。
- **包裝過的切換目錄**：用變數、`eval` 或別名包住 `cd`、`git -C`，hook 算不出指令實際在哪個 repo 執行。
- **token 外流**：拿到 token 後不經過 Claude Code，直接打 API。

所以合併、推送、核准能不能發生，最後要由**伺服器端**決定：ruleset、綁定 gate App 的 required check、CODEOWNERS、GitHub App 的最小權限。hook 的價值是讓 agent 的誤操作在本機就被擋下、並留下理由，不是安全保證。

### 1.2 hook 失敗時的取捨

plugin 以 user scope 安裝時，hook 會套在使用者**所有專案**。「hook 壞掉就鎖死所有工具」不能接受，所以 plugin 註冊的 hook 採取以下取捨（`crates/awf-core/src/hooks/mod.rs` 開頭的說明為準）：

| 情況 | 守門（guard-shell、guard-paths） | 交件（envelope） |
|---|---|---|
| hook **跑不起來**（找不到執行檔、逾時） | 放行（`hooks.json` 設 `onFailure: continue`，timeout 10 秒） | 放行 |
| 跑得起來，但輸入壞掉（空、不是 JSON、缺欄位） | 擋（exit 2） | 放行 |
| shell 指令超過 128KB | 擋。guard 的規則耗時隨指令長度約平方成長，拖到逾時就等於放行，所以直接擋超長指令 | — |
| 守門設定載入失敗，或程式內部出錯 | 改用 `awf hook` 內建的最小規則：擋 push、`gh pr merge`、`--approve`、GitHub API 寫入，其他放行；規則開始跑之後才出錯而且是 team agent 時一律擋 | — |
| 守門模組執行中出現意外錯誤 | 擋 | 放行 |

交件 hook 出錯時刻意放行：它擋不住任何寫入，出錯時擋下只會卡住所有 subagent。信封仍會由 workflow 的 `schema`、`awf save-run stage` 再驗一次，缺件一律當成 missing。

**要更嚴就用 project 模式**：`awf init --hooks project` 把 hook 註冊在專案的 settings，寫入執行檔的絕對路徑與 timeout 10，可以改成 `onFailure: block`，讓「跑不起來也擋」。啟用 `auto_merge` 的專案建議用這個模式。即使如此，信任邊界仍然在伺服器端。

## 2. ruleset 基準線（目標 repo 的 main）

在目標 repo 的 Settings → Rules → Rulesets 新增一條，套用到預設分支：

1. **Require a pull request before merging**
   - 自動合併通道（只限 fork、最低風險等級）：required approvals 設 0，由 gate check 把關。
   - 開 Dismiss stale pull request approvals when new commits are pushed、Require approval of the most recent reviewable push。
   - 開 Require review from Code Owners（見第 4 節）。
2. **Require status checks to pass**
   - 加入 `agent-merge-gate/decision`，來源選 **gate App**，不要選 any source。任何有 write 權限的身分都能設 status，只有綁來源才有意義。
   - 開 Require branches to be up to date before merging；有用 merge queue 時，gate 也會在 `merge_group` 重跑。
3. **Do not allow bypassing the above settings**：bypass list 留空，admin 也不例外。
4. **Restrict updates**：只有 merger App 與人能更新 main；開 Block force pushes、Restrict deletions。
5. Actions 設定維持「不允許 GitHub Actions 建立或核准 pull request」。

CI 範本 `plugin/scaffold/.github/workflows/agent-merge-gate.yml.tmpl` **預設不複製**（沒有 gate App 時它會讓每個 PR 失敗）；完成本節與第 3 節的設定後，用 `awf init --with-merge-gate` 重跑，才會複製成目標專案的 `.github/workflows/agent-merge-gate.yml`，並把 gate 的執行檔（`awf-linux-x64`）與記它 sha256 的 `checksums.json` 放進 `.claude/teams/bin/`（取自 plugin 的 `bin/`；模版裡沒有這支執行檔時 init 會停下並說明，可以用 `--merge-gate-bin <路徑>` 指定）。它用 `pull_request_target` 在 base 脈絡執行，**從受保護的 base 分支 checkout gate 與設定**，PR 只當資料（`git diff`），不執行 PR 自帶的 gate；執行前先用 `sha256sum` 核對執行檔和 `checksums.json` 記的一致（抓檔案損壞；信任來自 base 受保護與 CODEOWNERS，不是這個雜湊）。工作區不是目標 repo 本身時（`REPOS_DIR` 有值），要把 `.github/workflows/agent-merge-gate.yml`、`.claude/teams/bin/`（執行檔與 `checksums.json`）、`.claude/teams/schemas/` 與 `guard.config.json` 一起放進目標 repo 的 main。plugin 更新後用 `awf init --upgrade` 換執行檔，經 PR 由人核准後進 base。

## 3. GitHub App 身分

用兩個由組織擁有的 GitHub App，不用個人 token：

| App | 權限 | 用途 |
|---|---|---|
| gate App | Checks: write、Pull requests: read、Contents: read | CI 用它回報 `agent-merge-gate/decision`；ruleset 綁它當來源 |
| merger App | Contents: write、Pull requests: write | steward 的 `gh pr merge` 以它的身分執行；也是 restrict updates 白名單裡唯一的機器身分 |

**merger App 的身分必須和 PR 作者不同。** GitHub 不允許對自己開的 PR request changes（端到端演練實測）：awf publish 用誰的身分開 PR，steward 就不能用同一個身分退回。PR 由人或另一個 App 開、steward 用 merger App 退回；做不到時，steward 退回只能留言加轉 draft。

ADR 與本文要寫明：App 擁有者、私鑰保管人、撤銷人、事故聯絡人。私鑰外洩時先撤銷 App 安裝，再輪換金鑰。CI 需要的設定：`vars.AGENT_GATE_APP_ID`、`secrets.AGENT_GATE_APP_PRIVATE_KEY`、`vars.AGENT_MERGER_BOT`（merger App 的 bot 帳號；gate 只採信它貼在 PR 的輸入留言）。

## 4. CODEOWNERS 管守門設定

在目標 repo 的 `.github/CODEOWNERS` 加：

```
/.claude/teams/guard.config.json   @acme-org/maintainers
/.claude/teams/bin/                @acme-org/maintainers
/.claude/hooks/                    @acme-org/maintainers
/.github/                          @acme-org/maintainers
```

搭配 ruleset 的 Require review from Code Owners，`auto_merge` 的任何變更（開關、白名單、風險上限、授權人）都必須經人核准的 PR。client 端也有對應的擋法：agent 一律不能寫 `guard.config.json`、`merge-audit.jsonl`、`publish-audit.jsonl` 與凍結檔；`auto_merge` 啟用後，主 session 也不直接改 `guard.config.json` 與稽核紀錄。merge_gate 也把改到這些路徑的 PR 一律判 escalate。

## 5. 設定鍵（`.claude/teams/guard.config.json`）

```json
"protected_branches": ["main", "master"],
"auto_merge": {
  "enabled": false,
  "repos": {"acme-fork/app": "low"},
  "merger_role": "agent-workflow:dev-merge-steward",
  "merge_method": "squash",
  "return_to_draft": true,
  "freeze_writers": ["agent-workflow:tpm-writer"],
  "daily_cap": 5,
  "upstream_authorized_by": {},
  "freeze_file": "_tpm/runs/auto-merge.freeze.json",
  "small_lines": 100, "large_lines": 400, "large_files": 20,
  "carry_verdict_on_rebase": false,
  "allowed_skipped_checks": []
},
"requirements": {"source": "json", "path": "", "command": "", "id_pattern": ""}
```

- `repos`：白名單，值是該 repo 允許自動合併的最高風險等級（low／medium／high）。冷啟動期只開 low。
- `merger_role`：比對 hook 輸入的完整 `agent_type`。沒有命名空間的同名 agent（例如專案 `.claude/agents/dev-merge-steward.md`）或其他 plugin 的同名 agent 一律擋。設定值沒寫命名空間時自動補 `agent-workflow:`。換成角色名不同的 agent 時，`awf save-run` 與執行核心照這個設定值把它當合併角色（模型下限 strong、不自動重派、沒寫紀錄時依合併決定代寫），自訂腳本不能派它；只認設定檔，不認 trace 的說法。
- `merge_method`：steward 的 `gh pr merge` 必須帶對應旗標（`--squash`／`--merge`／`--rebase`）。`sdlc-merge` 的派工單照這個值寫合併指令（`awf next` 帶進 args，`--set` 蓋不掉；不是這三種時派工單寫 squash）。
- `return_to_draft`（預設 true）：退回 PR 時要不要用 `gh pr ready --undo` 轉回 draft。設成 false 時只留 request-changes（PR 不能轉 draft 的 repo，或團隊不用 draft 的時候用）；不合併、產出新需求照舊。
- `small_lines`、`large_lines`、`large_files`：merge_gate 的風險分級門檻（可選）。
- `daily_cap`：每日（UTC）合併上限。本機 gate 數 `merge-audit.jsonl` 裡當天的 merge 紀錄；CI 端見第 8 節。
- `allowed_skipped_checks`：required check 被 skipped 或 neutral 時預設**不算通過**（被跳過＝沒驗到）。只有列在這裡的 check 名稱才算通過。預設 `[]`。
- `required_checks`（選填，範本沒有預設這個鍵）：專案自己列的必過 check 名稱。有列時，每個名稱都要出現在 gate 收到的 `--checks` 裡，少一個就 hold（沒出現＝沒驗到）；只會讓 gate 更嚴。`awf ci render --write` 會把 profile 的 `ci.jobs` 裡 `required: true` 的 job 名稱加進來（只加不刪）。
- `freeze_writers`：能寫凍結檔的 agent（完整 agent_type），只能寫 `frozen: true`。`dev-release-watcher` 只讀，不在這裡。
- `upstream_authorized_by`：見第 7 節。值可以是字串，或 `{by, link, scope, expires}`。
- `carry_verdict_on_rebase`：預設 false，head 一變就 hold，要重跑對照與驗證。設 true 時，PR rebase 後 gate 會自己用 git 算 patch-id（`git diff $(git merge-base <base> <sha>) <sha> | git patch-id --stable`），對照、驗證、審查當時的 commit 和目前 head 的 patch-id 相同，才沿用原本的結果，並在 `reasons`、`carried` 記一筆。patch-id 不同、算不出來（例如 CI 的 checkout 裡沒有 rebase 前的 commit）、沒給 `--base-sha` 時一律 hold。
  - **風險**：patch 相同不代表在新 base 上行為相同（base 的其他改動可能影響這個 PR）。required checks 仍然以目前 head 為準，但驗證報告不會重跑。所以這是放寬，要團隊明確開啟，冷啟動期不建議開。
- **跟上 base（`sdlc-sync`）**：PR 落後或有衝突時，steward 在分析模式填 `needs_sync`、判 hold，不退回 PR、不做 gh 寫入，也不自己同步（`gh pr update-branch` 會在伺服器端改寫分支，hook 對所有人當成 GitHub 寫入）。同步由 dev-integrator 照 `awf sync-branch` 的策略做；head 變了一律重跑 `sdlc-test`。走中轉分支時開新 PR 取代原 PR，新 PR 一樣要經過完整的對照、skeptic 與 merge gate，信任邊界不變。
- **放寬閘門一律 escalate**（內建，不能關）：merge_gate 遇到兩種情況會交人會簽，agent 不能自己決定放寬：
  - diff 改到測試、lint、型別或覆蓋率設定（jest／vitest／playwright／cypress／karma config、`pytest.ini`、`tox.ini`、`.coveragerc`、`.nycrc`、`codecov.yml`、`.eslintrc`、`eslint.config.*`、`tsconfig*.json`、`.flake8`、`ruff.toml`、`mypy.ini`、`.golangci.yml`、`.rubocop.yml`、`phpunit.xml`、`.stylelintrc`）。
  - diff 新增壓制註解（`eslint-disable`、`@ts-ignore`、`@ts-nocheck`、`@ts-expect-error`、`# type: ignore`、`# noqa`、`pragma: no cover`、`istanbul ignore`、`c8 ignore`、`//nolint`、`NOLINT`、`@SuppressWarnings`、`rubocop:disable`）。
- `requirements`：需求來源 adapter，見第 10 節。

## 6. hook 的放行條件（守門規則的 `merge_refusal()`）

`gh pr merge` 只在以下條件**全部**成立時放行（Bash 與 PowerShell 一樣）：

1. `auto_merge.enabled` 為 true。
2. 完整 `agent_type` 等於 `merger_role`。
3. 指令是 `gh pr merge`（API 合併一律不放行），沒有 `--admin`，不含指令替換或變數展開。
4. repo 在 `auto_merge.repos` 白名單內，不在 forbidden_paths。
5. 帶 `--match-head-commit <40 字元 SHA>`，並帶 `merge_method` 對應的旗標。
6. `<runs_dir>/merge-audit.jsonl` 裡同 repo、PR、head_sha 的最後一筆紀錄是 `decision: merge`。
7. 上游 repo 要在 `upstream_authorized_by` 有有效的授權人（未過期）。
8. 沒有凍結（第 8 節）。

steward 另外可以在白名單 repo 上做：`gh pr review --request-changes`、`gh pr comment`、`gh pr ready --undo`。`--approve` 永遠擋，任何人都一樣；主 session 與其他 agent 仍不能合併；`dev-release-watcher` 的 gh 寫入（含 `gh run rerun`）一律擋。

## 7. 上游授權流程

上游第一版不做自動合併。我方決策者不能代上游授權。要開放某個上游 repo 時：

1. 查上游的 CONTRIBUTING 與 AI 政策；明文要求人在迴圈裡的，不開放。
2. 取得上游維護者的書面授權：連結、範圍（哪些路徑、哪個風險等級）、到期日。
3. 上游 org owner 安裝我方的 gate App 與 merger App，並在上游設同樣的 ruleset 基準線。
4. 經 PR＋CODEOWNERS 把授權寫進設定：

```json
"upstream_authorized_by": {
  "acme-up/app": {"by": "示範客戶 ACME 上游維護者", "link": "https://example.invalid/acme-up/app/discussions/1", "scope": "docs/ 與 tests/，low", "expires": "2027-06-30"}
}
```

5. 授權撤銷或到期：hook 與 gate 立即擋。`expires` 以判定當天的日期比較，當天仍有效；過期、日期讀不懂、`by` 空白都和沒有授權一樣（gate 判 escalate），hook 與 gate 規則一致。從設定移除該項也走 PR。

## 8. 凍結與 revert

- **凍結旗標**：`auto_merge.freeze_file`，預設 `<runs_dir>/auto-merge.freeze.json`，內容 `{"frozen": true, "reason": "…", "merge_shas": [...], "proposal": "<revert 提案路徑>", "lift_when": "<解除條件>"}`。
- **誰寫**：`event-post-merge` 偵測到 main CI 在合併後轉紅、歸因到合併 commit 時，由 `freeze_writers`（預設 tpm-writer）用 Write 寫入。hook 只允許寫入 `frozen: true` 的內容，不允許 Edit、不允許寫 `frozen: false`，Bash 也不能動它。
- **效果**：檔案存在而且 `frozen` 不是 false（讀不懂也算凍結）時，hook 不放行 steward 的合併，`awf merge-gate` 一律判 hold。steward 仍可退回 PR。
- **合併後讀回**：`gh pr merge` 回報成功時，merge queue 或 auto-merge 可能只是排隊。steward 合併後一律用 `gh pr view --json state,mergedAt,mergeCommit` 讀回，填進 merge-decision 的 `merge_state`（merged／queued／not_merged）。`sdlc-merge` 只在 `merged` 時回報已合併；`queued` 時回傳 `queued: true`，不重派合併，也不產出 followup。
- **flaky 判準**：watcher 不 rerun。同一個 SHA 有失敗也有成功的 run 才算疑似 flaky；同一個 SHA 連續兩次、或連續兩個 commit 以同樣的測試失敗，就是真失敗。steward 遇到 required check 失敗一律照 gate 判 hold，疑似 flake 時寫進 followup，由人決定要不要重跑一次。
- **revert**：watcher 只寫 revert 提案，不 revert、不 push。由人決定並合併 revert PR（主 session 可以用 `awf publish` 開 revert 分支的 PR，合併仍由人做）。
- **解凍**：由人刪除凍結檔或改成 `frozen: false`，並在 run 紀錄寫明理由。
- **CI 端的凍結**：凍結檔在 gitignore 裡的 run 目錄，CI 從受保護的 base checkout 看不到它。所以 CI 範本改讀 repo variable **`AGENT_AUTOMERGE_FROZEN`**：沒設或設成 `false` 才算未凍結，其他任何值（`true`、`1`、寫錯字）一律當成凍結，以 `--frozen` 傳給 gate，判 hold。
  - 凍結：`gh variable set AGENT_AUTOMERGE_FROZEN --body true`（或在 Settings → Secrets and variables → Actions → Variables 新增）。
  - 解凍（由人做）：`gh variable set AGENT_AUTOMERGE_FROZEN --body false`。
  - `event-post-merge` 建議凍結時，人要**同時**設這個 variable，CI 才會擋；只寫本機凍結檔，擋得住本機的 hook 與 gate，擋不住 CI。
- **CI 端的每日上限**：CI 每次都是全新的 runner，沒有本機的 `merge-audit.jsonl`，所以每日上限改用 GitHub API 算：`gh pr list --state merged --search "merged:>=<今天>"`，只計 `mergedBy` 是 `vars.AGENT_MERGER_BOT` 的 PR（人合併的不算）。結果以 `--merged-today` 傳給 gate，和本機 audit 的計數取大者再和 `daily_cap` 比較；查詢失敗時傳 `unknown`，gate 判 hold。「今天」與 gate 的判定時間用同一個時間點（UTC），避免跨午夜時對不上。

## 9. 稽核紀錄

`<runs_dir>/merge-audit.jsonl`（`awf merge-gate` 每次判定 append 一行）：

**哪一個專案的設定與稽核檔**：閘門（`awf merge-gate`、`awf save-run` 的 stage／approve／escalate、`awf publish`、`awf done`／`awf approve`）不看「在哪個目錄執行」。專案根的順序是 `--project-dir` → 環境變數 `CLAUDE_PROJECT_DIR` → 從目前目錄往上找含 `.claude/teams/VERSION` 的目錄，取**最外層**那一個（子目錄可以是 PR 的 checkout，自帶的 `.claude/teams/` 不採用；路徑上不只一個時在 stderr 說明用了哪一個）；都找不到就報錯，不退回目前目錄。設定、schema、開發規範 profile、稽核檔都取自同一個專案根；run.json 已有 recipe 而專案沒有 profile 檔時不採信（不退回內建節重算）。hook 讀稽核檔用的是 Claude Code 給的 `CLAUDE_PROJECT_DIR`：Claude Code 的專案就是最外層套用過的那個目錄時，兩邊是同一個位置；不是的話（例如在已套用的專案底下再開一個專案），hook 找不到 gate 的紀錄、合併會被擋，這時在 gate 的指令帶 `--project-dir`。

| 欄位 | 意思 |
|---|---|
| `timestamp` | 判定時間（ISO 8601） |
| `repo`、`pr`、`head_sha` | 判定對象；hook 依這三個欄位找最後一筆 |
| `decision` | merge／hold／escalate |
| `reasons` | 理由清單 |
| `risk_tier` | low／medium／high |
| `followups` | 不一致轉成的新需求（requirement_id、expected、actual、adjustment） |
| `carried` | 沿用 verdict 的紀錄（`carry_verdict_on_rebase` 開啟、patch-id 相同時才有） |
| `requirements_source` | 需求來源 adapter 與路徑 |
| `gate_version` | gate 版本 |

`<runs_dir>/publish-audit.jsonl`（`awf publish` 每次執行 append 一行）：`timestamp`、`repo`、`branch`、`base`、`head_sha`、`run`、`stage`、`decision`（published／pushed／dry-run／refused）、`reasons`、`pr_url`、`dry_run`。

本機 jsonl 只是 hook 的依據與快取；權威紀錄是 GitHub 上 gate App 寫的 check run。

## 10. 需求來源 adapter

`awf merge-gate` 與 steward 用同一份設定 `requirements` 取得需求清單，正規化成 `[{"id", "text", "source"}]`：

**json**：需求清單檔（陣列，或 `{"requirements": [...]}`）。

```json
"requirements": {"source": "json", "path": "specs/acme-export/requirements.json"}
```

```json
[{"id": "REQ-1", "text": "匯出按鈕下載 CSV", "source": "示範客戶 ACME Story"}]
```

**command**：團隊自己的腳本（從 issue、Story、PRD 轉出），stdout 輸出同上格式；執行時帶 `AWF_REPO`、`AWF_PR`、`AWF_HEAD_SHA`。

```json
"requirements": {"source": "command", "command": ["python3", "scripts/reqs_from_issue.py"]}
```

**spec-md**：內建的範例 adapter，逐行用 `id_pattern` 抓 ID。只是示範，不是規範。

```json
"requirements": {"source": "spec-md", "path": "specs/acme-export/spec.md", "id_pattern": "^\\s*[-*]\\s+\\*\\*(AC-\\d+)\\*\\*"}
```

**openspec**：需求清單＝規格目錄裡這次變更的差異檔碰到的情境（見 `docs/自訂與擴充.md`〈需求來源用規格層〉）。

```json
"requirements": {"source": "openspec", "path": "openspec"}
```

這個來源的清單讀的是**執行 gate 那個目錄的檔案**，要分兩種情況看：

| 在哪裡跑 | 清單取自 | team agent 改得到嗎 | 怎麼防 |
|---|---|---|---|
| 本機（steward 跑 `awf merge-gate check --recipe <run.json>`） | 專案工作目錄的 `openspec/changes/<名>/specs/**` | 改得到（dev-* 有寫入權） | gate 把現在的規格和 run.json 記下的基準比（design 核准時記的條目清單與差異檔雜湊；沒有 design 段的 recipe 用 plan 核准時記的）：條目變少、差異檔變了、id 對到別的條目、run.json 沒有基準，一律 hold |
| CI（`agent-merge-gate.yml`，沒有 run.json、不帶 `--recipe`） | 受保護的 base 分支的 checkout | 改不到（PR 的內容不會進來） | 不需要基準。但也因此**變更要先在 base 上**：差異檔如果是這個 PR 才加的，base 上沒有這個變更，CI 的 gate 會判 hold |

限制：CI 沒有 run.json，所以「和核准時的基準比」只在本機的 gate 生效；CI 那一關靠的是 base 分支受保護。本機不帶 `--recipe` 直接跑 gate 時沒有基準可比，清單就是工作目錄現在的樣子（`sdlc-merge` 的派工單固定帶 `--recipe`）。

沒設定或讀不到需求清單時，gate 一律判 hold。

## 11. 推送：`awf publish`

無人值守時，推分支與開 PR 由主 session 呼叫確定性工具，不交給 agent：

```
awf publish push --repo-dir repos/app --branch feature/acme-export \
    --run _tpm/runs/20261024-sdlc-acme-export --title "示範：匯出 CSV" --body-file _tpm/runs/20261024-sdlc-acme-export/pr.md
```

它只推 `fork_repo` 的功能分支（`allowed_branch_prefixes`，不是 `protected_branches`），remote 指向上游就拒絕；推送前掃 diff 的金鑰樣式與 `--secrets-file` 的機敏值；要求 run.json 的 deliver 段已核准（政策核准時重跑 `awf save-run` 的 `policy_violations`）；最後 `gh pr create --repo <fork>`。hook 只看得到 `awf publish`，所以主 session 呼叫時放行，`tpm-*`／`dev-*` 執行它一律擋。伺服器端的 ruleset 仍禁止直接推 main。

## 11.1 本機合併（`conventions.merge.mode: local`）

給不開 PR、由人在本機合併的專案用。和自動合併是兩條路，不能同時設（`auto_merge.enabled: true` 時 `awf next` 報錯）。

做法：merge 段不派合併 agent。`awf next` 回 `manual`，請人自己把分支合進主線（要留合併 commit）；人合併之後跑 `awf next --run <run_dir> --confirm-merge --by <誰>`，工具只做核對與記錄。

**保證的（確定性核對，任何一項讀不到或不成立都不算完成）**

- 整條閘門鏈到 deliver 都已核准，recipe 沒有被改鬆（和 `awf publish` 同一個檢查）。
- 沒有還沒確認的暫定做法；有被略過的子任務時要人當下確認。
- 凍結旗標沒設。
- 主線上有一個合併 commit，它合進來的正好是 test 段驗證過的那個 commit（審查之後分支又有改動就不算；快轉合併沒有合併 commit 也不算）。
- 合併前後的 diff 通過 recipe 的 diff 反查（例如 docs recipe 不能改到程式）。
- 通過後在 `merge-audit.jsonl` 留一筆 `decision: local-merge`（誰確認的、合併 commit、審過的 commit、各項檢查）。

**不保證的**

- 合併是誰做的：`--by` 是自己填的，工具無法分辨人與主 session。agent 與主 session 的 git 限制照守門規則（hook），而 hook 是減速帶；本機沒有伺服器端的 ruleset、required check、CODEOWNERS 可以擋。
- 合併 commit 的內容等於「主線＋審過的 commit」：解衝突時人可以改任何東西，工具只看 diff 的形狀，不重跑測試、不重新審查。
- 不做 PR 路徑上 `awf merge-gate` 的其他檢查：required checks、測試數下降、skip、風險等級、白名單、每日上限、上游授權。
- 之後有沒有推到遠端、遠端有沒有保護，不在這裡的範圍。

結論：本機合併只證明「人合併進主線的，是走完閘門、驗證過的那個 commit」，信任的是做合併的那個人。要伺服器端強制的保證，用 PR 與 ruleset。
