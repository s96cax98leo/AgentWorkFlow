# 事件處理

開發需求以外的工作都是「事件」。形狀相同的事件（會議、決策落地、Demo 前檢查、需求變動、上游變動，以及你自己定義的類型）共用 `event.js` 一支 workflow，事件類型是資料；形狀不同的（簡報、PR 審查、合併後監看）各有一支 `event-*.js`。範本在 plugin 的 `workflow-templates/`，由 `awf.py next` 產生腳本，入口是 `/event`、`/brief`、`/demo-check` 或 `tpm-team` skill。

## 1. 共通骨架

```
（Baseline：需要證明零寫入時，先記錄外部狀態）
   ▼
拆工（tpm-planner）或固定角度
   ▼
平行處理（tpm-researcher（含上游模式）／tpm-reviewer，每個角度一個）
   ▼
tpm-skeptic 反駁（逐則；不確定就判反駁成立）
   ▼
tpm-writer 寫文件（只用未被推翻的發現；被推翻的列「未能確認」），跑 check_rules.py --audience <internal|owner|external>
   ▼
（Accept：有驗收標準時逐條自我驗收）
```

共通規則：

- 事件流程**不寫程式**。發現要開發的事，產出 intent 草稿（`<run_dir>/intent-draft-<主題>.md`）交 SDLC 的 `sdlc-plan`。
- **缺件不是「沒有發現」**：任何 agent 沒交件（回 null、信封不合格、執行失敗或 throw）時記為 missing。分析、反駁、寫作、驗收哪一步缺件，workflow 都回傳 `halted: true`、`stage`（停在哪一段）、`halt_reason`（`缺件：<label>`）與 `missing` 清單，連同已完成的部分一起交回主 session，不當成空清單或「沒有被推翻」。
- 平行分析的事項 id 帶角度前綴（`<角度>:<原 id>`，例如 `conflict:1`、`impact:2`），不同角度的事項不會撞號，skeptic 的判定才對得回去。
- 給決策者的文件（`給決策者.md`）一律跑 `check_rules.py --audience owner`；writer 沒交出給決策者版或沒過檢查時 halted。
- 對外部系統全程唯讀：不留言、不改狀態、不切換主工作目錄的分支。
- 每個數字和結論附 `路徑:行號` 或可重跑的指令；查不到就寫「未能確認」。
- 衍生工作寫進 `derived_work`，只列不編號，交 `{{TASK_AUTHORITY}}` 編號。
- 文件依讀者跑 `check_rules.py --audience`：`internal`＝內部文件、`owner`＝給決策者版、`external`＝對外文件（後兩者不得出現內部編號）。
- 執行前先建 run 目錄：
  ```bash
  python3 .claude/teams/tools/save_run.py init <run_dir> --event <事件> --target <repo> --requirement "<描述>"
  ```
  workflow 回傳的 JSON 由 `awf.py done --run <run_dir>` 存檔並驗證（它轉給 `save_run.py stage`）。

## 2. 各事件

### 簡報（`event-brief`）

`{{TASK_AUTHORITY}}` 發來一份任務單（`{{BRIEFS_DIR}}/{{TASK_ID_PREFIX}}<編號>_*.md`）。任務單是唯一的指示來源。

| 階段 | agent | 做什麼 |
|---|---|---|
| Plan | `tpm-planner` | 拆子任務；`kind=code`／`test` 的標「轉 SDLC」；不可逆節點寫進 acceptance |
| Work | `tpm-researcher`（上游相關的子任務用上游模式） | 依相依分層，每層平行；前一層的結果帶進下一層。直接或間接依賴轉 SDLC 子任務的子任務標為 waiting，這次不跑 |
| Challenge | `tpm-skeptic` | 逐則反駁所有發現 |
| Write | `tpm-writer` | 依任務單指定的產出路徑寫文件，通常是對外版、research 版、執行紀錄三件套 |
| Accept | `tpm-skeptic` | 對任務單的驗收標準逐條給 pass／fail／not_verifiable 與證據 |

args：`brief`、`run_dir`。

回傳：`to_sdlc`（轉 SDLC 的子任務）、`waiting`（等 SDLC 完成才能跑的子任務）、`results`、`challenge`、`docs`、`accept`；有 waiting 時另有 `next`，說明要等哪些 SDLC 子任務合併後重跑 `event-brief`（或由主 session 另派）。等 SDLC 才能完成的驗收條目判 not_verifiable。

### 上游變動（`event`，類型 `upstream`）

上游有新 PR、main 前進或 CI 失敗。

| 階段 | 做什麼 |
|---|---|
| Baseline | 記錄上游狀態：main head SHA、開著的 PR 數、我方 PR 的 head SHA 與更新時間、分支數 |
| Analyze | `tpm-researcher`（上游模式）四個角度：conflict（`git merge-tree` 預測與我方每條分支的衝突並分類）、impact（改了哪些目錄、契約、migration）、timeline（絕對時間、含時區，不推論意圖）、action（該通知誰、要誰決定什麼、我方選項與代價） |
| Challenge | skeptic 重跑唯讀指令查證 |
| Write | 報告附開工與收尾的上游狀態對照，**證明零寫入**；另寫 `給決策者.md`（發生什麼、對我方的影響、要誰決定什麼、選項與代價），需要開發的寫 intent 草稿 |

args：`what`、`repo`、`run_dir`。全程只用 `git fetch` 到唯讀 ref 與 `git merge-tree`，不切分支。

回傳：`before`、`after`（開工與收尾的上游狀態）、`claims`（各角度的發現）、`refuted`（被推翻的 id）、`challenge`、`docs`。舊名 `tpm-upstream-analyst` 已併入 `tpm-researcher` 的上游模式。

### 會議（`event`，類型 `meeting`）

會議紀錄或逐字稿進來。五個角度平行抽取：交辦、決議、風險與依賴、要更新的文件、給上層系統的待辦。skeptic **對照原文**檢查有沒有誤讀或腦補，writer 寫會議摘要與待辦清單。

args：`source`、`run_dir`。

### PR 審查（`event-pr-review`）

審一個不是自己 SDLC 開發的 PR 或分支。

- 預設六個 lens：standards、spec、bugs、security、design、history，每個 lens 一個 `tpm-reviewer`；可用 `lenses` 只跑部分。
- 去重後每批由 skeptic 反駁，只留信心 ≥0.8 且未被推翻的。
- **只產報告，不留言、不核准**。要不要把意見貼到 PR 上，由決策者決定、由主 session 執行。

args：`target`、`repo`、`run_dir`（可加 `lenses`）。

### 合併後監看（`event-post-merge`）

`sdlc-merge` 合併之後，或 main 的 CI 變紅、要確認是不是自動合併造成。

| 階段 | 做什麼 |
|---|---|
| Watch | `dev-release-watcher` 讀 `<runs_dir>/merge-audit.jsonl` 與 main 的 CI（只讀），把失敗歸因到合併 commit，提出 `git revert <sha>` 的範圍 |
| Challenge | skeptic 檢查歸因；被推翻的歸因改列「未確認」，不影響凍結 |
| Write | tpm-writer 寫 `revert-proposal.md`、`給決策者.md`；有 blocker 時寫凍結旗標。路徑先讀 `guard.config.json` 的 `auto_merge.freeze_file`（預設 `<runs_dir>/auto-merge.freeze.json`），實際寫入的路徑列在交件的 documents。之後 hook 與 `merge_gate.py` 都不放行合併 |

watcher 沒有 Write，結果由信封交給 writer 落檔。Challenge 缺件時 halted，有 blocker 就建議主 session 先凍結再重跑。

**CI 看不到本機的凍結檔**：要讓 CI 端的 merge gate 也擋，人要同時設 repo variable `AGENT_AUTOMERGE_FROZEN=true`（見 [`自動合併信任模型.md`](自動合併信任模型.md)〈凍結與 revert〉）。**不 revert、不 push、不合併**：主 session 用 PushNotification 推播決策者，revert PR 由人決定、由人合併。

args：`repo`、`run_dir`（可加 `gh_repo`、`merge_sha`、`since`）。

### 需求變動（`event`，類型 `reqs-change`）

需求快照或 User Story 更新。

| 階段 | 做什麼 |
|---|---|
| Diff | 先抽出新舊差異 |
| Impact | 四個面向平行：specs（目標 repo 的 spec、契約、測試裡的 Story ID）、program（backlog、範圍、路線圖、風險）、deliverables（對外交付的文件與表格）、capability（能力對照、已排入的 demo 範圍） |
| Challenge／Write | 影響清單 `impact.md`；必要時產出新 intent 草稿交 SDLC |

需求取消（不是變更）時，對進行中的 SDLC run 跑 `save_run.py abandon <run_dir> --reason … --by … --at …`，之後不能再核准或推送。

args：`change`、`run_dir`（可加 `repo`）。

### 決策落地（`event`，類型 `decision`）

`{{DECISION_OWNER}}` 或 `{{STAKEHOLDER}}` 定案一件事後，找出所有要跟著改的地方。四個面向平行：專案工作區文件、目標 repo 的規範層、agent／skill／hook／rules、程式與 backlog。產出待改清單 `changes.md`、`給決策者.md` 與修改草稿；需要改程式或共用檔的寫 intent 草稿交 SDLC。**不直接改共用檔**。

args：`decision`（決策原文與出處）、`run_dir`。回傳：`items`、`refuted`（被推翻的 id）、`docs`。

### Demo 前檢查（`event`，類型 `demo-check`）

五個面向平行，只讀或本機操作：

| 面向 | 檢查 |
|---|---|
| env | 分支與 commit、服務能不能起、健康檢查、版本與 demo 腳本一致 |
| data | 帳號、租戶、種子資料、模型與 MCP 設定是否就緒（只檢查有沒有值，不印金鑰） |
| flow | 逐步走 demo 腳本，每步標 green／yellow／red 與證據 |
| ui | demo 會出現的頁面在指定尺寸下有沒有破版、錯字、console error（截圖存 run 目錄） |
| fallback | 網路、模型、外部服務失效時的備案（錄影、靜態頁、離線資料） |

skeptic 專門反駁綠燈，writer 寫紅綠燈清單；需要開發的產出 intent 草稿。

args：`target`、`run_dir`（可加 `script`、`date`）。

本機起服務時，compose 指令一律帶專屬的 `-p <專案名>`，避免撞到本機同名專案（見踩坑手冊）。

## 3. 不是 workflow 的事件

### 方案辯論（`team-debate` skill）

要比較 ≥3 個方案、或 design 段遇到架構取捨時用。每個方案一位 teammate 負責並互相挑戰，lead 彙整成比較表（選項、代價、風險、建議與理由），交決策者選。使用 Agent Teams（實驗功能，需先開啟）。

### 網站分析（`site-report` skill）

`tech-architect`、`infra-analyst`、`biz-analyst`、`perf-auditor`、`competitor-scout` 五個面向平行，`lead-synthesizer` 交叉驗證後合成總報告。規則：

- 抓外部網站前先看 robots.txt；不做任何會改變對方狀態的動作。
- 洞察要有 ≥2 個來源佐證；矛盾不強行調和，兩邊都列出。

## 4. 新增一種事件

### 自訂事件類型（不用寫程式）

事件的形狀是「幾個角度平行找 → skeptic 反駁 → writer 寫文件」時，在專案的 `.claude/teams/methodology.json` 加一筆 `events` 就好。例：事故回顧。

```json
{
  "events": {
    "incident": {
      "title": "事故回顧",
      "args": ["incident"],
      "optional": ["env"],
      "context": "事故：{incident}\n環境：{env|正式環境}\nrun 目錄：{run_dir}\n只讀。",
      "gather": {
        "label": "look",
        "angles": [
          { "key": "timeline", "ask": "重建時間線（絕對時間）。" },
          { "key": "cause", "ask": "列出可能的原因與證據。" }
        ]
      },
      "challenge": { "ask": "逐項反駁，不確定判 refuted=true：" },
      "write": {
        "ask": "寫事故回顧 {run_dir}/incident-review.md。payload 用 docs。",
        "data": [{ "label": "成立", "from": "kept" }, { "label": "存疑", "from": "doubted" }]
      }
    }
  }
}
```

用法：

```bash
python3 .claude/teams/tools/awf.py start --run _tpm/runs/20261112-incident-export --event incident --set incident="INC-1 匯出逾時"
python3 .claude/teams/tools/awf.py next --run _tpm/runs/20261112-incident-export
```

| 欄位 | 說明 |
|---|---|
| `args`、`optional` | 必要與選填的參數名。必要參數缺了，`awf.py next` 回 `need_input` |
| `context` | 每張派工單開頭的背景。`{參數名}` 換成參數值，`{參數名\|預設}` 在沒給時用預設，`{run_dir}` 是 run 目錄 |
| `payload` | 各角度交 `items`（預設）或 `findings` |
| `before`、`after` | 選填的前置與收尾步驟（各最多 3 步，依序、各派一個 tpm-researcher）：`name`、`label`、`ask`；`stop_if_empty` 有寫時，清單是空的就正常結束 |
| `gather.angles` | 角度清單（1～8 個），每個有 `key` 與 `ask`。各派一個 tpm-researcher，label 是 `<gather.label>:<key>` |
| `gather.heading`、`body`、`tail`、`data` | 調整派工單的排版與附帶資料，通常不用寫 |
| `challenge.ask` | 要 tpm-skeptic 怎麼反駁；事項清單會自動接在後面。`only_status` 可以只反駁某個 status 的事項 |
| `write.ask` | 要 tpm-writer 寫什麼、寫到哪。`data` 是附在後面的資料：`all`、`kept`（沒被推翻的）、`doubted`（被推翻或沒被驗證的）、`doubted_ids`，或前後步驟的 `name` |
| `write.owner_check` | `true`＝要交出給決策者版並通過 `check_rules.py --audience owner`，否則停下交人 |
| `returns` | 回傳的鍵名（`all` 預設 `items`、`doubted` 預設 `refuted`） |

規則：

- 角色固定是 tpm-researcher、tpm-skeptic、tpm-writer，不能換成別的 agent。
- 缺件一律停下交人；skeptic 沒判到的事項當成沒被驗證，列進存疑。
- 事件名不能用 `sdlc`、`brief`、`pr-review`、`post-merge`、`merge` 與 SDLC 的段名。和內建類型（`meeting`、`decision`、`demo-check`、`reqs-change`、`upstream`）同名時，整筆取代內建的定義。
- 改完跑 `python3 .claude/teams/tools/awf.py doctor`，它會用 schema 與語意規則檢查這份設定。

內建五種類型的完整定義在 plugin 的 `workflow-templates/event.js`（`BUILTIN_EVENTS`），可以當範例。

### 形狀不同的事件

要先拆工、要逐條驗收、或角色不同時，才需要自己寫一支 workflow：見 [`自訂與擴充.md`](自訂與擴充.md)「新增 workflow」。
