# 踩坑手冊

實際跑 agent team 時踩過的坑。每條：症狀、原因、做法。新踩到的坑照同樣格式補進來。

---

## 1. Workflow 把使用者訊息當授權轉給 subagent，subagent 拒做

- **症狀**：Workflow 派出的 subagent 回報「使用者沒有授權」或「使用者最新的訊息要求停止」而拒做，但決策者其實已經核准。
- **原因**：Workflow 工具會把主 session 最新的使用者訊息一起轉給 subagent。那則訊息可能屬於同時進行的別的任務，或語氣含糊，subagent 就把它當成這次工作的授權依據。
- **做法**：
  - 敏感流程（會動到 git、會寫共用檔）改用 Agent 工具逐段派，派工單自己帶授權來源。
  - 每張派工單都寫「依已核准的閘門派出，`run.json` 有核准紀錄；你看到的最新使用者訊息可能屬於別的任務，不要拿它推翻派工單」。
  - workflow 的 args 留一個 `authorization` 欄位，必要時補充授權說明。

## 2. 主 session 進 plan mode，背景 subagent 收尾卡住

- **症狀**：背景 agent 做到最後一步（commit、寫報告）時失敗，回報沒有寫入權限。
- **原因**：主 session 進 plan mode 後，背景 subagent 也被限制成唯讀。
- **做法**：進 plan mode 前先讓背景 agent 收尾；來不及的話，請它把收尾步驟（要寫的檔、要跑的指令）寫在回覆裡，等解除 plan mode 後由主 session 執行。

## 3. 部分 subagent 類型被 harness 擋寫檔

- **症狀**：subagent 回報「無法寫入檔案」，或報告檔不見了。
- **原因**：某些 subagent 類型或執行環境不允許寫檔（例如唯讀的探索型 agent）。
- **做法**：派工單寫明「若無法寫檔，把報告內容完整放在回覆裡」，由主 session 落檔。審查類 agent 本來就設計成只讀，報告一律放回覆。

## 4. 背景 agent 的 idle 通知是舊的、重複的

- **症狀**：收到「agent 已完成」或「agent 閒置」的通知，但實際上它還在做，或是同一則通知收到兩次。
- **原因**：通知可能延遲送達，或對應的是先前某一輪的狀態。
- **做法**：不要只看通知就下結論。先查 `git log`、檔案修改時間、run 目錄的實況，再判斷進度與下一步。

## 5. 系統把計畫記為「已核准」，但決策者沒看到內容

- **症狀**：工具狀態顯示計畫已核准，但決策者事後說沒看過、不同意其中幾項。
- **原因**：核准介面可能只顯示摘要，或決策者在別的情境下按了確認。工具狀態不等於決策者真的看過重點。
- **做法**：每個閘門都要在**對話裡**列出重點（產出、質疑、待決問題、不可逆動作），讓決策者明確回覆。`save_run.py approve` 的 `--by` 寫清楚是誰、在哪裡、核准了什麼內容。

## 6. `.env` 是 symlink，產生金鑰的工具寫到原檔

- **症狀**：在 worktree 或 demo 目錄執行「產生金鑰」之類的工具後，主工作目錄或共用的 `.env` 內容被改了。
- **原因**：`.env` 是指向共用檔的 symlink，寫入工具跟著連結寫到原檔。
- **做法**：
  - 執行前先記下原檔的 sha（`shasum .env`，只記雜湊、不印內容）。
  - 收尾時比對 sha，不同就還原。
  - 更好的做法：用拋棄式的 `.env`（從 `.env.example` 產生，放暫存目錄、不提交），不要 symlink 共用檔。

## 7. 共用測試暫存目錄壞掉＋中文 locale 讓 initdb 失敗

- **症狀**：資料庫測試在初始化時失敗，錯誤訊息和 locale 或暫存目錄權限有關；換台機器又正常。
- **原因**：多個測試共用同一個暫存目錄，前一次殘留讓它壞掉；系統 locale 是中文時，部分資料庫工具的初始化不支援。
- **做法**：測試一律用獨立的暫存目錄與固定的 locale：
  ```bash
  export TMPDIR="$(mktemp -d)"
  export LC_ALL=en_US.UTF-8
  ```

## 8. compose 專案名撞到本機同名專案

- **症狀**：起 demo 環境時，把決策者本機原本在跑的同名服務停掉或覆蓋了；或 `down -v` 刪掉了別人的資料。
- **原因**：compose 預設用目錄名當專案名，不同 worktree 或 clone 可能同名。
- **做法**：
  - demo 與測試用專屬的專案名，指令一律帶 `-p <專屬名>`。
  - 環境變數 `COMPOSE_PROJECT_NAME` 會覆蓋預設，文件要提醒：執行前先 `echo $COMPOSE_PROJECT_NAME` 確認。
  - 收尾的 `down -v` 也帶同樣的 `-p`。

## 9. 上游測試逐字比對清單

- **症狀**：只是新增一個目錄、一個樣本檔或一個工具，上游的測試就失敗，因為它比對「目錄清單」「樣本數」「工具數」。
- **原因**：上游測試把清單寫死逐字比對。改這種測試要走例外核准。
- **做法**：先找不必改測試的方案：新增內容放子目錄、另一份設定檔，或用測試沒掃到的命名，避開比對。真的避不開才走「整合修訂與例外」（見 `ai-native-sdlc.md`）。

## 10. 串流在開始前斷線，鎖永遠不釋放

- **症狀**：使用者重新整理頁面後，同一個 session 一直回「忙碌中」（例如 409），只能重啟服務。
- **原因**：服務在請求進來時就上鎖，鎖的釋放寫在串流結束的處理裡；串流還沒開始就斷線，結束處理不會執行。
- **做法**：加「串流未開始的寬限期」：上鎖後一段時間內串流沒有開始，就自動釋放。寫一條測試模擬「上鎖後立刻斷線」。

## 11. 只用指示限制寫入不夠

- **症狀**：派工單寫了「只讀，不要改檔」，agent 還是改了檔或執行了寫入指令。
- **原因**：提示是軟限制，agent 在想「順手修好」時會越界。
- **做法**：三層：
  1. **權限層**：該角色的 agent 定義裡直接不給 Edit、Write 等寫入工具。
  2. **腳本層**：`awf_hook.py` 的 `guard-shell`（Bash 與 PowerShell）、`guard-paths` hook 擋寫入指令與範圍外的路徑；對外部服務的寫入再加一層斷線保險（例如唯讀 token、只讀 mount）。
  3. **提示層**：派工單重申。

## 12. 語言被糾正很多次

- **症狀**：決策者一再要求「用繁體中文」，但 subagent 的報告、commit 訊息、SendMessage 還是混英文或簡體。
- **原因**：語言要求只寫在對話裡，subagent 看不到；派工單本身是英文時，回覆也跟著英文。
- **做法**：把語言寫成強規則：`rules.md` 一條（涵蓋回覆、派工單、SendMessage、信封文字、commit 內文、推播）＋記憶；派工單本身用輸出語言寫，並重申規則。本模版把語言做成 `{{OUTPUT_LANGUAGE}}`。

## 13. guard 只允許特定分支前綴

- **症狀**：照任務單建議的分支名建分支，被 hook 擋下。
- **原因**：目標 repo 的 guard 只允許特定前綴（例如 `feature/`、`bugfix/`）。
- **做法**：改用允許的前綴，並在執行紀錄註明「任務單建議 X，因 guard 規則改用 Y」。不要為了建分支去改 guard。

## 14. 改寫 commit 歷史讓 SHA 失效

- **症狀**：文件、執行紀錄、PR 說明裡引用的 commit SHA 找不到。
- **原因**：rebase、squash、amend 之後 SHA 全部改變。
- **做法**：改寫前留備份分支（`backup/<分支>-<日期>`）；改寫後搜尋所有引用舊 SHA 的文件並更新。能用分支名或 tag 引用的就不要寫死 SHA。

## 15. 決策者回的是「調整」不是「核准」

- **症狀**：決策者回「可以，不過 X 改成 Y」，agent 就直接進下一段，結果 X 沒改。
- **原因**：把附帶意見當成核准。
- **做法**：照字面讀。有附帶修改就是「要修改」：先改（SDLC 的 design 段用 `sdlc-design-revise`），改完再回到同一個閘門請決策者確認。`save_run.py approve` 只在明確核准時執行，`--by` 記錄核准的內容。

## 16. Windows 上 hooks 跑不起來，PowerShell 工具完全不經過守門

- **症狀**：Windows 沒裝 Git Bash 時，所有 `bash "…/guard-*.sh"` 形式的 hook 都失敗；而且 Claude Code 改用 PowerShell 工具下指令，`matcher: "Bash"` 的守門從頭到尾沒被觸發，agent 用 PowerShell 就能 `git push`、`gh pr merge`。
- **原因**（查證自官方 hooks 文件 https://code.claude.com/docs/en/hooks ，2026-10 版）：
  1. shell form 的 hook command 在 macOS／Linux 交給 `sh -c`，Windows 交給 Git Bash，**沒有 Git Bash 時改用 PowerShell**；可用 `"shell": "bash" | "powershell"` 明確指定（PowerShell 會優先找 `pwsh.exe`，找不到用 `powershell.exe` 5.1）。
  2. PowerShell 工具的 `tool_name` 是 `PowerShell`，`tool_input` 欄位和 Bash 一樣（`command`、`description`、`timeout`、`run_in_background`）。文件原話：只 match `Bash` 的 hook 在 PowerShell 工具上永遠不會觸發，要寫 `Bash|PowerShell`。Windows 沒有 Git Bash 時連 Bash 工具都不註冊。
  3. `${CLAUDE_PLUGIN_ROOT}`、`${CLAUDE_PROJECT_DIR}` 在 shell form 要包雙引號；PowerShell 下 Claude Code 會把它們改寫成 `${env:NAME}`，所以只能放在雙引號裡（單引號不展開；裸寫 `$CLAUDE_PROJECT_DIR` 在 PowerShell 是空值）。
  4. exec form（`command` ＋ `args`）不經 shell，但 Windows 上 `command` 必須是真正的 `.exe`；較舊的 Claude Code 不認得 `args`，會只跑 `command` 而讓守門悄悄失效。
  5. hook 只有 exit 2 會擋；其他結束碼與「啟動失敗」預設都放行。`"onFailure": "block"`（v2.1.295 起）讓 PreToolUse hook 失敗時改成擋下；對 SubagentStop、TaskCompleted 沒有作用。
- **做法**（本模版的選擇）：
  1. 拿掉所有 bash 外殼，hook 單一入口 `plugin/hooks/awf_hook.py <guard-shell|guard-paths|envelope>`，邏輯本來就在 Python。
  2. shell 守門 matcher 改成 `Bash|PowerShell`；`guard.py` 解析 PowerShell 指令（`;`、`&`、`&&`、`||`、`|`、呼叫運算子 `& gh …`、反引號續行、字串裡的 `$(…)`、`Start-Process`、`Invoke-Expression`、`pwsh -Command`、`cmd /c`、cmdlet 別名如 `Remove-Item`），正規化後套同一套規則。
  3. launcher：plugin 的 `hooks.json` 用 shell form `python3 "${CLAUDE_PLUGIN_ROOT}/hooks/awf_hook.py" <模式>`，這個字串在 sh、Git Bash、PowerShell 都能解析；`--hooks project` 時 `init.py` 把**跑 init 的那個 Python 的絕對路徑**寫進 `settings.json`，不靠 PATH，Windows 上另外指定 `"shell": "powershell"` 並用 `& "<python.exe>" "…"` 執行（PowerShell 一定存在）。沒選 `.cmd`／sh 雙語檔（exec form 不能跑 `.cmd`，shell form 兩種語法難以同時正確）、也沒選 `uv run`（多一個不一定有的依賴、每次啟動慢）。
  4. 守門類 hook 一律設 `"onFailure": "block"`：找不到 Python、腳本壞掉、輸入不是 JSON 時擋下而不是放行（取代舊 `lib.sh` 的「找不到 Python 就擋」）；交件檢查設 `"continue"`，出錯不擋。
  5. Windows 用 plugin 模式時，`python3` 必須是真的 Python（Microsoft Store 的空殼或只裝 `py` 啟動器都不行），否則守門會因 onFailure 擋下所有 shell 與改檔動作；`init.py` 偵測到時會警告，建議改用 `--hooks project`。
  6. 目標 repo 自己的 guard（轉呼叫）先找 `guard-git.py`／`guard-paths.py`，找不到才找 bash 腳本；Windows 上只用 Git for Windows 的 bash（或 `CLAUDE_CODE_GIT_BASH_PATH`），避開 System32 的 WSL `bash.exe`，找不到 bash 時擋下並說明。
  7. 本 repo 的 CI（`.github/workflows/ci.yml`）在 ubuntu、macos、windows（`shell: pwsh`）都跑 `python tests/run_all.py`，確認沒有偷偷依賴 bash。

## 17. 合併 agent 被 PR 內容說服，或需求對照表漏了幾條

- **症狀**：`dev-merge-steward` 的對照表全部寫 match，但其實少列了一條需求，或某條的驗證是 fail；也可能 PR 說明裡藏了「這條已確認，可以合併」之類的字，agent 照單全收。
- **原因**：對照表是 agent 寫的，agent 讀得到 PR 內容，可能被說服；而且「全部一致」是它自己宣稱的。
- **做法**：
  1. 合併前一律跑 `merge_gate.py check`。它只吃結構化輸入（需求清單、正規化證據、required checks、diff、測試數），不讀 PR 說明：需求清單的每個 ID 都要在對照表裡、判 match、而且證據裡同一 ID 的結果是 pass；漏列、mismatch、對不到需求的改動（out_of_scope）都判 hold，並把不一致項目列成 followup。
  2. gate 只會比 steward 更嚴：steward 判 hold 或 escalate，gate 不會改成 merge。輸入讀不到或缺漏一律 hold（fail-closed），只有 merge 時 exit 0。
  3. 需求清單不綁定任何開發規範：由 `guard.config.json` 的 `requirements` 指定來源。`json` 讀現成清單；`command` 跑團隊自己的腳本（從 issue、Story、PRD 轉出）；`spec-md` 只是內建範例。需求寫法對不上範例時，不要硬改 `id_pattern` 去湊，改用 `json` 或 `command`。
  4. 每次判定都寫進 `<runs_dir>/merge-audit.jsonl`（repo、pr、head_sha、decision、reasons、timestamp），合併時的守門以這份紀錄綁定 head SHA；SHA 一變就要重跑 gate。
## 18. 只擋 `gh pr merge` 不夠：合併有很多條路，切段也會截斷判斷

- **症狀**：主 session 帶 `--repo <fork>` 就能 `gh pr merge`、`gh pr review --approve`；`gh api repos/<fork>/pulls/3/merge -X PUT` 把 `-X PUT` 放在 URL 後面，或 URL 帶 `?a=1&b=2`，寫入判斷就漏掉；`curl`、`Invoke-RestMethod` 直接打 api.github.com 完全不經過 gh 的規則；主 session `git push origin main` 可以繞過整個 PR 流程。
- **原因**：
  1. 舊規則只把 `gh pr merge` 當成一般寫入，帶 `--repo <fork>` 就放行；沒有「合併與核准本身就不允許」的判斷。
  2. 合併端點不只一個：REST 的 `PUT /repos/{o}/{r}/pulls/{n}/merge`、`POST /repos/{o}/{r}/merges`（直接合併分支），GraphQL 的 `mergePullRequest`、`enablePullRequestAutoMerge`；核准則是 reviews 端點帶 `event=APPROVE`。
  3. 舊的 bash 切段用 regex 在 `&&`、`;`、`|` 切，不管引號；`gh api` 的寫入 regex 又用 `[^;&|]*` 當 lookahead，碰到 URL 裡的 `&` 就停，後面的 `-X PUT` 看不到。
  4. push 規則只看遠端（上游 slug）與 force，不看目標分支。
- **做法**（`plugin/hooks/guard.py`）：
  1. bash 切段改成認得引號（`segments()`）：引號內的 `&`、`;` 不切，`2>&1` 不切；段落切好之後 lookahead 看整段。
  2. 合併、核准、直接 REST 寫入各寫成一個判斷函式：`is_merge_cmd()`（gh pr merge，或任何 API 客戶端打 merge 端點；也對整條指令判斷，用變數拼 URL 也抓得到）、`is_approve_cmd()`（`--approve`、`-a`、`-ab` 這類合併短旗標；reviews 端點用 `--input` 看不到內容時一律當核准）、`is_rest_write()`（curl／wget／httpie／Invoke-RestMethod／Invoke-WebRequest 對 GitHub API 的寫入）。有設定檔時主 session 也擋，agent 一律擋。
  3. 合併的例外只有一個掛點 `merge_exception()`，目前一律回 False；之後開放給可信任的合併角色時只改這裡，核准與直接 REST 寫入不走例外。
  4. 有設定檔時，主 session push 到 `protected_branches`（預設 main、master）也擋：解析 refspec 的目標（`HEAD:main`、`x:refs/heads/master`；沒寫 refspec 時用 `@{push}` 或目前分支；`--all`、`--mirror`）。
  5. hook 只是第一道減速帶：`python -c` 用 requests、或把 token 交給別的程式，都不經過 shell 字串比對。真正的邊界在 GitHub 端（ruleset 禁止直接 push 預設分支、合併權只給 gate）。

## 19. 政策核准只看 agent 自己交的 status；workflow 默默丟掉失敗的 agent

- **症狀**：verifier 回報有 fail 的驗收條件，但信封 status 是 done，`save_run.py approve --by policy` 照樣通過；sdlc-build 有子任務 agent 失敗（回傳 null）時被 `.filter(Boolean)` 丟掉，save_run 只依信封算狀態，build 段被記成 done。
- **原因**：閘門狀態只由信封的 status 決定，不讀 payload；workflow 的回傳沒有標示中斷，save_run 也不看回傳物件本身的欄位。
- **做法**：
  1. `save_run.py` 的 `policy_violations(stage, result)` 讀 `<stage>.json` 的實際內容：test 段的 criteria 任何一條不是 pass、anti_cheat 非空、任何 blocking 待決問題、blocker／important 發現、回傳標了 halted，都不能政策核准。人工核准不受影響（人可以看過 fail 之後決定）。
  2. `sdlc-build.js` 不再丟掉 null：子任務或 integrator 沒交 done 就記進 `failures`，回傳 `halted: true` 與 `halt_reason`，不進下一層。`save_run.py stage` 讀到 halted 就把該段記成 blocked。

## 20. 開放 agent 合併後，只比對角色名、只信本機紀錄都不夠

- **症狀**：hook 只比對去掉命名空間的角色名時，專案 `.claude/agents/` 放一個同名的 `dev-merge-steward` 就能合併；gate 判 merge 之後 PR 又被推了新 commit，合併的卻是沒審過的 head；CI 跑 PR 自帶的 gate，PR 改一行 gate 就能放行自己。
- **原因**：client 端的身分與紀錄都能偽造或過期；gate 的程式與設定如果來自 PR，就等於讓被審查的人寫審查標準。
- **做法**：
  1. `merger_role` 比對 hook 輸入的完整 `agent_type`（含命名空間）；沒有命名空間或其他 plugin 的同名 agent 一律擋。
  2. 合併指令必須帶 `--match-head-commit <sha>`，而且 `merge-audit.jsonl` 裡同 repo、PR、head_sha 的最後一筆是 merge；gate 紀錄、守門設定與凍結檔 agent 一律不能寫（Edit／Write 與 Bash 重新導向都擋）。
  3. 目標專案的 CI（`agent-merge-gate.yml`）用 `pull_request_target` 從受保護的 base checkout gate 與設定，PR 只當資料；結果用 gate App 寫 check run，ruleset 綁定這個來源。hook 只是輔助，見 `docs/自動合併信任模型.md`。
  4. 無人值守的推送改走確定性工具 `publish.py`（主 session 呼叫；agent 執行它被 hook 擋），推送前掃機敏值、依 run.json 閘門判定。

## 21. Windows 上 build.py 寫出 CRLF，workflow 解析失敗

**現象**：三平台 CI 只有 windows-latest 失敗，`check_workflows.mjs` 回報「找不到 export const meta」，煙霧測試的 sdlc-build phases 是空的。

**原因**：`Path.write_text` 在 Windows 上會把 `\n` 轉成 `\r\n`。build.py 內嵌 profile 後重寫 workflow，`check_workflows.mjs` 的 meta 正規式只認 `\n}\n`。

**做法**：會被其他工具解析的產出一律用 `open(..., newline="")` 寫；讀檔的一方也把 `\r\n` 正規化成 `\n`。新增會寫檔的工具時，要在 Windows CI 跑過才算數。

## 22. steward 不能對自己開的 PR request changes

**現象**：端到端演練中，steward 退回 PR 時 `gh pr review --request-changes` 失敗：「Can not request changes on your own pull request」。

**原因**：開 PR（publish.py）與退回 PR（steward）用的是同一個 GitHub 身分。

**做法**：merger App 的身分要和開 PR 的身分分開。分不開時，退回只能用「留言列出新需求＋`gh pr ready --undo` 轉 draft」，dev-merge-steward 的執行模式已經這樣兜底。

## 23. 角色前綴撞名：使用者自己的 dev-helper 被當成模版角色

**現象**：套用模版到既有專案後，使用者自己的 `.claude/agents/dev-helper.md` 突然不能 push、只能寫 repos_dir 和 run 目錄、交件被要求附 JSON 信封；`tpm-notes` 也一樣。

**原因**：hook 判斷模版角色時先去掉命名空間，再只比對前綴 `dev-`／`tpm-`。plugin 的 agent 一定帶 `agent-workflow:`，使用者放在專案的 agent 沒有命名空間，但去掉命名空間後兩者長得一樣。

**做法**：模版角色要同時符合「命名空間在 `team_agent_namespaces`（預設 `["agent-workflow:"]`）」與「角色名以 `team_agent_prefixes` 開頭」（`awf_config.is_team_agent`，傳完整 agent_type）。guard-shell、guard-paths、交件信封、role_map、merger_role、freeze_writers 全部走這個判斷。角色名和 plugin 模版角色完全相同的（`RESERVED_ROLES`）不論命名空間一律當模版角色（fail-closed），避免冒用模版角色名拿到較寬的規則。要回到舊行為就在清單加空字串。新增判斷角色的程式時，傳 hook 輸入的完整 `agent_type`，不要先 `role_name()` 再比對。
