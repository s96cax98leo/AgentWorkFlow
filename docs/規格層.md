# 規格層（`awf spec`）

規格層讓模版認得專案裡的規格目錄：它讀現行規格與進行中的變更，給每個需求與情境一個不會變的 id，檢查變更的差異寫得對不對，並在變更完成後把差異併回現行規格。

它只做這四件事。怎麼寫規格、什麼時候開變更，仍然由你的開發規範決定。

## 和 OpenSpec 的關係

很多專案已經用 [OpenSpec](https://github.com/Fission-AI/OpenSpec) 的目錄格式放規格。規格層讀同一種目錄與 Markdown 格式，所以這些專案不用搬資料。

- 規格層是自己實作的，不安裝、不呼叫 OpenSpec 的套件，也沒有用它的程式碼。
- 你可以繼續用 OpenSpec 的指令。兩邊讀寫的是同一批檔案。
- 規格層多做的事是穩定 id（`ids.json`）；這個檔 OpenSpec 不會讀，也不受它影響。

### 目錄

```
openspec/
├── specs/
│   └── <能力>/spec.md          現行規格
├── changes/
│   ├── <變更名>/
│   │   ├── proposal.md         為什麼改、改什麼
│   │   ├── tasks.md            工作清單（- [ ]／- [x]）
│   │   ├── design.md           選用
│   │   └── specs/<能力>/spec.md  這個變更對該能力的差異
│   └── archive/<日期>-<變更名>/  已完成的變更
└── ids.json                    穩定 id 的登記（規格層寫的）
```

根目錄預設是目前目錄的 `openspec/`。用 `--root <目錄>` 可以換位置，也可以給另一個 repo 的絕對路徑。相對路徑不能有 `..`。

### 現行規格的格式

```markdown
# orders Specification

## Purpose
示範客戶 ACME 的訂單。

## Requirements

### Requirement: 建立訂單
系統 SHALL 讓會員建立訂單。

#### Scenario: 庫存足夠
- **WHEN** 會員送出訂單
- **THEN** 訂單成立
```

`### Requirement: <標題>` 是一個需求，其下的 `#### Scenario: <標題>` 是它的情境。

### 差異檔的格式

```markdown
## ADDED Requirements

### Requirement: 申請退款
系統 SHALL 讓會員在七天內申請退款。

#### Scenario: 七天內
- **WHEN** 收貨未滿七天
- **THEN** 受理退款

## MODIFIED Requirements

### Requirement: 建立訂單
（整個需求的新內容，包含全部情境）

## REMOVED Requirements

### Requirement: 傳真下單
**Reason**: 已經沒有人用傳真。

## RENAMED Requirements

- FROM: `### Requirement: 取消訂單`
- TO: `### Requirement: 撤回訂單`
```

- MODIFIED 是整塊取代，所以要寫完整的需求，不是只寫改的那幾行。
- 同一個需求不能出現在兩種區塊。唯一的例外：需求改名又改內容時，RENAMED 寫改名，MODIFIED 用**新名字**寫新內容。
- 建新能力時，差異檔可以多寫一節 `## Purpose`，apply 會把它放進新檔。

### 解析時的容忍範圍

- 換行可以是 LF 或 CRLF；apply 寫回時照原檔的換行。
- 標題前後的空白、結尾的 `#`、全形冒號（`：`）都接受。
- 圍欄程式碼區塊（三個反引號或 `~~~`）裡的 `###` 不算標題。圍欄沒有關閉時 validate 會報錯，因為後面的需求全部會被當成程式碼。
- 同一個能力裡有兩個同名需求時報錯，不會默默只取其中一個。
- 空檔是合法的（零個需求）。

規格檔的內容是資料。規格層只讀它的結構，不會把裡面的文字當成指令；輸出裡引用規格的地方只給標題與行號。

## 子指令

每個子指令都接受 `--root <目錄>` 與 `--id-pattern <正規式>`。

### `awf spec status [--json]`

列出每個能力的需求數與情境數、進行中的變更（tasks 的勾選比例、會動到哪些需求 id）、已歸檔的變更數、待確認的 id。

```
規格根目錄：openspec
能力（2）
  login　需求 1、情境 1　openspec/specs/login/spec.md
  orders　需求 3、情境 4　openspec/specs/orders/spec.md
進行中的變更（1）
  add-refund　tasks 1/3（33%）
    RENAMED　orders/取消訂單　「撤回訂單」
    ADDED　orders/申請退款　「申請退款」
已歸檔的變更：0
待確認的 id（0）
```

### `awf spec validate [--change <名>] [--json]`

檢查規格與變更。每個問題一行 `路徑:行號：說明`；有問題時 exit code 是 1。

| 檢查 | 範圍 |
|---|---|
| 同一個能力裡需求不重名；同一個需求裡情境不重名 | 現行規格、差異檔 |
| 每個需求至少一個情境 | 現行規格、差異檔的 ADDED 與 MODIFIED（REMOVED 不用） |
| 圍欄程式碼區塊有關閉；檔案是 UTF-8 | 全部 |
| 現行規格裡沒有 `## ADDED Requirements` 之類的差異區塊 | 現行規格 |
| MODIFIED、REMOVED、RENAMED 的 FROM 指到的需求在現行規格存在 | 差異檔 |
| ADDED 的需求、RENAMED 的 TO 在現行規格還不存在 | 差異檔 |
| 同一個需求沒有同時出現在兩種區塊 | 差異檔 |
| RENAMED 的 FROM 與 TO 成對 | 差異檔 |
| 需求都放在某個差異區塊裡；差異檔不是空的 | 差異檔 |
| 變更有 `proposal.md` 與 `tasks.md` | 變更 |

不給 `--change` 時檢查現行規格與全部進行中的變更。給了就只檢查那個變更，加上它動到的能力的現行規格。已歸檔的變更是歷史，不檢查。

### `awf spec show <id>`

印出需求或情境的位置與標題，不印內文。給 agent 定位用：先拿到行段，再只讀那幾行。

```
openspec/specs/orders/spec.md:8-17　需求：建立訂單
```

### `awf spec ids [--write] [--adopt <舊id>=<新標題>] [--retire <id>] [--json]`

顯示照現在的規格，`ids.json` 會有什麼變動，以及哪些 id 待確認。預設只印、不寫；`--write` 才寫 `ids.json`。有待確認的 id 時 exit code 是 1。

### `awf spec apply --change <名> [--write] [--date <YYYY-MM-DD>]`

把變更的差異併回現行規格，再把變更目錄搬到 `changes/archive/<日期>-<名>/`。見下面〈apply 的安全做法〉。

### `awf spec --selftest`

在暫存目錄建一組虛構的規格與變更，把上面的行為走一遍。全部通過時 exit code 是 0。

## id 怎麼產生與確認

- 需求的 id：`<能力>/<需求代稱>`，例如 `orders/建立訂單`。
- 情境的 id：`<能力>/<需求代稱>#<情境代稱>`，例如 `orders/建立訂單#庫存足夠`。

### 第一次：由標題產生

規格層把標題轉成代稱：全形轉半形、轉小寫，字母、數字、中日韓文字保留，其他字元（空白、標點）換成 `-`，去掉頭尾的 `-`。

| 標題 | 代稱 |
|---|---|
| `Cancel an Order!` | `cancel-an-order` |
| `建立訂單（含贈品）` | `建立訂單-含贈品` |
| `???`（轉完是空的） | `req-<第幾個需求>`；情境用 `scn-<第幾個情境>` |

同一個能力裡撞名時，後面的加 `-2`、`-3`。

專案已經有自己的編號時，用 `--id-pattern` 給樣式，標題符合就用編號當代稱。樣式有第 1 組時用第 1 組，否則用整段符合的文字。例如 `--id-pattern '^(REQ-\d+)'` 會讓 `REQ-12: 建立訂單` 的 id 變成 `orders/req-12`。預設不啟用。

### 之後：記在 `ids.json`

`awf spec ids --write` 把 id 與標題的對應寫進 `<root>/ids.json`：

```json
{
  "requirements": {
    "orders/建立訂單": {
      "scenarios": {
        "庫存足夠": "庫存足夠"
      },
      "title": "建立訂單"
    }
  },
  "version": 1
}
```

只有這個指令會寫 `ids.json`。同樣的規格永遠產生逐位元相同的檔，所以可以放進版控。

登記之後，id 跟著登記走，不再跟著標題走。還沒登記的需求仍然有 id（照上面的規則由標題算出），只是標題一改 id 就會變，所以建議初次使用就跑一次 `--write`。

### 改標題

改標題有兩種情況，規格層的處理不同。

**用 RENAMED 區塊改名**：這是明確的改名。變更 apply 之後，舊 id 直接接到新標題，不用確認。下次 `ids --write` 會把登記的標題更新。

**直接改檔案裡的標題**：規格層看到的是「登記的標題不見了，同一個能力多了一個沒登記的標題」。它不會自己判斷這是不是同一個需求。新標題和舊的相像時，列成待確認：

```
待確認（1）
  orders/建立訂單　登記的標題「建立訂單」找不到了；可能改成了 「建立新訂單」（openspec/specs/orders/spec.md:8）
    是改名：awf spec ids --adopt 'orders/建立訂單=<新標題>' --write
    舊的不要了：awf spec ids --retire 'orders/建立訂單' --write
```

由人決定：

- 是同一個需求改了名：`awf spec ids --adopt 'orders/建立訂單=建立新訂單' --write`，id 不變。
- 舊需求真的不要了，新的是另一個需求：`awf spec ids --retire 'orders/建立訂單' --write`，新標題拿到新的 id。

在人確認之前，`ids --write` 不動這一組：舊的登記留著，新標題不登記。

「相像」的判斷用的是標題的字，以及兩邊情境標題的重疊（`ids.json` 只記標題，不記內文）。新舊完全不像時，規格層當成「刪了一個、加了一個」，不列待確認。情境改標題的處理方式相同，id 寫成 `<需求 id>#<情境代稱>`。

## apply 的安全做法

`apply` 會改現行規格，所以做得保守。

1. **先檢查**。它先跑 `validate --change <名>`，有任何問題就拒絕，不寫任何檔。
2. **預設只預覽**。不加 `--write` 時，它印出每個規格檔的 unified diff 與歸檔的搬移，磁碟上的檔一個位元都不動。看過差異再加 `--write`。
3. **全部算好再寫**。它先在記憶體裡算出每個檔的新內容，把新內容寫到旁邊的暫存檔（`spec.md.awf-new`），最後才依序換上，並把變更目錄搬進 `archive/`。
4. **失敗就還原**。任何一步失敗（例如沒有權限），它把已經換掉的檔換回來、刪掉暫存檔與新建的目錄，並報錯。規格目錄會和執行前一樣。
5. **不重做**。變更已經在 `archive/` 時，再 apply 一次會回報「已歸檔」並結束，不會再併一次。

併入的規則：

| 區塊 | 做法 |
|---|---|
| RENAMED | 把標題那一行換成新標題，內文不動 |
| REMOVED | 刪掉整個需求 |
| MODIFIED | 用差異檔裡的整塊取代同名的需求 |
| ADDED | 加在 `## Requirements` 那一節的結尾；沒有這一節就加在檔尾 |

順序固定是 RENAMED → REMOVED → MODIFIED → ADDED，和 OpenSpec 一致。

能力還不存在時，apply 會建 `specs/<能力>/spec.md`。檔頭照專案現有規格檔的樣子（有沒有 `# … Specification` 標題、`## Purpose`、`## Requirements`）；專案還沒有任何規格檔時用 OpenSpec 的標準檔頭。差異檔沒寫 `## Purpose` 時，新檔的 Purpose 會是一行「待補」，請記得補上。

歸檔目錄名的日期用 `--date`；沒給時用系統日期（UTC）。日期只影響目錄名。

apply 不寫 `ids.json`。併入之後跑 `awf spec ids --write`，把新需求登記進去。

### 守門

- apply 只寫 `<root>/specs/` 底下的 `spec.md`，以及搬動 `<root>/changes/` 底下的變更目錄。
- 變更名稱只能是 `changes/` 底下的一個目錄名：不能有路徑分隔、不能是 `..`、`archive`，不能用 `.` 開頭。
- 符號連結指到規格根目錄外面時，規格層不讀它（status 會在 stderr 列出略過了什麼），也不透過它寫入。
- 規格層不呼叫外部程式；差異是自己算的。

## 和 OpenSpec 不同的地方

- OpenSpec 的 validate 要求需求的說明文字含 `SHALL` 或 `MUST`。規格層不檢查這一點，因為規格可能用中文寫。
- OpenSpec 可以在變更的 `.openspec.yaml` 設 `retire_capabilities`，讓最後一個需求被移除時連規格檔一起刪。規格層不讀這個檔；需求全部移除後會留下沒有需求的 `spec.md`，要不要刪由你決定。
- 某個能力的現行規格本身有問題時（例如某個舊需求沒有情境），動到這個能力的變更不能 apply。先修好現行規格再併。
- 新能力的 Purpose 沒有來源時，OpenSpec 寫一行英文的 TBD，規格層寫一行中文的「待補」。

## 接到存檔與閘門

把 profile 的 `requirements.source` 設成 `openspec` 之後，`awf save-run` 與 `awf merge-gate` 會用規格層的穩定 id 當需求與驗收條件的 id：proposal 當 intent、design 與 test 存檔時核對 id 找不找得到、merge gate 從變更的差異檔取需求清單。plan、design 核准時會把變更的條目清單與差異檔雜湊記進 run.json，之後各段與 merge gate 都和它比（核准之後直接改差異檔會被當成問題；要修訂就重跑 design 段）。沒有設就完全不啟用。設定方式與檢查項目見 `docs/自訂與擴充.md`〈需求來源用規格層〉。
