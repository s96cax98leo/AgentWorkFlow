# 從 0.x 升級到 1.0

給已經套用 0.x 的專案用。照順序做，每一步後面都有「怎麼確認」。指令對照與破壞性變更的完整清單在 [`CHANGELOG.md`](../CHANGELOG.md) 的 1.0.0 一節。

## 先知道這幾件事

- **不再需要 Python。** 全部工具變成一個執行檔 `awf`，由 plugin 提供；專案裡的 `.claude/teams/tools/` 與 `.claude/hooks/` 的 `.py` 不再使用。
- **資料格式沒變。** run 目錄、`run.json`、稽核紀錄、決策記憶、交付設定都不用轉換，進行中的 run 升級後可以繼續。
- **目前 plugin 只附 macOS arm64 的執行檔。** 其他平台要自己建置並設 `AWF_BIN`，做法見 [`建置與發佈.md`](建置與發佈.md)。
- **閘門比 0.x 嚴。** 原本會過的東西可能不過，見最後一節。

## 步驟

### 1. 更新 plugin

在終端機執行：

```bash
claude plugin marketplace update agentworkflow
claude plugin update agent-workflow@agentworkflow
```

然後在 Claude Code 裡執行 `/reload-plugins`（或重開 Claude Code）。

確認：

```bash
awf --version
```

要印出 `awf 1.0.0`。印不出來時：

| 現象 | 原因 | 處理 |
|---|---|---|
| 找不到 `awf` | plugin 還沒重新載入 | `/reload-plugins`，不行就重開 Claude Code |
| 「找不到執行檔」 | 這個平台沒有附執行檔 | 自己建置並設 `AWF_BIN` |
| 版本還是舊的 | 只更新了 marketplace 清單 | 再跑一次 `claude plugin update agent-workflow@agentworkflow` |

### 2. 先看專案現在的狀態（不會改任何檔）

在專案根目錄：

```bash
git status
awf doctor
```

- 工作目錄有沒 commit 的改動時，先 commit 或 stash：下一步會改專案的檔案，乾淨的工作目錄才看得出改了什麼。
- `awf doctor` 會列出版本不一致（plugin 是 1.0、專案還是 0.x），這是預期的。

### 3. 升級專案

```bash
awf init --target . --upgrade
```

它會做的事：

- 模版檔換成 1.0 的版本（schema、內建 profile、rules 的通用規則、golden-set）。
- 移除 0.x 複製進來的工具：和任何一版原樣相同的移除；**你改過的保留並逐一列出**；你自己加的檔不動。
- 改寫 hook 註冊；`settings.json` 裡舊的 `python3 .claude/teams/tools/<工具>.py` 權限換成 `awf <子指令>`，你自己加的權限不動。
- `guard.config.json` 補上新增的鍵，你的值一律保留。

它**不會**動的：

- `.claude/teams/methodology.json`（只列出這版新增、你還沒有的欄位）。
- `rules.md` 的〈專案規則〉之後、`CLAUDE.md` 的〈專案特定〉之後。
- run 目錄。

依專案的情況加旗標：

| 情況 | 加什麼 |
|---|---|
| 想採用列出的新欄位（補進 `methodology.json`，只補缺的） | `--adopt-new-fields` |
| hook 註冊在專案的 `.claude/settings.json`（0.x 用 `--hooks project` 裝的，Windows 常見） | `--hooks project`（把註冊換成執行檔；不加的話舊的 Python 註冊會留著） |
| 有用 merge gate 的 CI | `--with-merge-gate`（重新產生 CI 檔與專案裡的執行檔） |

確認：

```bash
git status          # 看改了哪些檔
awf doctor          # 不該有 error
awf golden          # schema 的正例、反例
```

`awf init` 列出「改過所以保留」的舊工具檔時：那些檔 1.0 不會再呼叫。確認裡面沒有你還需要的改動後可以刪掉；有的話，把改動的需求改用設定檔表達（見 [`自訂與擴充.md`](自訂與擴充.md)）。

### 4. 改掉自己寫的舊指令

專案裡自己的腳本、CI、文件、`CLAUDE.md` 若有呼叫舊工具，照這張表改（參數與旗標不變）：

| 0.x | 1.0 |
|---|---|
| `python3 .claude/teams/tools/awf.py next` | `awf next` |
| `save_run.py <子指令>` | `awf save-run <子指令>` |
| `merge_gate.py`、`publish.py`、`sync_branch.py` | `awf merge-gate`、`awf publish`、`awf sync-branch` |
| `pack.py`、`kb.py`、`locate.py`、`recipe.py` | `awf pack`、`awf kb`、`awf locate`、`awf recipe` |
| `deliverables.py`、`checklist.py`、`check_agents.py` | `awf deliverables`、`awf checklist`、`awf check-agents` |
| `awf_cost.py`、`awf_watch.py`、`awf_doctor.py`、`awf_script.py` | `awf cost`、`awf watch`、`awf doctor`、`awf script` |
| `run_brief.py`、`check_envelope.py`、`check_rules.py`、`build.py` | `awf run-brief`、`awf check-envelope`、`awf check-rules`、`awf build` |
| `golden-set/run.py` | `awf golden` |
| `<工具>.py --selftest` | `awf <子指令> --selftest` |

找出還有哪些地方在用舊寫法：

```bash
git grep -n "teams/tools/\|\.py --selftest\|init\.py"
```

### 5. 進行中的 run

不用轉換。接著做就好：

```bash
awf next --run <run 目錄>
```

要留意的是閘門變嚴之後，原本已核准的段在重存或重新核准時可能被擋（見下一節）。被擋時訊息會寫明原因。

### 6. 要不要用 1.0 的新功能（都不是必要的）

沒有另外設定時，流程和 0.x 相同。要用時：

| 功能 | 怎麼開 | 說明 |
|---|---|---|
| 知識圖（從需求找程式、追溯、影響範圍） | 先手動跑一次 `awf kg build`；之後每段開跑前自動更新 | [`知識圖.md`](知識圖.md) |
| 需求來源用 OpenSpec | `awf init --target . --reconfigure requirements` | [`規格層.md`](規格層.md) |
| 連結帳本與連結檢查 | `awf init --target . --reconfigure links` | [`自訂與擴充.md`](自訂與擴充.md)〈連結〉 |
| 模型分級（不要全部用最貴的模型） | `awf init --target . --reconfigure models` | `awf doctor` 會在 `models.mode` 是 inherit 時警告，並列出改成 auto 後各等級用的模型 |
| 專案自己的去客戶化掃描、測試／lint CI | `--reconfigure scrub`、`--reconfigure ci` | 預設不啟用 |

## 比 0.x 嚴的地方

升級後遇到「以前會過、現在不過」，先對這張表：

| 現在的行為 | 以前 | 怎麼處理 |
|---|---|---|
| 閘門類指令找不到專案根就報錯（`--project-dir` → `CLAUDE_PROJECT_DIR` → 往上找最外層含 `.claude/teams/VERSION` 的目錄） | 用目前目錄 | 在專案裡執行，或帶 `--project-dir` |
| 交件有兩個 JSON 區塊時只看最後一個 | 最後一個讀不懂就退回前一個 | agent 的交件只留一個 JSON 區塊 |
| 欄位型別不對是錯誤（例如 `owns` 寫成字串） | 當成空的 | 改成正確的型別 |
| 重存一段時回傳讀不懂，該段標成 invalid、清掉核准 | 舊結果與舊核准留著 | 重跑那一段 |
| run 已鎖定 recipe 而專案沒有 `methodology.json`：存檔、核准、推送、合併都拒絕 | 當成沒有 profile 照過 | 把 `methodology.json` 放回來 |
| `guard.config.json` 讀不懂時，team agent 的寫入全擋 | 退回預設值 | 修好設定檔（主 session 仍然可以改它） |
| recipe 指到沒定義的 lens、審查軸、驗證模式時停下來 | 默默略過 | 改 recipe，或在 profile 補定義 |
| 需求來源是 OpenSpec 時，design 核准後規格條目變少或差異檔被改算問題 | 不檢查 | 要改規格就重跑 design 段 |
| team agent 被擋的寫法變多（指令替換裡的 `awf`、藏起來的 `bash -c`、帶寫入旗標的唯讀子指令等） | 部分放行 | 這些操作由主 session 做 |

hook 的行為有一項變了：hook 內部出錯時，team agent 一律擋；主 session 與你自己的 agent 只套最小規則（擋 push、合併、approve、GitHub API 寫入）。hook 跑不起來（找不到執行檔、逾時）仍然放行，不會鎖死。

## 出問題時

- 先跑 `awf doctor`：每一項都附修法。
- 要退回 0.x：`git checkout` 還原專案的改動，plugin 用 `/plugin` 介面換回舊版。run 目錄兩版通用。
- 守門擋了不該擋的：訊息裡有規則名稱；確認是誤擋後，由主 session 執行那個操作，並回報問題。
