# 自訂與擴充

怎麼依專案調整、怎麼加新的 agent、skill、hook、workflow，以及改語言、接 MCP。

先分清楚改的是哪一層：

| 要改的 | 位置 | 影響範圍 |
|---|---|---|
| agent、skill、command、hook | 本 repo 的 `plugin/` | 所有裝了 plugin 的專案（改完要更新 plugin） |
| 硬規則、schema、工具 | 目標專案的 `.claude/teams/` | 只有這個專案 |
| workflow 範本 | plugin 的 `workflow-templates/`；專案要改就用覆寫檔（`.claude/workflows/<名>.js`，見〈覆寫 workflow〉） | 範本：所有專案；覆寫檔：只有這個專案 |
| 守門設定 | 目標專案的 `.claude/teams/guard.config.json` | 只有這個專案 |
| 專案說明、MCP | 目標專案的 `CLAUDE.md`、`.mcp.json`（或 `.mcp.json.example`） | 只有這個專案 |

想讓所有專案都拿到的改動，改 `plugin/` 或 `plugin/scaffold/`；只對一個專案有意義的，改那個專案自己的檔案。

## 1. 專案規則

`awf init` 產生的 `.claude/teams/rules.md` 有一段「## 專案規則」，放這個專案專屬的規則：

- 目標 repo（`{{REPOS_DIR}}` 下哪幾個是可以開發的 clone）
- 禁區（`{{FORBIDDEN_REPOS}}`）
- 審查規則（目標 repo 自己的 `REVIEW.md`、分支規範）
- 設計系統 skill 名稱（`{{DESIGN_SYSTEM_NAME}}`）
- 本機驗證指令（integrator、verifier 用的 verify 指令）

通用規則（先 plan 後動手、不可逆停下、機敏檔、信封……）不要在專案裡刪；要放寬就在專案規則裡寫明例外與核准者。

## 2. 守門設定

設定讀專案的 `.claude/teams/guard.config.json`（`awf init` 從 `guard.config.json.tmpl` 產生）。hooks 有兩種裝法，**二選一，不要同時用**：

| 模式 | 怎麼裝 | hooks 由誰註冊 |
|---|---|---|
| plugin（預設） | 安裝 plugin，`awf init` 不加 `--hooks` | `plugin/hooks/hooks.json`；專案 `settings.json` 不放 hooks |
| project | `awf init --hooks project` | 由專案 `settings.json` 註冊（寫入執行檔的絕對路徑）；這時不要再啟用 plugin 的 hooks |

`guard.config.json` 的主要欄位（清單欄位可寫 JSON 陣列或逗號分隔字串，空字串表示不設定）：

| 欄位 | 意思 |
|---|---|
| `runs_dir`、`briefs_dir` | run 目錄、任務單目錄 |
| `repos_dir` | 我方 clone 所在；空字串表示工作區本身就是目標 repo |
| `upstream_repos` | 上游 repo，禁止任何寫入 |
| `fork_repo` | 我方 fork；gh 寫入動作要明確帶 `--repo` 指向它 |
| `forbidden_paths` | 任何角色都不能寫的路徑 |
| `allowed_branch_prefixes` | 允許的新分支前綴 |
| `writer_dirs` | `tpm-writer` 可以寫的目錄。init 寫成 run 目錄、簡報目錄加上佔位符 `DOCS_DIRS`（預設 `docs`）；訪談的守門主題或 `awf init --reconfigure guard` 可以改 |
| `protected_branches` | 受保護分支：agent 與主 session 都不能直接 push，合併走 PR。init 取自佔位符 `PROTECTED_BRANCHES`（預設 `main,master`；留空也是這兩個），訪談的守門主題可以改、不能清空 |
| `base_branch`、`base_remote` | 主線分支（只寫分支名）與它所在的 remote，預設 `main`、`origin`；init 取自佔位符 `BASE_BRANCH`、`BASE_REMOTE`，訪談的守門主題問主線分支（`awf init --detect` 從遠端 `origin` 的預設分支看）。沒帶 `base` 時，各段 workflow 的比對基準是 `<base_remote>/<base_branch>`（範本的佔位符在 `awf next` 產生腳本時取這裡的值，不看 `workflow.config`），`awf sync-branch`、`awf recipe check-diff`、`awf deliverables affected` 的 `--base` 預設也是它，`awf publish` 開 PR 的目標分支（`--base`）預設是 `base_branch`；命令列旗標與 `--set base=…` 仍然優先。只收單純的名字（分支：英數與 `._/-`；remote：英數與 `._-`），沒寫或不合規則就用預設值（`awf doctor` 會列出來）。**它和 `protected_branches` 是兩件事**：設成主線分支不會讓它受保護，`awf doctor` 在主線分支不在 `protected_branches` 裡時提示一次。放在守門設定而不是 profile，是因為 hook 與工具都讀這一份、team agent 改不到 |
| `specs_dir`、`worktrees_dir`、`spec_templates_dir` | 目標 repo 裡的 spec 目錄、worktree 目錄、文件範本目錄，預設 `specs`、`.worktrees`、`<specs_dir>/_templates`；init 取自佔位符 `SPECS_DIR`、`WORKTREES_DIR`、`SPEC_TEMPLATES_DIR`，訪談的守門主題問 spec 目錄（`awf init --detect`：沒有 `specs/` 而有 `docs/specs/`、`doc/specs/`、`spec/` 時建議照既有的）。都是相對於目標 repo 的路徑：spec 目錄與範本目錄最多 4 層，worktree 目錄只能是一層的目錄名；只收英數與 `._-`，不能是絕對路徑、含 `..`，也不能在 `.claude`、`.github`、`.git` 底下。沒寫或不合規則一律用預設值（`awf doctor` 會列出不合規則的值）。讀它的地方：各段 workflow 的派工單（epic worktree 是 `<repo>/<worktrees_dir>/<epic>`、spec 在裡面的 `<specs_dir>/<epic>/`；佔位符在 `awf next` 產生腳本時取這裡的值）、`awf pack` 與 `awf save-run` 找 spec 目錄、`awf kb`（來源有 `specs/**/*.md` 時新目錄也算來源；排除了 `**/.worktrees/**` 時新的 worktree 目錄也排除）、`awf locate` 的文件角度、`awf deliverables` 型錄裡 `specs/**` 的來源、走訪 repo 時略過的 worktree 目錄名，以及 hook：tpm-writer 能寫的 spec 文件是 `(<worktrees_dir>/<名>/)?<specs_dir>/<epic>/*.md`，改了名就只認新目錄（不是兩個都認，放行範圍不會變大）。已經在跑的需求不會搬：改之前先把既有的 `specs/` 搬到新位置。profile 裡自己寫的路徑（`knowledge.sources`、`conventions.doc_format.notes`、限制文件的 `paths`）不會跟著改 |
| `task_id_prefix`、`task_authority` | 任務編號前綴與發編號的系統，用來檢查「不自編編號」 |
| `attribution_line` | commit 結尾署名行 |
| `main_session_git_rules` | 為 true（預設）時，分支前綴、不 force push、不 `--no-verify`、不直接 push 受保護分支也套用到主 session |
| `main_session_github_rules` | 為 true（預設）時，主 session 也不能 `gh pr merge`、核准、用 REST 合併或核准，`gh` 寫入要帶 `--repo`；設 false 放行。`auto_merge` 啟用時主 session 仍不能合併、核准，上游一律擋（見〈套用到既有專案〉） |
| `team_agent_namespaces` | 哪些命名空間的 `dev-*`／`tpm-*` 算模版角色，預設 `["agent-workflow:"]`；加 `""` 讓沒有命名空間的同名 agent 也算（舊行為） |
| `acceptance_test_dirs` | 驗收測試目錄（預設 `tests/acceptance`、`e2e`，工作區或 repo 內任一層的相對路徑）；dev-implementer 不能寫，驗收測試由 dev-acceptance-tester 寫 |
| `linked_repos` | 工作區以外、也算我方 clone 的 repo 目錄（絕對路徑、`~` 開頭，或相對於工作區）。登記後 dev-* 可以改裡面的檔、tpm-writer 可以寫它的 `specs/<epic>/*.md`；禁止路徑、`.claude/`、驗收測試目錄、唯讀審查角色只能寫報告這些規則照舊。預設空（只認工作區）。不要填上游或別的客戶的目錄；檔案系統根目錄與家目錄本身不會被採用 |
| `auto_merge` | 自動合併，預設關閉。各鍵（白名單、`merger_role`、`daily_cap`、風險門檻、`carry_verdict_on_rebase`、`allowed_skipped_checks`、`required_checks` 等）見 `docs/自動合併信任模型.md` 第 5 節 |
| `extension_agents` | 使用者加進 workflow 的自己的 agent：`{"完整 agent_type": "套用哪個模版角色的規則"}`，只能對應唯讀類角色，其他值改套 `tpm-reviewer`（見〈把自己的 agent 加進 workflow〉） |
| `role_map`（內建預設，可覆寫） | agent 名稱對應到目標 repo 自己 guard 的角色名 |

`guard-paths` 也擋 Read、Grep 讀機敏檔（`.env`、金鑰、憑證；`.env.example` 這類範例檔放行），主 session 也擋。權限層的 deny 規則（例如預設擋 `Read(**/*.key)` 這類機敏檔）在 `.claude/settings.json`；專案真的需要放寬時，見 `plugin/scaffold/.claude/settings.README.md` 的「如何放寬讀取限制」：優先在 `settings.local.json` 只放行單一檔案；`.env` 和 `*.pem` 不放寬。

沒有設定檔時只套用角色規則（`agent-workflow:` 命名空間下的 `tpm-*`／`dev-*` 不推送、不做 gh 寫入、只寫自己的範圍），不擋主 session 與使用者自己的 agent，所以 plugin 在還沒 init 的專案也不會誤擋。兩種模式同時開會讓每個 hook 跑兩次。

hook 跑不起來（找不到執行檔、逾時）時 plugin 模式放行，project 模式可以設成擋；完整的失敗語意與取捨見 [`自動合併信任模型.md`](自動合併信任模型.md)〈hook 失敗時的取捨〉。

## 3. 改輸出語言

1. 在 `workflow.config` 改 `OUTPUT_LANGUAGE`，重跑 `awf init`；或直接改專案 `rules.md` 的語言規則與 `CLAUDE.md`。
2. 語言規則要涵蓋：給決策者的回覆、派工單、agent 之間的訊息與 SendMessage、信封的 summary／open_questions／derived_work、文件、commit 內文、推播。程式識別字、指令、路徑、技術名詞保留原文。
3. 派工單本身要用新的輸出語言寫，subagent 的回覆才會跟著改。
4. 建議也寫進記憶，讓下一個 session 一開始就知道。

plugin 裡 agent 的提示是繁體中文，改輸出語言不需要改它們；提示裡已經寫「檔案、信封、訊息一律用 `.claude/teams/rules.md` 設定的輸出語言」。

## 4. 新增 agent

1. 在 `plugin/agents/` 加 `<前綴>-<角色>.md`。前綴決定守門規則：plugin 命名空間下的 `dev-*`、`tpm-*` 會套用角色寫入範圍與「不推送」規則（見 `guard.config.json` 的 `team_agent_prefixes`、`team_agent_namespaces`）。使用者放在專案 `.claude/agents/` 的 agent 沒有命名空間，不套這些規則（名字和模版角色完全相同的除外）。新增模版角色時，把名字同時加進 `crates/awf-core/src/config.rs` 的 `RESERVED_ROLES` 與 `crates/awf-core/src/check_agents.rs` 的 `CORE`（`awf check-agents` 會核對兩邊），並更新 README 等文件的角色數與名單（`cargo xtask check-docs` 會核對）。
2. frontmatter 至少要有 `name`、`description`（寫清楚什麼時候派給它）、`tools`。**只讀的角色不給 Edit、Write**。
3. 本文照既有 agent 的段落：切分理由、職責、硬性約束、工作方式、交件（最後附信封與 payload 名）。
4. 要套用目標 repo 的 guard，就在 `role_map` 加對應。
5. 跑 `awf check-agents --plugin-dir <AgentWorkFlow>/plugin` 檢查格式（agent 放專案 `.claude/agents/` 時改用 `--agents-dir`）。`awf check-agents` 檢查 16 個 team 角色（`tpm-*`／`dev-*`）：五段內文、`model: inherit`、`skills` 欄位、payload schema 這些規定只對它們成立，因為它們由 workflow 派出、要交 JSON 信封、hooks 也只把它們當 team 角色。site-report 那 6 個不交信封、不受角色寫入範圍限制，不在這支工具的範圍內；要檢查它們的 frontmatter 基本格式，另寫一支小檢查放 `tests/`，不要塞進 `awf check-agents`。
6. workflow 和 Agent 工具呼叫 plugin 的 agent 時要帶命名空間：`{{AGENT_NS}}<agent 名>`，預設 `agent-workflow:`。agent 放在專案 `.claude/agents/` 時，`AGENT_NS` 設成空字串。

### 把自己的 agent 加進 workflow（使用者用）

上面是改模版本身（所有專案都拿到）。只想讓**某個專案**的 SDLC 多一個自己的 agent（例如 migration 審查、無障礙檢查、團隊內部規範檢查、領域調研）時，不用改模版，在 Claude Code 裡跑 `/agent-workflow:add-agent`（`add-agent` skill），它會一步步問完並幫你設定。手動設定的話分三步：

1. **寫進 profile**：`.claude/teams/methodology.json` 的 `extensions` 加一筆。
   ```json
   {"name": "db-migration", "agent": "acme-db-reviewer", "stage": "test",
    "instructions": "檢查示範客戶 ACME 的 migration 能不能回滾；不能回滾列 important。"}
   ```
   - `agent`：專案 `.claude/agents/<名>.md` 的寫 `<名>`；其他 plugin 的寫 `<plugin>:<agent>`。
   - `stage`：只有四段可以加。

     | stage | 和誰平行 |
     |---|---|
     | `plan` | 調研 |
     | `design` | 一致性檢查 |
     | `test` | 驗證與設計、安全審查 |
     | `deliver` | 四軸 PR 審查，之後一樣經 skeptic 反駁 |

   - build 與 merge 不開放：build 有檔案所有權與 worktree 分工；merge 是信任邊界，只有 `dev-merge-steward` 加確定性 gate。
2. **登記守門角色**：`.claude/teams/guard.config.json` 的 `extension_agents` 加 `"acme-db-reviewer": "tpm-reviewer"`。
   - 登記後，這個 agent 的推送、GitHub 寫入、寫入範圍都照對應角色擋，交件信封也會驗證。
   - 只能對應唯讀類角色：`tpm-researcher`、`tpm-reviewer`、`tpm-skeptic`、`dev-verifier`、`dev-security-reviewer`、`dev-design-reviewer`。舊名 `dev-pr-reviewer` 已併入 `tpm-reviewer`，仍可填（相容一版），照 `tpm-reviewer` 套用。對應到其他角色（例如 merge-steward、implementer）一律改套 `tpm-reviewer`。
   - 沒登記的話，`awf` 會拒絕產生腳本（有覆寫檔時 `awf build` 也拒絕內嵌）：沒登記的 agent 不套任何角色規則，和主 session 一樣能 push。
3. **確認**：不用另外內嵌，下一段開跑時 `awf next` 就會帶上（有覆寫檔才要跑 `awf build`）。用 `awf render --all --out _tpm/wf-check` 加 `check_workflows.mjs --wf-dir _tpm/wf-check` 確認擴充 agent 會被派出，而且定義檔存在。

擴充 agent 一律交 `findings`，詳細結果寫在 `<run_dir>/ext-<name>.md`。它的 blocker／important 發現會擋住政策核准，要人決定。

## 5. 新增 skill

1. 在 `plugin/skills/<名稱>/SKILL.md`。`description` 要寫觸發情境（使用者會怎麼說）。
2. 細節放 `references/`，可重跑的腳本放 `scripts/`，SKILL.md 只放流程與指向。
3. 專案專屬的 skill（例如綁定某個 repo 的工作流程）放目標專案的 `.claude/skills/`，不要放進 plugin。

### 設計系統 skill

`plugin/skills/design-system-template/` 是骨架。為專案做一份：

1. 複製到目標專案 `.claude/skills/<設計系統名>/`。
2. 填 token（顏色、字級、間距、圓角、陰影）、元件規則、狀態色、RWD 斷點、無障礙要求、交付檢查表。
3. 在專案規則寫上設計系統 skill 名稱，讓 `dev-design-reviewer` 與 implementer 載入。

## 6. 新增 workflow（新的事件種類）

形狀是「幾個角度平行找 → skeptic 反駁 → writer 寫文件」的事件**不用寫 workflow**：在 `methodology.json` 的 `events` 加一筆就好，見 [`事件處理.md`](事件處理.md) 的〈自訂事件類型〉。下面的步驟是形狀不同（例如要先拆工、要逐條驗收）時才需要。

1. 在專案的 `.claude/workflows/` 複製一支 plugin 的 `workflow-templates/event-*.js` 當骨架：拆工或固定角度 → 平行 → skeptic → writer。
2. `meta` 寫 `name`、`description`、`whenToUse`（含必要 args）、`phases`。
3. 檢查必要 args，缺了就 `throw`；派工單 context 要帶 run 目錄、硬規則、授權來源。
4. 每個 `agent()` 都帶 `agentType`（寫成 `NS + '<agent 名>'`，`NS` 來自 `'{{AGENT_NS}}'`）與 `schema`。schema 用 `/*@schema:<payload>*/ null /*@end*/` 標記，不要手寫。
5. 跑：
   ```bash
   awf build          # 把 schema 內嵌進 workflow
   node <plugin>/workflow-templates/check_workflows.mjs --project . --wf-dir .claude/workflows  # 乾跑（<plugin> 是 plugin 目錄）
   ```
6. 乾跑走不到的分支（halted、缺件、子計劃等）要靠情境檔：情境跟著乾跑腳本放在模版的 `plugin/workflow-templates/scenarios/<workflow>.mjs`（`export default` 陣列，`check_workflows.mjs` 自動載入）。只放在專案裡的 workflow 沒有情境檔，只會跑預設路徑；要補情境就照第 8 步把 workflow 放進模版 repo。
7. 在 `tpm-team` skill 的事件對照表加一列；需要 slash command 就在 `plugin/commands/` 加一支（不要和 skill 同名）。
8. 想讓所有專案都有，把 workflow 放進本 repo 的 `plugin/workflow-templates/`，並加進 `crates/awf/tests/smoke_init.rs` 的清單與狀態機（`crates/awf-core/src/state/mod.rs`）的 `FIXED_EVENTS`、`REQUIRED`（狀態機才認得這個事件）。

注意：workflow 腳本裡不能取時間、跑到一半不能等人輸入。日期由主 session 放進 `run_dir`；需要人決定的點，就把 workflow 拆成兩支。

**共用片段**：workflow 不能 import 檔案，多支 workflow 共用的程式放在 `plugin/workflow-templates/snippets/<名>.js`，在 workflow 裡寫標記：

```js
/*@snippet:challenge*/
/*@end*/
```

跑 `awf build` 時，片段內容會內嵌在標記之間（標記保留，可重跑）；`awf build --check` 會偵測片段和 workflow 內嵌內容的漂移。內建片段：

| 片段 | 用途 |
|---|---|
| `challenge` | `tryAgent`（`agent()` 一律走它，throw 當缺件）；把 skeptic 的 verdicts 對回事項，分出保留與被推翻（預設模式同一事項任一則 refuted 就存疑）；缺件時組 halted 回傳 |
| `review-skeptic` | 審查 agent 交 findings 後派 skeptic 逐則反駁（`@requires: challenge`） |
| `layers` | 依 `depends_on` 把子任務拓撲分層，回報循環與指向不存在的相依 |

寫片段的規則：

- 只定義函式，不能有頂層 `await`，不能用 `{{佔位符}}`，也不讀 workflow 的區域變數；需要的值一律用參數傳進去。
- 片段之間有依賴時，在片段開頭寫 `// @requires: <名>`；引用它的 workflow 也要引用被依賴的片段。
- 違反以上規則時 `awf build` exit 1。改了片段要重跑 `awf build`，並確認 `plugin/workflow-templates/scenarios/*.mjs` 用到的 agent label 沒變。

## 7. 新增 payload

1. 在 `.claude/teams/schemas/payloads/<名稱>.schema.json` 定義。
2. 在 `golden-set/valid/`、`golden-set/invalid/` 各補至少一個例子。
3. 跑：
   ```bash
   awf build --check
   awf golden              # 專案的 golden-set：正例要零錯誤、反例要有錯誤（模版 repo 用 cargo xtask golden）
   ```
4. 有 schema 表達不了的規則，加在驗證器（`crates/awf-core/src/schema.rs`）的語意檢查，並補反例。

## 8. 新增 hook

1. 規則寫在 `crates/awf-core/src/hooks/`（`awf hook <種類>` 的實作）；新的事件或 matcher 在 `plugin/hooks/hooks.json` 註冊（指令用 `${CLAUDE_PLUGIN_ROOT}` 的 `bin/awf`）。
2. 設定值從 `guard.config.json` 讀（共用 `crates/awf-core/src/config.rs`），不要寫死專案路徑。
3. 擋下時輸出清楚的理由（用輸出語言），告訴 agent 該怎麼做才合規。
4. 在 `tests/hooks/cases.jsonl` 補案例：一個該擋的、一個該放的，Bash 與 PowerShell 各一（格式見 `tests/hooks/README.md`）。hook 失敗時的語意（跑不起來放行、輸入壞掉擋、設定載入失敗用內建最小規則）由 `awf hook` 的入口（`crates/awf-core/src/hooks/mod.rs`）統一處理，新規則寫在 `crates/awf-core/src/hooks/` 的守門規則就會套用。跑 `cargo test -p awf --test hooks_cases`（每一組案例在自己的暫存目錄重建環境）。

## 9. 接 MCP

1. `awf init` 預設從 `plugin/scaffold/.mcp.json.tmpl` 產生 `.mcp.json.example`；加 `--with-mcp` 才產生正式的 `.mcp.json`。
2. 加 server 時，金鑰一律用環境變數引用（`${VAR}`），不要寫進檔案。
3. 給 agent 用的 MCP 工具，要在 agent 的 `tools` 列出；只讀的角色只給讀取類工具。
4. 會改變外部狀態的 MCP 工具（寄信、建立工單、改設定）算不可逆動作，要決策者當下同意，最好只在主 session 用。
5. 可選的 LLM 或 runtime（本機模型、其他雲端模型）也可以透過 MCP 或環境設定接上，但不要把特定客戶的部署細節寫進模版。

## 10. 改 slash command

`plugin/commands/*.md` 是 slash command，只有 4 支：`/sdlc`、`/brief`、`/event`、`/demo-check`。`init-workflow`、`add-agent`、`correct` 是 skill（`plugin/skills/<名>/`），用 `/agent-workflow:init-workflow` 這類完整名稱叫用；依 [Claude Code 文件](https://code.claude.com/docs/en/skills)，plugin skill 的指令名是 `/<plugin>:<skill>`，沒有其他指令同名時也可以省略前綴。不要新增和 skill 同名的 command，兩者會搶同一個名字。command 只負責把使用者的話整理成 `tpm-team` skill 的輸入，流程本身留在 skill 與 workflow 裡，避免兩邊不一致。

## 11. 自訂開發規範

模版只管工作流程（plan → design → build → sync → test → deliver → merge 與各閘門）。開發規範（TDD、DDD、SDD、spec 驅動…）與慣例（code style、commit 格式、分支命名、PR 大小、文件格式）由套用的團隊決定，寫在目標專案的開發規範 profile：`.claude/teams/methodology.json`。workflow、agent、rules.md 都只引用它；模版原本的做法收在 default profile，當成預設值與範例。

| `test_modes`（選填） | 驗證模式的說明：`{"<名稱>": {"note": "<寫進驗證派工單的說明>"}}`；同名的換掉內建說明，新名稱讓 recipe 的 `test.modes` 選用。`verify` 不能定義 | sdlc-test |
| `research_angles`（選填） | 調研角度的定義：`{"<名稱>": {"ask", "modes", "locate"}}`。`ask` 是問法；`modes`（`{plan_mode: 問法}`）逐個 plan_mode 蓋過；`locate`（布林）是要不要先派定位（內建角度沒寫照內建，自訂角度預設 true） | sdlc-plan |
| `plan_modes.<mode>.refute`（選填） | 這個 plan_mode 的 intent 由 skeptic 反駁時的重點（1–2000 字）；沒寫照內建。每份 intent 都要檢查的共同項目拿不掉 | sdlc-plan |
| `roles`（選填） | 把某一步換成自己的 agent：`{"<段>.<步驟>": "<agent_type>"}`。只開放七個唯讀步驟，見下面〈名稱表與換角色〉 | sdlc-plan、sdlc-design、sdlc-design-revise、sdlc-deliver、awf next、awf build |
| `briefs`（選填） | 簡報的格式假設：`language_section`（語言寫在哪一節，預設 `§1`）、`outputs_section`（產出路徑，預設 `§3`）、`acceptance_section`（驗收標準，預設 `§4`）、`record_pattern`（同目錄可參考的執行紀錄檔名樣式，預設 `*_執行紀錄.md`，只能是檔名）、`upstream_keywords`（子任務標題含這些字就用上游模式，1–12 個，預設 `上游`、`upstream`、`衝突`、`PR`） | event-brief |
| `conventions.pr_size` | `max_lines`、`max_files`（null＝不限，deliver 段就不量 PR 大小）、`scope`（怎麼量） | sdlc-deliver、sdlc-design-revise |
| `conventions.doc_format` | `format`、`notes` | 各段派工單 |

內建兩份：
- `default.json`：模版原本的做法（spec 驅動、驗收條件用 EARS 句型、測試先行、Conventional Commits 加 Story scope、修改既有檔 300 行或 15 檔），讓既有使用者行為不變。
- `lightweight.json`：範例。需求來自 issue（`requirements.source=command`）、不強制測試先行（實作後由 dev-acceptance-tester 補驗證測試）、commit 格式自由、不限 PR 大小。

`parallelism` 的效果（不是開發規範，只調整工作流程怎麼平行）：
- **規劃**：sdlc-design 先由 dev-spec-author 出大綱（payload `plan-outline`）。預估子任務超過 `split_threshold`，或有多個不共用檔案、可各自規劃的區塊時，拆成子計劃，每個子計劃一個 dev-spec-author 平行規劃（`specs/<epic>/sub/<id>/`），再由一個 dev-spec-author 彙整、核對介面與檔案所有權、統一 commit。子計劃範圍重疊、相依循環、彙整後默默少了子任務，workflow 都會 halted 停下交人。
- **開發**：sdlc-build 依子任務相依分層，同一層沒有相依的子任務各自 worktree 平行實作，每層由 dev-integrator 合併。跨子計劃的相依在彙整時展開成子任務的 `depends_on`。
- **測試與驗證**：有 2 個以上子計劃且 `shard_verification` 不是 false 時，sdlc-test 每個子計劃派一個 dev-verifier，另加一個整合分片（總覽 spec 的跨子計劃驗收條件＋整條 diff 的反作弊），平行驗證後彙整成 `verifier.md`，workflow 會核對彙整沒有漏條目、沒有改結果、各分片驗的是同一個 HEAD。修正時，失敗分散在多個子計劃就各自 worktree 平行修，再由 dev-integrator 合併；整合分片的失敗在合併後單獨修。

`build.test_first` 的效果：true 時 sdlc-build 走 Red 階段（先寫會失敗的測試、合進整合分支才實作）；false 時跳過 Red，實作合併後走 Tests 階段補驗證測試，測試失敗代表實作不符驗收條件，交人判斷，不改測試遷就實作。

`build.affected_tests_only` 的效果（預設 false）：true 時，子任務被退回重做（修正迴圈，第 2 次以後的派工）的派工單多一句「先用 `awf kg impact --diff <base>` 算受影響的測試、只跑那些」，算不出來就照常全跑。只省修正迴圈的時間：第一次派工、整合時的 verify、test 段的閘門都照舊全跑。需要先建知識圖（見 `docs/知識圖.md`）。


### 去客戶化掃描（`scrub`）

專案想在推送前擋掉某些字串（客戶名、內部代號）時用。**要不要掃、掃什麼、什麼時候掃都由你決定，預設完全不啟用**：沒有 `scrub`、或 `enabled` 不是 `true` 時，`awf scrub` 只印「未啟用」，`awf publish` 的行為和沒有這個功能時完全相同。

```json
"scrub": {
  "enabled": true,
  "terms": ["ACME[- ]Orbital"],
  "terms_files": [".claude/teams/scrub_terms.txt", ".claude/teams/scrub_terms.local.txt"],
  "exclude": ["docs/vendor/**"],
  "when": ["publish"]
}
```

| 欄位 | 說明 |
|---|---|
| `enabled` | 預設 `false`。 |
| `terms` | 直接寫在 profile 的規則。profile 會進版控，真實名稱不要寫這裡。 |
| `terms_files` | 規則檔，相對專案根目錄，不能是絕對路徑或含 `..`。一行一個正規式，空行與 `#` 開頭的行略過。真實名稱放一份 gitignore 的本機檔；檔案不存在時略過並提示（那份清單的規則這次沒有掃）。 |
| `paths`、`exclude` | glob，相對被掃的 repo：`*` 不跨目錄、`**` 跨目錄；寫目錄名就涵蓋底下全部。沒寫 `paths` 就全部掃。 |
| `when` | 自動跑的時機。目前只有 `publish`：`awf publish` 推送前掃「要推的分支」裡這次 diff 涉及的檔，命中就不推，掃描本身出錯（設定讀不懂、規則編不過）也不推。空的＝只在人手動跑 `awf scrub` 時掃。寫其他值是錯誤。 |

- `awf scrub [路徑…] [--json]`：掃檔案內容與路徑名。在 git repo 裡只掃 git 看得到的檔（有追蹤的，以及沒追蹤但沒被 `.gitignore` 略過的），二進位檔不掃內容，規則檔自己不掃。通過 exit 0、有命中 exit 1、設定或規則有錯 exit 2。
- **不外洩**：命中只印 `路徑:行號` 與「規則 #N（來源:行號）」，不印命中的字串，也不印規則；規則編不過只報來源與行號。規則本身可能就是機密名稱。
- 正規式的語法和模版 repo 自己的 `tests/scrub_terms.txt` 相同（`\b`、`\d`、`\s`、字元類別、`(?i)` 這些常見寫法都可以；編不過會明確報錯，不會默默略過）。
- profile 的規則有錯（路徑在專案外、inline 的規則編不過、`when` 寫了不支援的值）時，整份 profile 不合規則，閘門會照 profile 讀不懂處理（不放行）。
- team agent 可以跑 `awf scrub`（只讀）。

### 專案的 CI（`ci`）

想讓專案自己的測試與 lint 在 GitHub Actions 上跑、而且由 profile 管理時用。**預設不啟用**：沒有 `ci`、或 `enabled` 不是 `true` 時，`awf ci render` 只印「未啟用」，不產生也不檢查任何檔。跑哪些指令、哪些必過都由你決定；`awf init` 的訪談會從 `package.json` 的 scripts、`Makefile`、`Cargo.toml`、`pyproject.toml`、`go.mod` 偵測既有的測試／lint 指令當預設。

```json
"ci": {
  "enabled": true,
  "provider": "github",
  "name": "project-ci",
  "triggers": ["pull_request"],
  "runs_on": "ubuntu-latest",
  "jobs": [
    {"id": "test", "name": "測試", "run": "npm ci\nnpm test", "required": true},
    {"id": "lint", "run": "npm run lint"}
  ]
}
```

| 鍵 | 意思 |
|---|---|
| `enabled` | 預設 false。 |
| `provider` | CI 平台，目前只支援 `github`。 |
| `name` | workflow 名稱，也是檔名（`.github/workflows/<name>.yml`）；預設 `project-ci`。只能是小寫英數字與連字號，不能是 `agent-merge-gate`（模版自己的）。 |
| `jobs[].id` | job 的代號，不能重複。 |
| `jobs[].name` | 顯示名稱，也是 GitHub 上的 check 名稱（不能重複）；沒寫用 `id`。 |
| `jobs[].run` | 要跑的指令，可以多行；不能是空的。不能寫 GitHub Actions 的運算式（`$` 接兩個左大括號那種），也就不能引用 secrets。 |
| `jobs[].required` | `true`＝必過。預設 false。 |
| `triggers` | `pull_request`、`push`、`workflow_dispatch`；預設只有 `pull_request`。 |
| `runs_on` | runner 標籤（字串，或自架 runner 用的字串陣列）；預設 `ubuntu-latest`。 |

- `awf ci render`：把會產生的檔印在 stdout，**只印不寫**。`awf ci render --write` 才寫到 `.github/workflows/<name>.yml`，只由主 session 或人執行（team agent 由 hook 擋；不帶 `--write` 的 `render` 與 `check` team agent 可以跑）。同名檔不是這支工具產生的就拒絕覆寫，既有的 CI 檔不會被動到。
- 產生的檔：action 只有 checkout、釘在 commit SHA，`persist-credentials: false`；權限只有 `contents: read`；不放任何 secrets；用 `pull_request`（不是 `pull_request_target`），fork 來的 PR 拿不到 secrets。檔頭兩行是「由 awf ci render 產生」的標記與內容的 sha256。工具鏈（node、python…）用 runner 預裝的；要別的版本就寫在 `run` 裡。
- `required: true` 的 job：`--write` 時把 `name` 併進 `guard.config.json` 的 `auto_merge.required_checks`（只加不刪）。`awf merge-gate` 看到這份清單時，裡面每個名稱都要出現在 `--checks` 裡，少一個就 hold。要讓 GitHub 也擋，仍要在 ruleset 把這些 job 設成 required（伺服器端才是信任邊界）。
- `awf ci check` 與 `awf doctor`：檔還沒產生、被手改（檔頭的雜湊和內容不符）、或和現在的 profile 產生的不同，都提示並附修法。
- 改 CI 檔的 PR 在 merge gate 一律交人（`.github/` 是內建的敏感路徑）。

### 依需求類型分流（recipes、modifiers）

完整 SDLC 每次約派 25–35 個 agent，修一個 bug 不需要這麼多。`sdlc-plan` 第一步先派一個 `tpm-planner` 理解需求（triage），建議 recipe；由人在 plan 閘門選定，寫進 `run.json` 鎖定，之後只能用 `awf save-run escalate` 加嚴。內建 11 個 recipe（feature、bugfix、change、hotfix、refactor、deps、docs、test-only、perf、spike、revert）與 5 個 modifier（ui、security、migration、public_api、large），表格見 README〈依需求類型分流〉。

自訂方式：
- **改內建 recipe**：直接改專案 `methodology.json` 的 `recipes.<名>`（下一個 run 生效）。例如團隊的 bugfix 也要 design：在 `stages` 加 `design`、`design_lenses` 加 `coverage`、`plan`。
- **新增 recipe**：在 `recipes` 加一個鍵；triage 會讀 `description` 判斷什麼時候用它。`plan_mode` 只能選內建的 8 種（feature、diagnose、impact、invariants、changelog、baseline、research、revert），每種 mode 的 intent 必要節可以用 `plan_modes.<mode>.sections` 覆寫。
- **不能省的部分**（schema 與工具強制，改 profile 也拿不掉）：每個 recipe 都有 plan 段（intent）；會產生改動的 recipe 都有 build、deliver、merge 段；plan 一律由人核准；每張派工單引用 `rules.md` 與輸出語言；每個 agent 都留執行紀錄。
- **diff 反查**：`awf publish` 推送前、`awf merge-gate --recipe <run.json>` 判定時，用實際 diff 檢查 recipe 夠不夠：`build_kinds` 沒有 code 卻改了程式、碰到 migration 卻沒有 design 段與 rollback lens、改了依賴宣告或鎖檔卻沒有一定做安全審查、spike 要推送，都拒推／hold。
- **舊 profile**：沒有 `recipes` 時一律當成 feature（行為和 0.2.0 一樣）。`awf init --upgrade` 會列出缺少的 `recipes`、`modifiers`，加 `--adopt-new-fields` 才補上。
- 解析規則有工具端（`awf recipe`，`crates/awf-core/src/recipe.rs`）與 JS（`plugin/workflow-templates/snippets/recipe.js`）兩份，`golden-set/recipes/*.json` 兩邊都跑，`cargo xtask check-recipes` 比對結果一致；改規則要兩邊一起改並補 golden 案例。

### 執行紀錄與 run_brief

- **每個 agent 都留紀錄**：每張派工單最後一行指定 `<run_dir>/<段>/<label>.md`，agent 自己寫任務摘要、做了什麼、指令與結果、結論、不確定的地方。`awf save-run stage` 依 workflow 回傳的 `trace` 產生 `<run_dir>/<段>/執行紀錄索引.md`，紀錄檔缺了算缺件、不能政策核准。tpm-reviewer、tpm-skeptic、dev-release-watcher、tpm-planner 因此有 Write，但 hook 只准它們寫 runs_dir 底下的 .md；dev-merge-steward 仍沒有 Write，紀錄由 `awf save-run stage` 依信封代寫。
- **awf run-brief**（Read less）：`awf run-brief --log <run_dir>/<段>/logs/<label>.log -- <指令>`。完整輸出寫進 log，終端只印結束碼、失敗的測試（最多 20 則）、最後幾行與 log 路徑，結束碼原樣傳回。`--log` 只能指到 runs_dir 底下某個 run 目錄裡的 `.md`／`.log`／`.txt`，不能是工具自己的檔（`run.json`、稽核檔、帳本、資料包、執行紀錄索引…）或 `archive/` 底下，不合就拒絕、不執行指令；不帶 `--log` 寫到暫存目錄。認得 pytest、jest／vitest、go test、unittest。做法參考 [caveman](https://github.com/juliusbrussee/caveman)（Apache-2.0）的 Read less，自己實作。
- **信封上限**：summary 400 字、evidence 12 則、每則 result 300 字；細節寫在檔案。
- **token 預算**：`cargo xtask check-budget` 乾跑量各 workflow 的派工數與派工單字數，超過 `golden-set/token-budget.json` 基準 10% 失敗；確認是預期的變多後用 `--update` 更新。乾跑量不到 agent 實際讀寫的 token。

### 省 token：模型分級、讀取預算、知識層與資料包

起因：實測一個 plan 段要 21～29M token，其中 95% 是 context 重讀——agent 整檔讀大檔，之後每一輪都把它重讀一次；而且每個 agent 都用最貴的模型。0.4 起用四個機制處理，都是 profile 的工作流程參數，不是開發規範。

**模型分級（`models`）**
- 等級只有三個：`light` < `standard` < `strong`。內建對應 `haiku`、`sonnet`、`inherit`（沿用主對話模型）；要換模型改 `tiers`。
- `mode: auto`（預設）：triage 會回傳 `model_plan`（各角色建議的等級與理由），design 可以給子任務標 `complexity`。工具取 **max(AI 建議或 `defaults`、`floors`、modifier 的 `model_floors`)**，所以 AI 只能在下限以上選。
- 內建下限（profile 蓋不掉，只能再加高）：`dev-merge-steward`、`dev-security-reviewer`、`tpm-skeptic@merge`、`dev-spec-author@plan` 是 `strong`，`tpm-skeptic@plan` 是 `standard`。modifier `security` 把 `tpm-skeptic` 拉到 `strong`、`large` 把 `dev-spec-author` 拉到 `strong`（內建 modifier 的下限，profile 把 `model_floors` 拿掉也照樣生效）。
- `tiers` 的對應不能倒掛：`strong` 不能對到比 `standard` 弱的模型（已知別名 haiku < sonnet < opus < inherit），否則 profile 驗證不過。
- 使用者自己的 agent（擴充 agent）不指定模型，沿用它 frontmatter 的設定。
- **失敗升級**：`auto` 模式下，agent 沒交件或交件無效時，用高一級重派一次（最多一次），trace 會記 `superseded` 與 `escalated_from`。
- **閘門**：`awf save-run stage` 用 profile 重算每筆 trace 的下限，trace 的模型比下限低就判 invalid。workflow 回傳的 `models` 列出這次各角色實際用的等級與理由。
- 不想分級：`mode: inherit`。沒有 `models` 的舊 profile 也是全部沿用主對話模型。
- 0.5 起 12 支 workflow 的派工都走執行核心（`snippets/kernel.js`）。profile 有 `models` 時，design 之後各段的模版角色也由模型分級決定模型（預設 `standard`），不再沿用主對話的模型；要維持原樣就設 `mode: inherit`。
- **派工數上限**：一支 workflow 一次執行最多派 `limits.max_agents` 個 agent（1–1000 的整數；沒寫或不在範圍內用 40；design 另加 `3×max_sub_plans`、build 另加 `4×子任務數`、test 另加 `4×子計劃數`）。到上限就不再派、停下交人，執行紀錄索引會寫明是上限。
- 會動到共用分支的角色（`dev-integrator`、`dev-merge-steward`）失敗時不自動重派，交人判斷。

**讀取預算（`limits`）**
- hook 對**模版角色**的 Read 做兩件事：超過 `whole_file_lines` 的檔沒帶 offset／limit 就擋下（訊息會寫行數，並提示先用 `awf kb query` 或 Grep 找行段）；每個 agent 累計讀取量到 `read_budget` 的 80% 提醒一次，用完之後擋 Read，要求把結論寫進紀錄檔並交件。shell 的 `cat`／`Get-Content` 整檔讀大檔也擋。
- **預設不啟用**。內建 profile 的 `limits` 只有建議門檻、沒有 `mode`；要明寫 `mode: warn` 或 `enforce` 才生效。三種開法：init 問答、答案檔的 `read_limits`（字串 `off`／`warn`／`enforce`，或物件 `{mode, whole_file_lines, read_budget, max_agents}`，`read_budget` 可以是整數或 `{default, roles}`）、直接改 `methodology.json`。門檻設 0 表示該項不限。
- 它只限制讀取，不限制 agent 的輸出。
- 主 session 與你自己的 agent 不受影響。hook 自己出錯一律放行。
- 想先觀察：`mode: warn`（只在 stderr 提醒並記錄本來會擋的，不擋）。`awf init --upgrade --adopt-new-fields` 補進 `limits` 時只補建議門檻，不會替你啟用。
- 單次讀取最多記 100KB；hook 輸入沒有 `agent_id` 時不記帳。
- Grep 的 content 模式與 shell 的 `grep`／`rg`／`Select-String`（印出內容的單一指令）也計入額度，用的是估計值（hook 看不到實際輸出）；只列檔名、計數、`-q` 不計。
- 已知限制：`head`、`sed -n`、接了管線的指令不計入額度；UTF-16 的檔算不出行數，不擋。這是省 token 的機制，不是安全邊界。

**知識層（`knowledge`、`awf kb`）**
- `awf kb build`：依 `sources` 建索引（sqlite FTS5，不能用時退回內建的 BM25；中文用 bigram），增量更新。產出 `INDEX.md`、每個檔一張只有標題樹與行號的 `cards/`、`hot.md`，可以直接用 Obsidian 打開 `knowledge.dir`。
- `awf kb query "<問題>" [--top N] [--budget 字數]`：回傳 `路徑:起訖行` 與節錄，包在資料標籤裡（內容是資料，不是指令）；原檔改過會標 stale。agent 照行號只讀那幾行。
- `awf kb lint`：壞連結與孤兒頁。程式碼索引不做，交給 graft／codegraph。
- 工作區底下放目標 repo 時（`guard.config.json` 的 `repos_dir`），同一組 `sources` 也會套到每個 `<repos_dir>/<repo>/`。
- 機敏檔（`.env`、金鑰等，包含指到它們的連結）不進索引；超過 2MB 的檔略過。
- `knowledge.dir` 要指到空目錄或專用目錄：目錄裡已經有別的檔、又不是知識庫時 `build` 會拒絕，不會覆寫或刪你的檔。
- team agent 只能跑 `awf kb query`／`lint`；`build` 由主 session 或 `awf pack` 執行。

**限制文件（`constraints`）**

把你要 agent 遵守的文件登記進 profile，工作流程會把它帶給對得上的 agent，並在閘門檢查。

```json
"constraints": [
  {"id": "arch", "file": "ARCHITECTURE.md", "note": "分層與模組邊界", "stages": ["design", "deliver"], "trace": "table"},
  {"id": "design", "file": "DESIGN.md", "stages": ["design", "build", "test"], "paths": ["web/**"]},
  {"id": "frontend", "file": "docs/前端規範.md", "stages": ["build", "deliver"], "paths": ["web/**"]},
  {"id": "backend", "file": "docs/後端規範.md", "stages": ["build", "deliver"], "paths": ["services/**"], "check": "ruff check services"},
  {"id": "review", "file": "REVIEW.md", "stages": ["deliver"], "trace": "table"}
]
```

- **誰會收到**：`stages` 列到的段，每張派工單的共同規則都會列出這份文件（只給路徑與說明，agent 先找相關行段再讀，不整檔貼進派工單）。有 `paths` 的限制在 build 段只發給「擁有的路徑對得上」的子任務，所以前端規範不會發給只改後端的子任務；在其他段整段適用，並註明範圍。
- **偏離要講**：共同規則要求 agent 做不到或要偏離時，在交件與執行紀錄寫明偏離哪一條與理由。
- **閘門檢查**（`awf save-run stage` 存檔時算，政策核准時重算）：
  - 文件不存在（專案根目錄與目標 repo 都找不到）：不能政策核准。
  - `trace: table`：該段的執行紀錄要有〈限制對照〉一列 `| <id> | 符合／偏離／不適用 | 依據或理由 |`。沒有這一列、或判定是「偏離」，都不能政策核准，要由人決定。
  - `check`：在目標 repo 執行（沒有目標 repo 就在專案根目錄），exit 非 0 或逾時（預設 300 秒，可用該筆的 `timeout` 改）不能政策核准；結果記在 run.json 的 `constraint_checks`。這是你自己寫在 profile 的指令，會由主 session 在存檔時執行。
  - 人工核准照記，但會印出警告。
- **範圍的細節**：build 段有 `paths` 的限制不要求對照表（它只發給部分子任務）；要對照就把同一筆也套到 test 或 deliver。
- **怎麼登記**：init 問答、答案檔的 `constraints`（可以寫簡寫 `"ARCHITECTURE.md"` 或 `"docs/fe.md=build+deliver"`，沒寫段時是 design＋deliver），或直接改 `methodology.json`。
- 沒有 `constraints` 的 profile 行為完全不變。這是「告知並檢查有沒有對照」的機制：內容有沒有真的符合，仍靠審查 agent 與你寫的 `check` 指令。

**工具先定位（`awf locate`）**
- `awf pack plan` 會先用 `awf locate` 找行段：把目標 repo 的文字檔切成 40 行的視窗，用需求全文的詞排序（和知識層同一套分詞，中英文都可以），不花 token。
- 文件類的調研角度（既有 specs／ADR、需求出處）命中夠多時，直接把行段交給分析 agent，不派定位 agent。
- 程式類的角度只當起點：工具找得到字面對得上的檔，也會沿 import 與引用關係多帶一層，但「需求沒提到名字、這次卻會用到」的檔找不到，所以定位 agent 照派，只是從這些行段出發、查詢上限減半。
- 不想用：`awf pack plan … --no-locate`。workflow 回傳的 `located_by` 寫明每個角度是工具（`tool`）、agent（`agent`）、兩者（`tool+agent`）還是知識圖（`kg`；圖標了夠用但合格的行段不到 3 段時是 `kg+agent`）找的。

**資料包與調研重用（`awf pack`）**
- 每段開跑前由主 session 跑 `awf pack <段> --run <run_dir>`，寫出 `<run_dir>/<段>/pack.md`（需求、知識庫命中的行段、前面各段的紀錄索引）與 `pack-args.json`（要併進 workflow args 的 `pack`、`reuse`）。不花 LLM token，內容可重現。
- **兩段式調研**：`sdlc-plan` 的每個調研角度先派一個 `light` 等級的定位 agent（只回傳 `locations`：路徑與行段），再派分析 agent 只讀那些行段。定位沒交件時該角度列缺件，不派分析。
- **角度數**：triage 可以用 `angles` 從 recipe 的角度裡挑需要的；modifier 帶進來的角度不能省。回傳的 `angles.skipped` 會列在閘門重點。
- **重用**：plan 存檔後，`<run_dir>/plan/reuse.json` 記下每個角度讀過的來源檔 sha1。plan 重跑、或同一個 epic 另開 run（`--reuse-from <舊 run_dir>`）時，來源檔沒變的角度直接沿用、不派工；`awf save-run stage plan` 會重新核對 hash，不符判 invalid。需求改了（需求是檔案時看檔案內容）預設全部重做，確認不影響調研才加 `--keep-research`（會記在 `reuse.json`，閘門才認）。沒做完的結論（blocked）不記也不沿用。 來源檔所在的目錄新增、刪除或改名了檔案時，該角度也會重做（新的檔可能就是該讀的）。
- 重用的判斷是「上次定位到的檔沒變」：repo 裡**新增**的檔不會觸發重做。新增了會影響結論的文件時，不帶 `reuse` 重跑（刪掉 `pack-args.json` 裡的 `reuse`，或刪 `reuse.json`）。
- **決策記憶**：人在閘門上回答的問題用 `awf save-run approve … --answer "<問題>=<答覆>"`（可重複；`--answer-scope epic|project`、`--answer-expires YYYY-MM-DD`）或 `awf save-run decide <run_dir> --question … --answer … --by … --at …` 記進 `<runs_dir>/decisions.jsonl`。之後每份資料包的〈既有決定〉會帶上相關的，共同規則要求 agent 提問前先看、已經答過的不再問。
  - 範圍 `epic`（預設）：只帶給同一個 run、同一個 epic，或用 `--reuse-from` 接續的 run。範圍 `project`：帶給用詞和需求對得上的任何 run。
  - 同一題後面的答覆取代前面的；過期（或到期日讀不懂）的不帶。只有人能記，政策核准不能帶 `--answer`。
  - `<runs_dir>/決策記憶.md` 是同一份資料給人看的檢視；想讓知識庫查得到，把它加進 `knowledge.sources`。這兩個檔 team agent 不能寫。
  - 這是輔助：決定寫不進去不影響核准，資料包讀不到就不帶。
- **build 的子任務資料包**：`awf pack build` 另外為每個子任務寫 `<run_dir>/build/<子任務 id>/pack.md`：子任務說明、擁有的檔、spec 對應小節的行段、依路徑對到的限制文件（標題與行號）、相依子任務擁有的檔與完成條件。實作與寫測試的 agent 開工先讀這一份，不用整份讀 spec。
  - 小節怎麼對：design 段拆工時每個子任務標 `spec_refs`（`spec.md#小節標題`，檔相對於 `specs/<epic>/`，省略就是 `spec.md`；標題要照抄、不能重名）。沒標的子任務仍有資料包，只是沒有 spec 行段。
  - `spec_refs` 指到不存在的檔或小節時記在 `pack-args.json` 的 `spec_ref_errors`，`sdlc-build` 開工前就停下交人（拆工和 spec 對不上）。
  - 子任務清單取自 `<run_dir>/design.json`（沒有 design 段取 `plan.json`）；也可以用 `--subtasks <檔>`、`--epic`、`--spec <目錄>` 指定。
- `pack.md`、`reuse.json`、`pack-args.json` 只由主 session 產生：team agent 不能寫這些檔，也不能執行 `awf pack`。

**量成本**：`awf cost --project . --run-dir <run_dir>` 讀 Claude Code 存的 workflow transcript，依角色與模型加總 token、時間、平均 context。transcript 格式官方沒承諾穩定，讀不懂時會明說並 exit 0；它不參與任何閘門。

### 查詢量與調研上限

`limits.dispatch` 與 `limits.research` 是寫在派工單上的用量指示，不是閘門：agent 照它收斂，工具不會因為超過而擋。大 repo 可以調大，小 repo 可以調小。沒寫或值不合法（超出範圍、不是整數）一律用預設值。

| 鍵 | 範圍 | 預設 | 寫在哪張派工單 |
|---|---|---|---|
| `dispatch.triage_queries` | 1–40 | 8 | 需求分類（triage）最多做幾次查詢 |
| `research.locate_rounds` | 1–20 | 6 | 定位最多幾輪工具呼叫 |
| `research.locate_queries` | 1–40 | 12 | 定位最多幾次查詢 |
| `research.stall` | 1–10 | 3 | 連續幾次查詢沒有新發現就停（定位與分析共用） |
| `research.max_segments` | 3–16 | 12 | 一個角度最多回報幾段（16 是 `locations` 信封的上限） |
| `research.segment_lines` | 20–400 | 120 | 每段最多幾行 |
| `research.context_lines` | 1–100 | 20 | 定位時要確認內容，只讀命中處前後各幾行 |
| `research.analysis_rounds` | 3–50 | 15 | 分析最多幾輪工具呼叫 |
| `research.extra_segments` | 0–12 | 4 | 分析時行段不夠，最多再補幾段 |

- 工具已經給了種子（`awf locate` 找到的行段）時，定位的輪數、查詢數、停手次數各減半（無條件進位）：預設是 3 輪、6 次、連續 2 次。
- 行段直接由工具或知識圖給、沒有派定位 agent 時，補段數是 `extra_segments` 的 1.5 倍（無條件進位）：預設是 6。
- 「定位到幾段才算夠」（3 段）沒有開放：它要和 `awf locate`、知識圖的判斷一致。

### 工具端的大小、節奏與只能加嚴的清單

這一節的欄位都是工具（`awf` 各子指令）在讀，範本不讀。前兩張表只影響輔助輸出的大小與節奏：沒寫、型別不對、超出範圍的那一項用預設值（＝原本寫死的值），閘門不讀它們。後兩張表是閘門與守門在讀的，只能往嚴的方向加，寫壞了不會被當成沒設定。

**資料包、知識層、工具定位**（`knowledge`）

| 鍵 | 範圍 | 預設 | 用途 |
|---|---|---|---|
| `knowledge.pack.top` | 1–50 | 12 | 資料包從知識庫取幾筆 |
| `knowledge.pack.budget` | 200–20000 | 3000 | 知識庫節錄的字數預算 |
| `knowledge.pack.decisions` | 0–50 | 12 | 〈既有決定〉最多帶幾筆（0＝不帶） |
| `knowledge.pack.requirement_lines` | 20–2000 | 200 | 需求是檔案時貼前幾行 |
| `knowledge.pack.headings` | 1–200 | 40 | 子任務資料包裡每份限制文件最多列幾個標題 |
| `knowledge.extensions` | 1–16 個副檔名 | `.md`、`.markdown`、`.txt` | 知識庫與知識圖收哪些副檔名的文件。寫了就是整份清單；`sources` 的 glob 要對得到才會收；機敏檔一律不收。不合規定時用預設並警告 |
| `knowledge.locate.max_segments` | 1–40 | 12 | 工具定位每個角度最多幾段 |
| `knowledge.locate.segment_lines` | 40–400 | 120 | 相鄰行段合併後最多幾行 |
| `knowledge.locate.min_segments` | 3–12 | 3 | 少於幾段算不夠、照派定位 agent。只能調高：3 段是範本與知識圖共用的下限 |
| `knowledge.locate.min_coverage` | 0.05–1 | 0.3 | 行段涵蓋的查詢詞比例低於這個算不夠 |
| `knowledge.locate.max_files` | 100–20000 | 4000 | 最多看幾個檔；超過算沒看完，結果不算夠 |
| `knowledge.locate.prune` | 最多 32 個目錄名 | 空 | 另外不看的目錄名（單一層的名字）。內建的 `.git`、`node_modules`、`dist`、`build`、`target` 等拿不掉 |

同樣的輸入與設定重跑，`pack.md` 逐字相同；改了這些值，資料包的內容會跟著變，這是預期的。

**watcher、長輸出濃縮、閘門重點**

| 鍵 | 範圍 | 預設 | 用途 |
|---|---|---|---|
| `progress.watch.interval` | 1–3600 | 5 | `awf watch` 每隔幾秒看一次；`--interval` 有給以旗標為準 |
| `progress.watch.stall_seconds` | 0–86400 | 900 | 超過幾秒沒有動靜記 `workflow_stalled`（0＝不記）；`--stall-seconds` 有給以旗標為準 |
| `progress.watch.progress_step` | 1000–10000000 | 50000 | 同一個 agent 每多用多少 token 記一筆 `agent_progress` |
| `limits.run_brief.max_fails` | 1–200 | 20 | `awf run-brief` 最多列幾則失敗的測試 |
| `limits.run_brief.tail` | 5–500 | 20 | 認得測試框架時結尾留幾行；`--tail` 有給以它為準 |
| `limits.run_brief.unknown_tail` | 5–500 | 40 | 認不得框架時結尾留幾行 |
| `limits.display.agents` | 1–200 | 40 | 閘門重點（`awf next` 的 `highlights`）最多列幾個 agent 的摘要 |
| `limits.display.questions` | 1–200 | 30 | 未決問題與暫定做法各最多列幾則 |

決策記憶的長度上限（問題 300 字、答覆 600 字）沒有開放：它是 `decisions.jsonl` 的寫入檢查，內容會進資料包與對話。

**閘門在讀的（profile，只能加嚴）**

| 鍵 | 內容 | 寫壞了 |
|---|---|---|
| `gates.extra` | 另外要等核准的段，只能是 `build`、`sync`。內建的四個閘門（plan、design、test、deliver）拿不掉。存檔當下列了的段標上閘門，之後把設定拿掉也不會消失；設定之前已經存檔的段不回溯 | profile 判不合規則 |
| `stages.design.criteria_id_pattern` | 驗收條件編號的樣式（Python `re` 的寫法，最多 200 字），沒寫用內建的 `AC-1` 這類寫法。拆工檢查與連結檢查（`links`，含連結帳本）用同一個樣式對 spec、子任務與測試結果的編號 | 編不過、會對到空字串：profile 判不合規則，不會當成沒設定 |
| `constraints_format.heading`、`constraints_format.verdicts.{ok,deviation,na}` | 限制對照的節名與判定詞。內建的「符合／偏離／不適用」永遠認得，這裡的詞是另外也認。派工單（共同前綴的限制規則）要 agent 寫的節名與三個判定詞也照這裡，所以 agent 寫的和工具認的是同一組 | 和內建的詞撞意思、三個詞有重複、含 `\|`：profile 判不合規則 |
| `diff_classes_extra` | `{ "migration": [正規式…], "manifest": […], "agent_config": […], "code": […] }`，每一類最多 32 條（Python `re` 的寫法、不分大小寫，比對相對 repo 根的路徑）。命中的路徑另外算成那一類（不再只當文件或測試）。`awf publish`、`awf merge-gate --recipe`、`awf recipe check-diff` 的 diff 反查與 merge-gate 的風險分級共用。不能指定成 `doc`、`test` | publish 拒推、merge-gate 交給人 |

`constraints_format` 兩邊用同一套規則：範本的共用片段（`awfConstraintFormat`）和工具端的檢查一樣嚴，有一處不合規則就整份不採用、派工單退回內建的「限制對照」與「符合／偏離／不適用」，不會出現「派工單要 agent 寫、工具卻不認得」的詞。只設其中幾個詞時，沒設的用內建的。設了 `criteria_id_pattern` 之後內建的 `AC-1` 寫法不再算編號（拆工檢查與連結檢查都一樣）。

**守門設定在讀的（`guard.config.json`，只能加）**

| 鍵 | 內容 | 寫壞了 |
|---|---|---|
| `auto_merge.sensitive_paths_extra` | 另外算高風險的路徑樣式（正規式陣列，最多 64 條）。命中就交給人；內建的高風險清單拿不掉 | 這次判定一律 high、交給人 |
| `secret_files_extra` | 另外算機敏檔的路徑樣式（正規式陣列，不分大小寫，最多 64 條、每條 300 字） | 和設定檔讀不懂一樣：模版角色的寫入全擋、主 session 照預設規則；`awf publish` 拒推；`awf kb`、`awf kg` 不建索引 |
| `secret_patterns_extra` | 另外算機敏值的樣式（正規式陣列，分大小寫，比對 diff 新增的每一行） | 同上 |

`secret_files_extra` 由 hook（Read、Grep 與 shell 的讀取）、`awf publish`、`awf kb`、`awf kg` 共用同一份；`secret_patterns_extra` 用在 `awf publish` 推送前的掃描，命中時只印是第幾條，不印值。兩個欄位都是選填，範本不放這兩個鍵。

### 名稱表與換角色（`lenses`、`test_modes`、`research_angles`、`roles`）

recipe 與 modifier 用名稱選用 lens、審查軸、驗證模式、調研角度。這些名稱的定義原本寫在範本裡；現在可以在 profile 改寫內建的，或加自己的：

```json
"lenses": {
  "design": { "data-privacy": { "ask": "設計有沒有交代個資欄位的遮罩與保存期限？" } },
  "deliver": { "i18n": { "ask": "新增的畫面文字有沒有進翻譯檔？" } }
},
"test_modes": { "load-test": { "note": "加跑壓力測試，回應時間列成一則 criteria。" } },
"research_angles": { "data-model": { "ask": "找出這次需求會碰到的資料表與欄位。" } },
"recipes": { "feature": { "design_lenses": ["coverage", "plan", "data-privacy"], "deliver_axes": ["standards", "spec", "bugs", "history", "i18n"] } }
```

- 名稱是小寫英數與連字號（英文字母開頭、40 字以內），每張表最多 24 個（`design_revise` 8 個）；`ask`／`note` 是 1–2000 字。
- 同名的定義換掉內建的問法；`lenses.design_revise` 的新名稱一律加派，其餘的新名稱要由 recipe 或 modifier 選用才會派。
- 自己加的審查軸排在內建四軸後面；閘門照 label `review:<軸>` 核對有沒有交件，自訂的軸一樣會被核對。
- **指到沒有定義的名稱會停下**：recipe 的 `design_lenses`、`deliver_axes`、`test.modes` 寫了內建與 profile 都沒有定義的名稱時，profile 的檢查（`awf doctor`、存檔）會報錯，workflow 開工前 halted。以前不認得的驗證模式會被默默略過（少跑一種驗證也不說），現在不會。定義本身不合法的（`ask` 不是字串等），內建有同名的照內建，沒有的等於沒定義。
- 調研角度沒有定義時照舊用通用的問法，不會停下。自訂角度一律經過定位 agent（`awf locate` 的文件／程式分類只認內建角度）。

`roles` 把內建流程的某一步換成你自己的 agent：

```json
"roles": { "plan.research": "acme-researcher", "deliver.review": "my-plugin:acme-reviewer" }
```

| 步驟 | 原本的角色 | 是哪一步 |
|---|---|---|
| `plan.locate`、`plan.research` | tpm-researcher | plan 段兩段式調研的定位與分析 |
| `plan.challenge` | tpm-skeptic | 反駁 intent |
| `design.analyze` | tpm-skeptic | design 段的各個 lens |
| `design.recheck` | tpm-skeptic | 修正後的複查 |
| `deliver.review` | tpm-reviewer | 各審查軸 |
| `deliver.verify` | tpm-skeptic | 反駁審查發現 |

- 換上去的 agent 要登記在 `guard.config.json` 的 `extension_agents`（和擴充 agent 同一張表，只能對應唯讀類的角色）；沒登記時 `awf next` 與 `awf build` 拒絕產生腳本。不能換成模版角色（`tpm-*`、`dev-*`）。
- 模型分級與下限照被換掉的角色算（trace 記 `role_as`），不會因為換了 agent 就沒有下限；交件格式、派工單、缺件的處理都不變。`awf save-run stage` 存檔時會重算一次，而且不採信 trace 的 `role_as`：依這一段與派工的 label 認出是哪一步，再看 profile 的 `roles` 把這一步換成誰，照被換掉的角色的下限判；低於下限、或 `role_as` 和設定對不上，該段判 invalid。
- 沒有開放的：merge 段（信任邊界）、build 段（檔案所有權）、test 段的驗證與兩種審查（閘門依角色名核對有沒有交件）、撰寫類的步驟、事件 workflow。寫了不開放的步驟，profile 的檢查會報錯，範本不採用。

`sdlc-merge` 的合併角色與凍結檔不在 profile，跟著 `guard.config.json` 的 `auto_merge.merger_role`、`auto_merge.freeze_file`（hook 與 `awf merge-gate` 讀的同一份）：有明寫而且和預設不同時，`awf next` 把它帶進這一段的參數，`--set` 蓋不掉。

合併角色換成角色名不是 `dev-merge-steward` 的 agent 時（例如別的 plugin 的合併 agent；它要是 team agent，hook 才會放行合併，見 [`自動合併信任模型.md`](自動合併信任模型.md)），工具端照設定檔認它、不看 trace 怎麼寫：

- 模型下限照 `dev-merge-steward`（strong），存檔時重算，低於下限判 invalid。
- 不自動重派（和 `dev-merge-steward` 一樣：合併有副作用）。
- 它沒有寫執行紀錄時，存檔工具和對 `dev-merge-steward` 一樣依它的合併決定代寫；自己寫了就用它寫的。
- 自訂腳本（`awf next --script`）不能派它，就算它登記在 `extension_agents`。

沒有設 `merger_role`、或設的就是預設值時，以上都不啟用，行為和沒有這個設定時相同。

### 沒有開放、或只開放一個方向的值

| 值 | 處置 | 理由 |
|---|---|---|
| 信封長度（`limits.envelope`） | 只能調小 | 信封 schema 的上限（summary 400 字、evidence 12 則）是交件驗證的一部分，調大等於放寬驗證。調小的部分只寫在派工單上，工具仍照 schema 的上限驗 |
| 審查信心門檻（`review.min_confidence`） | 只能調低 | 門檻越高，留下的發現越少 |
| 事件的角度數與步驟數（`limits.event`） | 可調到 16 與 6 | 超過仍然拒絕執行；派工數另受 `limits.max_agents` 限制 |
| 備份 ref（`conventions.sync.backup_ref`） | 只能在 `refs/backup/` 底下 | 樣式寫到別處會建出分支或 tag，繞過分支守門 |
| 子任務的合併方式（`conventions.branch.integrate`） | 只有 `merge --no-ff` 與 `merge` | squash、rebase 會改寫子任務的 commit：commit 格式與署名的檢查、合併後清分支（`git branch -d`）都依賴原本的 commit 還在 |
| 安全審查者能寫的位置 | 不開放（`stages.test.security_review.docs_dir` 只決定讀哪裡） | 審查者只讀：守門只放行自己的報告與 `evidence/` |
| 重做與修正的輪數（`limits.rounds`） | 0–5 | 跑滿仍然交人 |
| recipe 選用的 lens、審查軸、驗證模式 | 可以加自己的，指到沒定義的名稱一律停下 | 默默略過等於少查一項 |
| 換角色（`roles`） | 只開放七個唯讀步驟 | merge 是信任邊界、build 有檔案所有權、test 的驗證與審查由閘門依角色名核對 |
| test 段的驗證者與兩種審查者 | 不開放換成別的 agent | 政策核准前，閘門依角色名核對 recipe 要求的角色有沒有交件（dev-verifier、dev-design-reviewer、dev-security-reviewer）。換成別的名字之後，要嘛閘門認不出誰交了件，要嘛得採信 trace 自己說的身分，兩種都是放寬 |
| 合併角色 | 不在 profile，只跟 `guard.config.json` 的 `auto_merge.merger_role` | 誰能合併由 hook 依完整的 agent_type 判；工具端的下限、代寫紀錄、不重派也只認設定檔，不認 trace |
| 整合分支的命名（`<prefix><epic>`） | 不開放 | 守門、`awf publish`、`awf sync-branch` 與狀態機都照這個樣式認分支；只開放它後面的子任務與修正分支 |
| plan_mode 的種類 | 不開放新增 | intent 的必要節由工具端依 plan_mode 核對；只開放每種 mode 的 `sections` 與 `refute` |
| `spec.md` 的檔名 | 不開放 | `awf save-run` 的拆工檢查讀 spec 目錄的 `spec.md`、子任務的 `spec_refs` 沒寫檔名時指的是它（`awf pack`、知識圖都照這個預設），交付文件型錄的來源也用這個檔名；改名等於這些檢查找不到檔 |
| `intent.md`、`design.md`、`plan.md`、`progress.md` 的檔名 | 不開放 | 交付文件型錄用檔名當來源（`<spec 目錄>/**/intent.md` 等），過期判斷靠它（閘門核對 intent 是看信封裡 `kind: intent` 的文件，不看檔名）；派工單、agent 檔與各段之間也用這幾個名字交接。要不要產出其中哪幾份可以調（`stages.<段>.artifacts`），放在哪個目錄也可以調（`specs_dir`） |
| `verifier.md`、`verifier-<分片>.md`、`design-review.md`、`security-review.md`、`evidence/` | 不開放 | 守門依檔名放行：唯讀的審查角色只能寫這幾個名字（`guard_paths` 的白名單）。開放改名就要讓設定決定審查者能寫哪些檔，等於放寬守門；`sdlc-test` 的彙整核對與合併時的 `--reviewed-sha` 也從 `verifier.md` 那一步來 |
| `outline.md`、`sub/<id>/`（拆子計劃時） | 不開放 | `sdlc-design` 的平行規劃與彙整照這個位置交接，彙整後的確定性核對也照它 |
| run 目錄裡的 `pr-description.md`、`review.md`、`revert-proposal.md` | 不開放 | 沒有工具依這幾個檔名做檢查，技術上可以開；但它們是流程自己放在 run 目錄的中間產物（PR 說明草稿、審查彙整、revert 提案），不進目標 repo，沒有要跟專案慣例對齊的地方 |
| run 目錄裡的 `context.md`、`pack.md`、`執行紀錄索引.md`、`接手摘要.md`、`run.json` | 不開放 | 由工具產生，守門依檔名保護（team agent 不能寫） |

### 新增 profile

1. 複製 `plugin/scaffold/.claude/teams/methodologies/default.json` 成新檔（檔名就是 profile 名稱），改內容；範例一律用虛構的「示範客戶 ACME」。
2. golden-set 會把 `methodologies/*.json` 全部當正例驗：`cargo xtask golden`。
3. 要改 schema 時，同時在 `golden-set/valid|invalid/methodology*.json` 補正反例（範例檔寫 `"schema": "methodology"` 而不是 `payload`）；schema 表達不了的規則寫在 `crates/awf-core/src/schema.rs` 的 `methodology_errors`。
4. 不想改模版也可以：把 profile JSON 放在任何地方，init 時 `METHODOLOGY=<路徑>` 或答案檔 `"methodology": "<路徑>"`。

### init 問答與答案檔

`awf init` 互動模式在佔位符問答之後逐項詢問（每題有預設值，Enter 直接用）：開發規範 profile、要不要測試先行、code style 工具或指令、commit 格式與檢查 regex、分支前綴、PR 大小上限（行數、檔案數，0＝不限）、文件格式。在 Claude Code 裡可以用 `/agent-workflow:init-workflow`，它會先在對話中問完再寫答案檔。

非互動用 `--answers <答案檔>`（JSON；沒寫的鍵沿用 profile）：

```json
{
  "methodology": "lightweight",
  "test_first": false,
  "code_style": {"description": "提交前跑 ruff", "tool": "ruff", "command": "ruff format --check ."},
  "commit": {"format": "<type>: <摘要>", "examples": {"feat": "feat: <Story> 實作"}, "check_regex": "^(feat|fix|docs|test|chore): .+"},
  "branch_prefix": "feature/",
  "pr_size": {"max_lines": 400, "max_files": null},
  "doc_format": "Markdown",
  "requirements": {"source": "json", "path": "_tpm/requirements.json"},
  "overrides": {"stages": {"test": {"guidance": "示範客戶 ACME：先跑 make verify"}}}
}
```

- `methodology`：profile 名稱或 JSON 路徑（蓋過 workflow.config 的 `METHODOLOGY`）。
- `code_style`、`doc_format`：字串或物件；`commit` 給字串時只改格式說明，profile 的範例與 `check_regex` 會清掉。
- `branch_prefix`：同時改 `BRANCH_PREFIX`（workflow 的分支名）並加進 `ALLOWED_BRANCH_PREFIXES`。
- `pr_size`：`null` 或 0 表示不限。
- `sync_strategy`：分支落後 main 時怎麼跟上，`auto`（預設）、`rebase`、`merge`、`transit`，寫進 profile 的 `conventions.sync.strategy`。
- `overrides`：深層合併進 profile，可以改任何欄位。
- `main_session_push_merge`：你既有的 skill 或習慣會不會在主 session 直接 push main、合併 PR。`true` 時 `guard.config.json` 的 `main_session_git_rules`、`main_session_github_rules` 設成 false（見〈套用到既有專案〉）；不寫或 `false` 維持預設。互動模式最後也會問這一題。
- 訪談的鍵（1.0）：`models`（模式字串或物件）、`scrub`、`knowledge`、`links`、`deliverables`、`ci`、`parallelism` 原樣合併進 `methodology.json` 的同名鍵；`affected_tests_only`（布林）寫成 `stages.build.affected_tests_only`；`guard`（物件）合併進 `guard.config.json`；`auto_merge`（布林）寫成 `auto_merge.enabled`；`hooks`（`plugin`／`project`，命令列的 `--hooks` 優先）。

優先順序：答案檔 > 互動回答 > workflow.config 的 `METHODOLOGY`；`--defaults` 且沒有答案檔時一律用 default。合併後的結果先用 schema 驗，再寫成 `.claude/teams/methodology.json`（已存在時保留專案自己的那份，`--force`、`--upgrade` 也不覆寫；要整份換掉加 `--overwrite-user-files`），最後跑 awf build。

### 訪談：先偵測、再確認、可重跑（1.0）

- **偵測**：`awf init --detect --target <專案> [--json]` 只印、不寫任何檔。它只讀固定幾個小檔（`package.json`、`Cargo.toml`、`go.mod`、`pyproject.toml`、`Makefile`、lint 設定檔名、`.github/workflows/` 的檔名、`openspec/`、文件目錄）與 git 的唯讀查詢（近 50 筆 commit 標題、分支名、主線分支），不執行專案的任何程式、不讀機敏檔。輸出依主題列：要確認什麼、答案檔的鍵、偵測到什麼與依據、建議的答案。
- **偵測到的只是建議**：`--defaults`、`--answers` 不採用偵測值；互動模式把它當那一題的預設，由你確認。
- **主題**：開發規範、慣例、需求來源、限制文件、模型分級、讀取預算、平行與拆分、去客戶化掃描、知識庫與知識圖、連結、交付文件、專案的 CI、build 修正迴圈、自動合併、主 session 的習慣、hook 註冊方式、守門設定。限制類的功能（讀取預算、去客戶化掃描、連結強制、交付文件、CI、自動合併）預設都不啟用。
- **對照表**：寫入前印「設定｜偵測到｜你的回答｜會寫成」。互動模式要你答 y 才寫；`--defaults`、`--answers` 不問但照印。
- **答案檔**：這次的答案存成 `.claude/teams/init-answers.json`（鍵排序、像機敏值的字串略去）。它只是紀錄，流程不讀它。
- **改設定**：`awf init --target <專案> --reconfigure [--answers <檔>]`。以上次的答案當預設；`--answers` 只寫要改的鍵（值寫 `null`＝拿掉那個答案）。只把「答案有變」造成的差異套到現有的 `methodology.json` 與 `guard.config.json`，你手改過的其他鍵不動；套完驗 schema，不過就不寫。不能和 `--upgrade`、`--force`、`--overwrite-user-files`、`--with-*` 一起用。
- **只重問一個主題**：`awf init --target <專案> --reconfigure <主題>`（或 `--reconfigure=<主題>`；主題 id 見 `awf init --detect`）。只問那個主題的題目，其他主題不問、不動；搭配 `--answers` 時答案檔只能有那個主題的鍵（有別的鍵就拒絕，不會默默略過）。可以單獨重問的主題：`requirements`、`models`、`scrub`、`links`、`ci`、`build_loop`、`auto_merge`、`hooks`、`knowledge`、`deliverables`、`parallelism`、`guard`、`main_session`；`methodology`、`conventions`、`constraints`、`read_limits` 的題目互相有關，要問一整輪。
- **互動問答最後幾題**（接在 hook 註冊方式後面，全部 Enter＝不寫任何答案）：知識圖三題（要不要建＝`knowledge.auto.update`；提問時要不要帶位置＝`knowledge.auto.prompt`，預設不帶；別的 repo＝`knowledge.repos`，候選是專案同一層目錄的 git repo 與需求來源指到的工作區外路徑，不自動加，id 由目錄名產生，收進來的 repo 對 team agent 唯讀）、交付文件一題（profile 有文件清單、專案沒有自己的 `deliverables.json` 時才問要不要啟用）、平行與拆分兩題（`split_threshold`、`max_sub_plans`）、守門設定三題（`protected_branches`、`acceptance_test_dirs`：不能清空；文件目錄：和 run 目錄、簡報目錄合成 `writer_dirs`，只收工作區裡的相對路徑，不能在 `.claude`、`.github`、`.git` 底下）。受保護分支與文件目錄的預設值取自佔位符 `PROTECTED_BRANCHES`、`DOCS_DIRS`（`workflow.config`；預設 `main,master`、`docs`），所以互動模式不在佔位符那一輪重複問。`--detect` 的 `knowledge` 主題會列 `sibling_repos`、`requirements_outside`、`graph`，`guard` 主題會列 `default_branch`（不在 main／master 時）與 `acceptance_dirs`，並給只會加嚴的建議答案。

### 需求來源和 merge_gate 共用

`awf merge-gate` 讀需求清單的順序：`guard.config.json` 的 `requirements` 有設 `path` 或 `command` 時以它為準（auto_merge 的設定走 PR＋CODEOWNERS，所以優先）；沒設時讀 `methodology.json` 的 `requirements`；都沒有就只能靠 `--requirements`，仍沒有就判 hold。CI 範本（`agent-merge-gate.yml`）從 base 分支 checkout 後跑同一支 gate，讀的也是 base 分支上的這兩個檔。

### 需求來源用規格層（`source: "openspec"`）

沒有選 `openspec` 時，這一節的功能完全停用，判定與輸出和原本一樣。

```json
"requirements": {
  "source": "openspec",
  "path": "openspec",
  "change": "refund",
  "section_map": {"不做的事": ["Non-Goals", "先不碰"]}
}
```

| 鍵 | 意思 |
|---|---|
| `path` | 規格根目錄。相對路徑從專案根目錄算；規格放在另一個 repo 時寫絕對路徑。不能有 `..`。沒寫用 `openspec` |
| `change`（選填） | 這個需求對應 `changes/` 底下哪一個變更。沒寫時：`awf save-run` 依序試 run 的 `args.change`、epic 名稱；`awf merge-gate` 可以用 `--requirements-change` 指定，都沒有而且進行中的變更剛好一個就用它，超過一個判 hold |
| `id_pattern`（選填） | 同 `awf spec` 的 id 樣式 |
| `section_map`（選填） | 必要節對應到 proposal 的哪些節名。只寫要改的那幾節，沒寫的用內建對照 |

id 一律用規格層的穩定 id（`<能力>/<需求代稱>`、`<能力>/<需求代稱>#<情境代稱>`，見 `docs/規格層.md`）。需求清單＝這個變更的差異檔碰到的需求，驗收條件＝它們的情境。

**intent**：plan 段把變更的 `proposal.md` 當成 intent，不另外要 `intent.md`。內建對照：

| 必要節 | proposal 的節名（任一個有就算） |
|---|---|
| 目標 | `Why` |
| 範圍 | `What Changes` |
| 不做的事 | `Non-Goals`、`Non Goals`、`Out of Scope` |
| 驗收條件 | `Acceptance Criteria`、`Success Criteria`，或變更的差異檔裡有情境（寫成 `@scenarios`） |

對不到的節算缺，和 `intent.md` 缺節一樣判 invalid。plan_mode 專屬的節用同名對照，要別的節名就寫在 `section_map`。

**design 存檔**（`awf save-run stage design`）會檢查，問題記在 `spec_issues`：

- `awf spec validate` 對這個變更有問題、或有待確認的 id。
- 子任務的 `spec_refs` 每一筆都要是找得到的 id（現行規格加上這個變更的差異）。
- 子任務的 `acceptance` 開頭是 `<能力>/…` 形狀的 id 時，要找得到。
- 這個變更的每一條（需求或情境）都要有子任務的 `acceptance` 對應（開頭寫它的 id 或它所屬需求的 id）。

**test 存檔**：每條驗收條件的 id 用同一組 id，對不上的、以及變更裡沒被驗到的情境都列出來。

有 `spec_issues` 時，`awf save-run approve --by policy` 用現在的規格重算一次（不採信 run.json），還有問題就拒絕；人工核准只印警告。規格目錄打不開時算一個問題（gate 只會更嚴）。

**規格基準**：規格檔在工作目錄裡，寫程式的 agent 改得到。只照「現在的規格」檢查的話，把沒過的情境從差異檔刪掉檢查就過了，所以核准時會把規格當下的樣子記下來，之後都和它比：

| 什麼時候 | 記什麼、比什麼 |
|---|---|
| plan 核准 | 記進 `run.json` 的 `stages.plan.approved.spec`：變更名稱、`proposal.md` 的 sha256、差異檔（`changes/<名>/specs/**`）每個檔的 sha256、條目清單（穩定 id → 標題） |
| design 存檔、政策核准 | 和 plan 的基準比：proposal 改過、條目變少、id 對到別的條目算問題。差異檔的內容不比（那是 design 段在寫的） |
| design 核准 | 同樣的內容記進 `stages.design.approved.spec` |
| test、deliver 存檔與政策核准，`awf publish`（政策核准的段），`awf merge-gate --recipe <run.json>` | 和 design 的基準比（recipe 沒有 design 段就用 plan 的）：變更換了、proposal 改過、條目變少、id 對到別的條目、差異檔有任何一個新增／刪除／內容不同，都算問題。該有基準卻沒有也算 |

- 問題和其他規格檢查一樣記在 `spec_issues`：政策核准不過，人工核准只警告；merge gate 判 hold。
- **要修訂規格，重跑 design 段**：重存 design 會清掉 design 的核准（基準跟著清掉），重新核准時記新的基準，後面各段照既有規則重跑。plan 之後要改 proposal 則重跑 plan。
- `ids.json` 不整份釘住（別的變更歸檔時它本來就會變）；釘的是「這次變更的每個 id 對到哪一條」。改 `ids.json` 讓某個 id 消失或對到別的標題，會被上面的比對抓到。
- 基準放在核准紀錄裡，所以重存該段、`escalate` 把該段改成 stale 時會一起清掉。

`awf merge-gate` 用同一個來源：需求清單取自變更的差異檔，規格檢查沒過、沒有變更、清單是空的都判 hold。`guard.config.json` 的 `requirements` 有設 `path` 或 `command` 時仍以它為準。清單讀的是執行 gate 那個目錄的檔案：本機靠上面的基準（要帶 `--recipe <run.json>`），CI 靠受保護的 base 分支，差別見 `docs/自動合併信任模型.md` 第 10 節。

目前的限制：`awf pack build` 的子任務資料包還不認得規格層的 id（`spec_refs` 寫穩定 id 時會記 `spec_ref_errors`）。

### 連結（`links`）

profile 沒有 `links` 物件時，帳本不寫、檢查不做，輸出和原本一樣。寫成 `"links": {}` 就啟用（只提醒）；`"links": {"enforce": true}` 是連結不齊不能政策核准。

**帳本**：`awf save-run stage` 每存一段，把這一段宣告的連結附加到 `<runs_dir>/links.jsonl`，一行一筆，格式在 `.claude/teams/schemas/link.schema.json`：

```json
{"from":{"id":"orders/申請退款#七天內","type":"ac"},"kind":"ac_spec","op":"add","run":"20261114-sdlc-refund","schema_version":1,"source":"design.json:subtasks[t1].spec_refs","stage":"design","strength":"strong","to":{"id":"orders/申請退款","type":"spec"}}
```

- 只附加、不改寫。同一段重存而連結一模一樣時不寫；有變時先寫一筆 `{"op":"supersede","run":…,"stage":…}`，再寫新的。讀的一方看到 supersede 就把這個 run 這一段先前的連結作廢。
- 寫入失敗只警告，不影響存檔。閘門不讀這個檔。
- team agent 不能寫這個檔（守門規則），只有主 session 跑 `awf save-run` 會寫。
- id、目標與出處的字出自 agent 交的結果，寫入前會清理：控制字元（含換行）換成空白，反引號與角括號拿掉，超過 200 字截短。

**檢查**：design、test、deliver 存檔時，從 `design.json`、`build.json`、`test.json`、`run.json` 算每條驗收條件有沒有對到規格小節、檔案、測試、commit，缺的記在 `link_gaps`。它不讀帳本。design 段只看有沒有宣告（還沒有東西可以對）；test 段起核對宣告的東西是不是真的：

| 環節 | 怎樣才算有 |
|---|---|
| 規格小節 | 子任務有 `spec_refs`，或驗收條件的 id 就是規格層的條目 id |
| 檔案 | 子任務 `owns` 至少有一個檔在 build（與 test 段修正）回報的 `files_changed` 裡，或 repo 裡真的有這個檔。絕對路徑、含 `..` 的不算。recipe 沒有 build 段時只看有沒有寫 `owns` |
| 測試 | test 段這一條的驗證指令不是空操作。空字串、`true`、`:`、`echo …`、`printf …`、`exit …`、`sleep …`，以及結尾是 `\|\| true` 這類寫法都不算 |
| commit | test 段這一條記的 commit 是 40 碼十六進位，而且 test 段每一份逐條結果（彙整的與各分片的）記的是同一個 |

另外這幾種情況直接算缺口：

- 這個 run 有 design、build、test 段，而 `design.json`、`build.json`、`test.json` 讀不到或不是物件（讀不到不等於沒有缺口）。
- 需求來源是 openspec、變更有條目，而某個子任務完全沒有 `acceptance`。
- 整份 design 沒有任何可辨識的驗收條件 id（沒有東西可以連，不能算齊）。

| `links.enforce` | 有缺口時 |
|---|---|
| 沒寫或 `false` | 存檔與核准時印「連結檢查」提醒，政策核准照舊 |
| `true` | `awf save-run approve --by policy` 重算，還有缺口就拒絕；人工核准只印警告 |

**保證什麼、不保證什麼**：

- 保證：通過時，每條驗收條件在 design 對得到規格小節，`owns` 至少有一個檔是 build 回報改過的或 repo 裡有的，test 段有一條不是空操作的驗證指令，而且 test 段記的是同一個 40 碼的 commit。
- 不保證：那個檔的內容真的實作了這一條；那條指令真的驗了這一條（空操作清單只擋最明顯的寫法，`test -n x`、跑一個和這一條無關的測試都擋不到）；那個 commit 真的存在、就是分支的 HEAD（合併前由 `awf merge-gate --reviewed-sha` 對 PR 的 head 把關）。
- build 與 test 的結果是 agent 交的。這個檢查核對的是它們彼此一致、和 repo 對得上，不能取代 test 段的驗證與人的審查。

### 改了 profile 之後

workflow 不能讀檔，所以 profile 要內嵌進腳本。0.5 起這件事由 `awf next` 做：每一段開跑前，它用 plugin 的範本加專案的 `.claude/teams/methodology.json` 產生 `<run_dir>/.wf/<名>.js`。**改了 profile 不用再跑任何指令**，下一段就生效；進行中的段用的是開跑當下的那一份。

只有用了覆寫檔（見下）才要自己重跑 `awf build`（`--check` 驗證一致）。

範本裡沒有 profile 時（模版 repo 本身），標記保留 `null`，workflow 改用中性指引（依目標 repo 既有慣例），測試時機沿用測試先行。

### build 分波

子任務可以標 `wave`（正整數，沒標算第 1 波）。sdlc-build 會把同一波做完、合進整合分支，才做下一波；波次裡面照相依分層平行。

- 用在想先打地基、或想分段確認的時候。多數需求不用標。
- 子任務不能依賴比自己晚的波次，交件時就會被擋。
- `parallelism.wave_pause: true` 時，每做完一波停下交人；確認後 `awf next --retry` 續跑，只做剩下的波次。預設不停。

### 自訂腳本（`awf next --script`）

標準的 `sdlc-*.js` 排不出你要的流程時，可以為 **design、build、deliver** 段寫一支自己的腳本：

```bash
awf next --run <run_dir> --script scripts/my-build.js
```

腳本只寫流程。`awf` 會檢查它，再接上執行核心、pattern 庫與這一段的參數，產生 `<run_dir>/.wf/custom-<段>.js`。派工單的共同前綴和內建範本一樣：限制文件、知識圖的查圖指示（圖開得起來才有）、profile 裡可調的字都會帶上。

```js
export const meta = { name: 'my-build', description: '分兩波打地基' }
const SUBTASKS = /*@schema:subtasks*/ null /*@end*/
const waves = [['t1'], ['t2', 't3']]
for (const wave of waves) {
  const r = await awfFanOut(wave.map((id) => ({ prompt: `${awfPrefix()}\n做子任務 ${id}`, label: `Implement:${id}`, agentType: NS + 'dev-implementer', schema: SUBTASKS })), { max: 4 })
  if (r.halted) return { stage: 'build', halted: true, halt_reason: r.reason, missing: r.missing, recipe: RECIPE, trace: awfTrace() }
}
return { stage: 'build', halted: false, recipe: RECIPE, trace: awfTrace() }
```

可以直接用的名字：`A`（這一段的參數）、`NS`、`METHODOLOGY`、`RECIPE`、`awfAgent`、`awfTrace`、`awfPrefix`、`layerByDeps`，以及六個 pattern。

| pattern | 函式 | 上限（`max`）管什麼 |
|---|---|---|
| Fan-out & synthesize | `awfFanOut(jobs, { max, synth })` | 派工單數 |
| Classify & act | `awfClassifyAct(items, { max, classify, pick, routes, fallback })` | 要分類的項目數 |
| Adversarial verification | `awfAdversarial(lenses, { max, quorum, refuted })` | 反駁者數 |
| Generate & filter | `awfGenerateFilter({ max, generate, key, keep })` | 候選數 |
| Tournament | `awfTournament(entries, { max, judge, pick })` | 參賽作品數 |
| Loop until done | `awfLoop({ max, step, done })` | 輪數 |

每個 pattern 都要給 `max`，沒給會丟錯誤。超過上限、有 agent 沒交件、跑滿輪數還沒完成，都回 `halted: true` 與原因，由腳本停下交人。

檢查不過就不執行。會被擋的寫法：

- 直接用 `agent()`、`tryAgent()`，或呼叫別的 workflow。
- `agentType` 不是 `NS + '<角色>'` 或完整字串，或不是登記過的角色。`dev-merge-steward` 不能派。
- `while`、`do`，或沒有條件與遞增的 `for`。
- 有 `return` 沒帶 `trace: awfTrace()`。
- 重新定義或改寫執行核心的名字，或用 `eval`、`Function`、`import`、`require`。
- 正規式字面值（`/…/`）、字串外的反斜線、`constructor`／`__proto__`／`prototype`。要比對文字請用字串方法。

閘門不因為自訂腳本放寬：

- 存檔時的檢查和標準腳本一樣：recipe 要求的角色要在 trace 裡交件、紀錄檔要齊、模型不能低於下限、recipe 要和 run.json 一致。
- 腳本內容會被包成一個函式執行：`agent`、`tryAgent` 與核心的內部狀態在裡面拿不到；回傳的 `stage`、`recipe`、`trace` 由外層覆寫，trace 一律取自執行核心。
- 執行時再擋一次：派白名單以外的 agent 會直接失敗；派工數到上限就停。
- 自訂腳本跑的段**不能政策核准**，一律由人核准。閘門重點會列出用了哪支腳本。
- plan、sync、test、merge 不開放：這幾段的確定性核對寫在標準腳本裡，merge 是信任邊界。

靜態檢查是幫你早點發現寫錯，它擋不住所有寫法；把關靠的是上面四條。

另外兩種情況也一律由人核准，不能政策核准：

- 這一段用的是專案的覆寫檔（`.claude/workflows/<名>.js`）或舊副本，不是 plugin 的範本。
- 這一段的結果是用 `awf done --output <檔>` 手動給的。

### 覆寫 workflow

要改某一支 workflow 的流程（不只是 profile 的參數）時，用覆寫檔，不要改 plugin：

```bash
awf init --target . --upgrade --with-workflows   # 在 .claude/workflows/ 放 12 支，結尾帶「// awf-override: <版本>」
```

- 只留你要改的那幾支，其餘刪掉（刪掉的繼續用 plugin 的範本，跟著 plugin 更新）。
- `awf next` 看到結尾有 `// awf-override: <版本>` 的同名檔就用它；標記的版本和 plugin 不同時會警告，提醒你對一下 plugin 這版改了什麼。
- 沒有這個標記的同名檔不會被採用：那是 0.4 以前 init 複製的副本，`awf init --upgrade` 會移除沒改過的，改過的保留並列出來，由你決定要不要加標記變成覆寫檔。
- 覆寫檔改了 profile、schema 或片段要自己跑 `awf build`。
- team agent 不能寫 `.claude/workflows/` 與 run 目錄的 `.wf/`（hook 擋），腳本只由人或主 session 改。
- 過閘門的條件和用範本時一樣：`awf save-run stage` 照樣驗信封、trace、紀錄與 recipe。

## 12. 套用到既有專案

`awf init` 可以直接套用到已經有 `.claude/`、`CLAUDE.md`、CI 的專案。原則是**只新增模版自己的檔案，使用者的檔案不覆蓋**；使用者原本的 agent、skill、command 與設定都照常能用。

### 會新增哪些檔

- `.claude/teams/`：rules、schemas、methodologies、golden-set、`guard.config.json`、`methodology.json`、`VERSION`（套用的模版版本）、`workflow.config`（這次的佔位符值，`--upgrade`、`--force` 沒給 `--config` 時沿用），以及 `agent-workflow.CLAUDE.md`（模版的工作流程說明，見下）。
- workflow **預設不放**（由 `awf next` 用 plugin 的範本逐段產生）。加 `--with-workflows` 才在 `.claude/workflows/` 放 12 支覆寫檔。
- `--hooks project` 時不放檔案，只在專案的 `.claude/settings.json` 註冊 `awf hook`（寫入執行檔的絕對路徑）。工具也不放進專案：`awf` 由 plugin 的 `bin/` 提供。
- run 目錄（`{{RUNS_DIR}}/README.md`）、`.mcp.json.example`。
- `.github/workflows/agent-merge-gate.yml` **預設不放**，加 `--with-merge-gate` 才放：沒有設好 gate App 時它會讓每個 PR 失敗。

### 不會動哪些檔

| 檔案 | init 的做法 |
|---|---|
| `.claude/agents/`、`.claude/skills/`、`.claude/commands/` | 一律不碰（模版的 agent、skill、command 由 plugin 提供，不複製進專案）。 |
| `CLAUDE.md` | 不覆蓋。模版內容寫成 `.claude/teams/agent-workflow.CLAUDE.md`，再在 `CLAUDE.md` 結尾追加兩行：一行註解標記、一行 `@.claude/teams/agent-workflow.CLAUDE.md`（Claude Code 的 import 語法）。已經引用過就不再追加，重跑 init 不會重複。換行字元沿用原檔（CRLF 的檔案追加的也是 CRLF）。 |
| `.claude/settings.json` | 深度合併：使用者已有的值一律保留（`permissions.allow` 這類清單也不改），只補上模版有、使用者沒有的鍵；`hooks` 依事件合併，使用者自己的 hooks 原樣保留，`awf hook` 的每個模式（guard-shell、guard-paths、envelope）只註冊一次，重跑時就地更新指令（例如執行檔換了位置）。不是合法 JSON 時不動，印提示請你手動補。 |
| `.mcp.json`（`--with-mcp`） | 同上，深度合併。 |
| `.claude/workflows/`、`.claude/hooks/`、`.github/workflows/` 裡的同名檔 | 內容看得出是模版產生的（含 `agent-workflow`、`agent-merge-gate` 或 `/*@schema:` 標記）才當成模版檔；否則當成使用者的檔案保留，列在「保留 N 個使用者的檔案」清單。 |

`--force` 只覆蓋模版自己的檔案；你的設定照〈升級已 init 的專案〉的規則保留（`methodology.json`、`guard.config.json`、rules.md 的〈專案規則〉、CLAUDE.md 的〈專案特定〉不整份覆寫）。上表的使用者檔案即使加 `--force` 也照上表處理，不整份覆蓋。真的要整份換成模版版本，另加 `--overwrite-user-files`。分成兩個旗標的理由：更新模版是常做的事，重設使用者檔案很少做而且不可逆，不該被同一個旗標順手帶上。更新已 init 的專案建議用 `--upgrade`，見下一節。

### 命名空間怎麼避免衝突

- plugin 的 agent、skill、command 都帶 `agent-workflow:` 命名空間（例如 `agent-workflow:dev-implementer`、`/agent-workflow:brief`），不會覆蓋使用者同名的東西。使用者自己有 `/brief` 時，打 `/brief` 用的是使用者的版本，plugin 的版本用 `/agent-workflow:brief`。
- 守門 hook 只把「命名空間在 `team_agent_namespaces`（預設 `["agent-workflow:"]`）而且角色名以 `team_agent_prefixes`（`dev-`、`tpm-`）開頭」的 agent 當成模版角色。使用者自己的 `.claude/agents/dev-helper.md`（agent_type 是沒有命名空間的 `dev-helper`）不套角色規則：可以 push 功能分支、寫任何檔、交件不需要信封，規則和主 session 一樣。
- 例外：角色名和 plugin 的模版角色**完全相同**（`dev-implementer`、`tpm-writer` 等 14 個核心角色，加上 2 個舊名，共 16 個，見 `crates/awf-core/src/config.rs` 的 `RESERVED_ROLES`）的 agent，不論有沒有命名空間都套模版角色規則（fail-closed）：它多半是模版 agent 的複本，或是冒用模版角色名。所以自己的 agent 不要取和模版角色一樣的名字；合併、寫凍結檔仍比對完整 agent_type，冒用不會因此放行。
- 想讓沒有命名空間的 `dev-*`／`tpm-*` 也套模版角色規則（舊版行為），在 `team_agent_namespaces` 加空字串：`["agent-workflow:", ""]`。agent 放在專案 `.claude/agents/`、`AGENT_NS` 設成空字串時，init 會自動填 `[""]`。
- `auto_merge.merger_role`、`freeze_writers` 比對完整 agent_type，也要是模版角色；使用者的同名 agent 不能合併、不能寫凍結檔。

### 主 session 的開關

使用者自己的 skill 在主 session 跑。有 `guard.config.json` 時，主 session 預設也不能 push 受保護分支、不能 `gh pr merge`、不能核准、`gh` 寫入要帶 `--repo`。如果你的 skill 或習慣本來就會在主 session 直接 push main、合併 PR：

- init 問答會問「你既有的 skill 或習慣會不會在主 session 直接 push main、合併 PR？」，答會（或答案檔寫 `"main_session_push_merge": true`）時，把下面兩個鍵設成 false。`--defaults` 兩個都維持 true。
- 也可以事後自己改 `guard.config.json`：
  - `main_session_git_rules: false`：主 session 不檢查分支前綴、force push、`--no-verify`、push 受保護分支。
  - `main_session_github_rules: false`：主 session 可以 `gh pr merge`、`gh pr review --approve`、用 REST 合併或核准，`gh` 寫入不必帶 `--repo`。
- 例外（不論開關）：上游與禁止的 repo 一律擋；`auto_merge.enabled` 為 true 時，主 session 一律不能合併、核准、直接 push 受保護分支（信任模型要求合併只走 merger_role＋gate）。agent 的限制不受這兩個開關影響。

### 升級已 init 的專案

plugin 與專案裡的 scaffold 檔案分開更新。新版發佈後依序做：

1. **更新 plugin**：`claude plugin update agent-workflow@agentworkflow`，或在 `/plugin` 介面更新。只跑 `/plugin marketplace update agentworkflow` 只會更新目錄清單，不會更新 plugin。
2. 在 Claude Code 裡執行 `/reload-plugins` 載入新版。
3. **更新專案的 scaffold**，在每個已 init 的專案跑：

   ```bash
   awf init --target . --upgrade
   ```

4. 看 `--upgrade` 列出的「profile 缺少的新欄位」，要採用時加 `--adopt-new-fields` 再跑一次：

   ```bash
   awf init --target . --upgrade --adopt-new-fields
   ```

5. 跑 `awf render --all --out _tpm/wf-check` 確認腳本產生得出來，再照 `CHANGELOG.md` 該版的〈升級步驟〉處理破壞性變更（例如舊角色名改新名）。

`--upgrade` 做什麼：

| 檔案 | 做法 |
|---|---|
| 模版檔（`.claude/teams/` 的 schemas、methodologies、golden-set，模版產生的 workflow） | 一律換成這版，包括你改過的；要保留的修改先 commit，再用 git 比對 |
| `.claude/teams/methodology.json` | 不動。列出這版內建 profile 新增、你的 profile 還沒有的欄位與預設值；加 `--adopt-new-fields` 才補進去，只補缺的，既有值永遠不改，補完驗 schema |
| `.claude/teams/guard.config.json` | 你的值一律保留，只補上這版新增的鍵；說明文字 `_說明` 換成新版 |
| `.claude/teams/rules.md` | 「## 專案規則」段（含 correct skill 維護的對照表）之後保留，前面的通用規則更新 |
| `CLAUDE.md`（init 產生的）與 `.claude/teams/agent-workflow.CLAUDE.md` | 「## 專案特定」段之後保留，前面更新 |
| 使用者的檔案（自己寫的 `CLAUDE.md`、`settings.json`、`.mcp.json`、非模版的同名檔） | 照〈不會動哪些檔〉處理 |

兩個記錄檔：

- **`.claude/teams/VERSION`**：套用的模版版本，內容等於 plugin 的 `plugin.json` 的 `version`。`--upgrade` 會顯示「舊版 → 新版」。有模版檔沒更新到時（例如沒加 `--upgrade` 也沒加 `--force` 重跑），init 不寫 VERSION，避免謊報版本。
- **`.claude/teams/workflow.config`**：init 時用的佔位符值。`--upgrade`、`--force` 沒給 `--config` 時都沿用它，不再詢問；只有給了 `--config`、值本來就取自它、或還沒有這個檔時才會重寫；佔位符的值要改，就改這個檔或另給 `--config`。

`--upgrade`、`--force`、`--overwrite-user-files` 的差別：

| 旗標 | 模版檔 | 你的設定（methodology、guard.config、〈專案規則〉、〈專案特定〉） | 使用者的檔案 |
|---|---|---|---|
| `--upgrade` | 更新 | 保留，只補新鍵；列出 profile 新欄位 | 不整份覆寫 |
| `--force` | 更新 | 保留規則和 `--upgrade` 相同 | 不整份覆寫 |
| `--overwrite-user-files` | 更新 | **整份覆寫** | **整份覆寫** |

`--overwrite-user-files` 只在想重設時用；要換 profile 時搭配 `--answers`。

### 怎麼移除模版

1. 刪掉 `CLAUDE.md` 結尾那兩行（`<!-- agent-workflow：… -->` 與 `@.claude/teams/agent-workflow.CLAUDE.md`）。
2. 刪掉 `.claude/teams/`、`.claude/workflows/` 裡模版的覆寫檔或舊副本（看檔頭的 `const NS =` 與 `/*@schema:` 標記）、run 目錄的 README.md；用過 `--hooks project` 的話刪掉 `.claude/hooks/` 裡的 awf 檔案（1.0 以前的版本才有），並從 `.claude/settings.json` 的 `hooks` 拿掉指令含 `awf hook` 的項目。
3. 放過 merge gate CI 的話刪掉 `.github/workflows/agent-merge-gate.yml`。
4. 在 Claude Code 跑 `/plugin uninstall agent-workflow@agentworkflow`。
init 合併進 `settings.json` 的權限（`permissions.deny` 等）如果不需要，也一併刪掉；用 git 比對 init 前後最清楚。
