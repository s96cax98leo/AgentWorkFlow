# 自訂與擴充

怎麼依專案調整、怎麼加新的 agent、skill、hook、workflow，以及改語言、接 MCP。

先分清楚改的是哪一層：

| 要改的 | 位置 | 影響範圍 |
|---|---|---|
| agent、skill、command、hook | 本 repo 的 `plugin/` | 所有裝了 plugin 的專案（改完要更新 plugin） |
| 硬規則、workflow、schema、工具 | 目標專案的 `.claude/teams/`、`.claude/workflows/` | 只有這個專案 |
| 守門設定 | 目標專案的 `.claude/teams/guard.config.json` | 只有這個專案 |
| 專案說明、MCP | 目標專案的 `CLAUDE.md`、`.mcp.json`（或 `.mcp.json.example`） | 只有這個專案 |

想讓所有專案都拿到的改動，改 `plugin/` 或 `scaffold/`；只對一個專案有意義的，改那個專案自己的檔案。

## 1. 專案規則

`init.py` 產生的 `.claude/teams/rules.md` 有一段「## 專案規則」，放這個專案專屬的規則：

- 目標 repo（`{{REPOS_DIR}}` 下哪幾個是可以開發的 clone）
- 禁區（`{{FORBIDDEN_REPOS}}`）
- 審查規則（目標 repo 自己的 `REVIEW.md`、分支規範）
- 設計系統 skill 名稱（`{{DESIGN_SYSTEM_NAME}}`）
- 本機驗證指令（integrator、verifier 用的 verify 指令）

通用規則（先 plan 後動手、不可逆停下、機敏檔、信封……）不要在專案裡刪；要放寬就在專案規則裡寫明例外與核准者。

## 2. 守門設定

設定讀專案的 `.claude/teams/guard.config.json`（`init.py` 從 `guard.config.json.tmpl` 產生）。hooks 有兩種裝法，**二選一，不要同時用**：

| 模式 | 怎麼裝 | hooks 由誰註冊 |
|---|---|---|
| plugin（預設） | 安裝 plugin，`init.py` 不加 `--hooks` | `plugin/hooks/hooks.json`；專案 `settings.json` 不放 hooks |
| project | `init.py --hooks project` | hooks 複製到專案 `.claude/hooks/`，由專案 `settings.json` 註冊；這時不要再啟用 plugin 的 hooks |

`guard.config.json` 的主要欄位（清單欄位可寫 JSON 陣列或逗號分隔字串，空字串表示不設定）：

| 欄位 | 意思 |
|---|---|
| `runs_dir`、`briefs_dir` | run 目錄、任務單目錄 |
| `repos_dir` | 我方 clone 所在；空字串表示工作區本身就是目標 repo |
| `upstream_repos` | 上游 repo，禁止任何寫入 |
| `fork_repo` | 我方 fork；gh 寫入動作要明確帶 `--repo` 指向它 |
| `forbidden_paths` | 任何角色都不能寫的路徑 |
| `allowed_branch_prefixes` | 允許的新分支前綴 |
| `writer_dirs` | `tpm-writer` 可以寫的目錄 |
| `task_id_prefix`、`task_authority` | 任務編號前綴與發編號的系統，用來檢查「不自編編號」 |
| `attribution_line` | commit 結尾署名行 |
| `main_session_git_rules` | 為 true（預設）時，分支前綴、不 force push、不 `--no-verify`、不直接 push 受保護分支也套用到主 session |
| `main_session_github_rules` | 為 true（預設）時，主 session 也不能 `gh pr merge`、核准、用 REST 合併或核准，`gh` 寫入要帶 `--repo`；設 false 放行。`auto_merge` 啟用時主 session 仍不能合併、核准，上游一律擋（見〈套用到既有專案〉） |
| `team_agent_namespaces` | 哪些命名空間的 `dev-*`／`tpm-*` 算模版角色，預設 `["agent-workflow:"]`；加 `""` 讓沒有命名空間的同名 agent 也算（舊行為） |
| `acceptance_test_dirs` | 驗收測試目錄（預設 `tests/acceptance`、`e2e`，工作區或 repo 內任一層的相對路徑）；dev-implementer 不能寫，驗收測試由 dev-acceptance-tester 寫 |
| `auto_merge` | 自動合併，預設關閉。各鍵（白名單、`merger_role`、`daily_cap`、風險門檻、`carry_verdict_on_rebase`、`allowed_skipped_checks` 等）見 `docs/自動合併信任模型.md` 第 5 節 |
| `extension_agents` | 使用者加進 workflow 的自己的 agent：`{"完整 agent_type": "套用哪個模版角色的規則"}`，只能對應唯讀類角色，其他值改套 `tpm-reviewer`（見〈把自己的 agent 加進 workflow〉） |
| `role_map`（內建預設，可覆寫） | agent 名稱對應到目標 repo 自己 guard 的角色名 |

`guard-paths` 也擋 Read、Grep 讀機敏檔（`.env`、金鑰、憑證；`.env.example` 這類範例檔放行），主 session 也擋。權限層的 deny 規則（例如預設擋 `Read(**/*.key)` 這類機敏檔）在 `.claude/settings.json`；專案真的需要放寬時，見 `scaffold/.claude/settings.README.md` 的「如何放寬讀取限制」：優先在 `settings.local.json` 只放行單一檔案；`.env` 和 `*.pem` 不放寬。

沒有設定檔時只套用角色規則（`agent-workflow:` 命名空間下的 `tpm-*`／`dev-*` 不推送、不做 gh 寫入、只寫自己的範圍），不擋主 session 與使用者自己的 agent，所以 plugin 在還沒 init 的專案也不會誤擋。兩種模式同時開會讓每個 hook 跑兩次。

hook 跑不起來（找不到 Python、逾時）時 plugin 模式放行，project 模式可以設成擋；完整的失敗語意與取捨見 [`自動合併信任模型.md`](自動合併信任模型.md)〈hook 失敗時的取捨〉。

## 3. 改輸出語言

1. 在 `workflow.config` 改 `OUTPUT_LANGUAGE`，重跑 `init.py`；或直接改專案 `rules.md` 的語言規則與 `CLAUDE.md`。
2. 語言規則要涵蓋：給決策者的回覆、派工單、agent 之間的訊息與 SendMessage、信封的 summary／open_questions／derived_work、文件、commit 內文、推播。程式識別字、指令、路徑、技術名詞保留原文。
3. 派工單本身要用新的輸出語言寫，subagent 的回覆才會跟著改。
4. 建議也寫進記憶，讓下一個 session 一開始就知道。

plugin 裡 agent 的提示是繁體中文，改輸出語言不需要改它們；提示裡已經寫「檔案、信封、訊息一律用 `.claude/teams/rules.md` 設定的輸出語言」。

## 4. 新增 agent

1. 在 `plugin/agents/` 加 `<前綴>-<角色>.md`。前綴決定守門規則：plugin 命名空間下的 `dev-*`、`tpm-*` 會套用角色寫入範圍與「不推送」規則（見 `guard.config.json` 的 `team_agent_prefixes`、`team_agent_namespaces`）。使用者放在專案 `.claude/agents/` 的 agent 沒有命名空間，不套這些規則（名字和模版角色完全相同的除外）。新增模版角色時，把名字同時加進 `plugin/hooks/awf_config.py` 的 `RESERVED_ROLES` 與 `scaffold/.claude/teams/tools/check_agents.py` 的 `CORE`（`check_agents.py` 會核對兩邊），並更新 README 等文件的角色數與名單（`tests/check_docs.py` 會核對）。
2. frontmatter 至少要有 `name`、`description`（寫清楚什麼時候派給它）、`tools`。**只讀的角色不給 Edit、Write**。
3. 本文照既有 agent 的段落：切分理由、職責、硬性約束、工作方式、交件（最後附信封與 payload 名）。
4. 要套用目標 repo 的 guard，就在 `role_map` 加對應。
5. 跑 `python3 .claude/teams/tools/check_agents.py --plugin-dir <AgentWorkFlow>/plugin` 檢查格式（agent 放專案 `.claude/agents/` 時改用 `--agents-dir`）。`check_agents.py` 檢查 16 個 team 角色（`tpm-*`／`dev-*`）：五段內文、`model: inherit`、`skills` 欄位、payload schema 這些規定只對它們成立，因為它們由 workflow 派出、要交 JSON 信封、hooks 也只把它們當 team 角色。site-report 那 6 個不交信封、不受角色寫入範圍限制，不在這支工具的範圍內；要檢查它們的 frontmatter 基本格式，另寫一支小檢查放 `tests/`，不要塞進 `check_agents.py`。
6. workflow 和 Agent 工具呼叫 plugin 的 agent 時要帶命名空間：`{{AGENT_NS}}<agent 名>`，預設 `agent-workflow:`。agent 放在專案 `.claude/agents/` 時，`AGENT_NS` 設成空字串。

### 把自己的 agent 加進 workflow（使用者用）

上面是改模版本身（所有專案都拿到）。只想讓**某個專案**的 SDLC 多一個自己的 agent（例如 migration 審查、無障礙檢查、團隊內部規範檢查、領域調研）時，不用改模版，在 Claude Code 裡跑 `/agent-workflow:add-agent`（`add-agent` skill），它會一步步問完並幫你設定。手動設定的話分三步：

1. **寫進 profile**：`.claude/teams/methodology.json` 的 `extensions` 加一筆。
   ```json
   {"name": "db-migration", "agent": "acme-db-reviewer", "stage": "test",
    "instructions": "檢查示範客戶 ACME 的 migration 能不能回滾；不能回滾列 important。"}
   ```
   - `agent`：專案 `.claude/agents/<名>.md` 的寫 `<名>`；其他 plugin 的寫 `<plugin>:<agent>`。
   - `stage`：只有四段可以加。

     | stage | 和誰平行 |
     |---|---|
     | `plan` | 調研 |
     | `design` | 一致性檢查 |
     | `test` | 驗證與設計、安全審查 |
     | `deliver` | 四軸 PR 審查，之後一樣經 skeptic 反駁 |

   - build 與 merge 不開放：build 有檔案所有權與 worktree 分工；merge 是信任邊界，只有 `dev-merge-steward` 加確定性 gate。
2. **登記守門角色**：`.claude/teams/guard.config.json` 的 `extension_agents` 加 `"acme-db-reviewer": "tpm-reviewer"`。
   - 登記後，這個 agent 的推送、GitHub 寫入、寫入範圍都照對應角色擋，交件信封也會驗證。
   - 只能對應唯讀類角色：`tpm-researcher`、`tpm-reviewer`、`tpm-skeptic`、`dev-verifier`、`dev-security-reviewer`、`dev-design-reviewer`。舊名 `dev-pr-reviewer` 已併入 `tpm-reviewer`，仍可填（相容一版），照 `tpm-reviewer` 套用。對應到其他角色（例如 merge-steward、implementer）一律改套 `tpm-reviewer`。
   - 沒登記的話，`build.py` 會拒絕內嵌：沒登記的 agent 不套任何角色規則，和主 session 一樣能 push。
3. **重新內嵌**：跑 `python3 .claude/teams/tools/build.py`。用 `check_workflows.mjs` 確認擴充 agent 會被派出，而且定義檔存在。

擴充 agent 一律交 `findings`，詳細結果寫在 `<run_dir>/ext-<name>.md`。它的 blocker／important 發現會擋住政策核准，要人決定。

## 5. 新增 skill

1. 在 `plugin/skills/<名稱>/SKILL.md`。`description` 要寫觸發情境（使用者會怎麼說）。
2. 細節放 `references/`，可重跑的腳本放 `scripts/`，SKILL.md 只放流程與指向。
3. 專案專屬的 skill（例如綁定某個 repo 的工作流程）放目標專案的 `.claude/skills/`，不要放進 plugin。

### 設計系統 skill

`plugin/skills/design-system-template/` 是骨架。為專案做一份：

1. 複製到目標專案 `.claude/skills/<設計系統名>/`。
2. 填 token（顏色、字級、間距、圓角、陰影）、元件規則、狀態色、RWD 斷點、無障礙要求、交付檢查表。
3. 在專案規則寫上設計系統 skill 名稱，讓 `dev-design-reviewer` 與 implementer 載入。

## 6. 新增 workflow（新的事件種類）

1. 複製一支 `event-*.js` 當骨架：拆工或固定角度 → 平行 → skeptic → writer。
2. `meta` 寫 `name`、`description`、`whenToUse`（含必要 args）、`phases`。
3. 檢查必要 args，缺了就 `throw`；派工單 context 要帶 run 目錄、硬規則、授權來源。
4. 每個 `agent()` 都帶 `agentType`（寫成 `NS + '<agent 名>'`，`NS` 來自 `'{{AGENT_NS}}'`）與 `schema`。schema 用 `/*@schema:<payload>*/ null /*@end*/` 標記，不要手寫。
5. 跑：
   ```bash
   python3 .claude/teams/tools/build.py          # 把 schema 內嵌進 workflow
   node .claude/teams/tools/check_workflows.mjs --agents-dir <AgentWorkFlow>/plugin/agents  # 乾跑所有 workflow
   ```
6. 乾跑走不到的分支（halted、缺件、子計劃等），在 `.claude/teams/tools/scenarios/<workflow>.mjs` 補情境（`export default` 陣列，`check_workflows.mjs` 自動載入）。
7. 在 `tpm-team` skill 的事件對照表加一列；需要 slash command 就在 `plugin/commands/` 加一支（不要和 skill 同名）。
8. 想讓所有專案都有，把 workflow 也放進本 repo 的 `scaffold/.claude/workflows/`，並加進 `tests/smoke_init.py` 的清單。

注意：workflow 腳本裡不能取時間、跑到一半不能等人輸入。日期由主 session 放進 `run_dir`；需要人決定的點，就把 workflow 拆成兩支。

**共用片段**：workflow 不能 import 檔案，多支 workflow 共用的程式放在 `.claude/teams/tools/snippets/<名>.js`，在 workflow 裡寫標記：

```js
/*@snippet:challenge*/
/*@end*/
```

跑 `build.py` 時，片段內容會內嵌在標記之間（標記保留，可重跑）；`build.py --check` 會偵測片段和 workflow 內嵌內容的漂移。內建片段：

| 片段 | 用途 |
|---|---|
| `challenge` | `tryAgent`（`agent()` 一律走它，throw 當缺件）；把 skeptic 的 verdicts 對回事項，分出保留與被推翻（預設模式同一事項任一則 refuted 就存疑）；缺件時組 halted 回傳 |
| `review-skeptic` | 審查 agent 交 findings 後派 skeptic 逐則反駁（`@requires: challenge`） |
| `layers` | 依 `depends_on` 把子任務拓撲分層，回報循環與指向不存在的相依 |

寫片段的規則：

- 只定義函式，不能有頂層 `await`，不能用 `{{佔位符}}`，也不讀 workflow 的區域變數；需要的值一律用參數傳進去。
- 片段之間有依賴時，在片段開頭寫 `// @requires: <名>`；引用它的 workflow 也要引用被依賴的片段。
- 違反以上規則時 `build.py` exit 1。改了片段要重跑 `build.py`，並確認 `tools/scenarios/*.mjs` 用到的 agent label 沒變。

## 7. 新增 payload

1. 在 `.claude/teams/schemas/payloads/<名稱>.schema.json` 定義。
2. 在 `golden-set/valid/`、`golden-set/invalid/` 各補至少一個例子。
3. 跑：
   ```bash
   python3 .claude/teams/tools/build.py --check
   uv run --no-project --with jsonschema python3 .claude/teams/golden-set/run.py
   ```
   `TASK_ID_PREFIX` 留空時，golden-set 會跳過「自編任務編號」那一例並印「略過：未設 TASK_ID_PREFIX」，不算失敗。
4. 有 schema 表達不了的規則，加在 `tools/schemalib.py` 的語意檢查，並補反例。

## 8. 新增 hook

1. 腳本放 `plugin/hooks/`，在 `plugin/hooks/hooks.json` 註冊（事件、matcher、指令用 `${CLAUDE_PLUGIN_ROOT}`）。
2. 設定值從 `guard.config.json` 讀（共用 `awf_config.py`），不要寫死專案路徑。
3. 擋下時輸出清楚的理由（用輸出語言），告訴 agent 該怎麼做才合規。
4. 在 `plugin/hooks/tests/` 補測試：一個該擋的、一個該放的，Bash 與 PowerShell 各一。hook 失敗時的語意（跑不起來放行、輸入壞掉擋、guard 壞掉用內建最小規則）由 `awf_hook.py` 統一處理，新規則寫在 `guard.py` 就會套用。跑 `python3 plugin/hooks/tests/run.py [--project <已 init 的專案>]`；不給 `--project` 時會自己在暫存目錄建一個。

## 9. 接 MCP

1. `init.py` 預設從 `scaffold/.mcp.json.tmpl` 產生 `.mcp.json.example`；加 `--with-mcp` 才產生正式的 `.mcp.json`。
2. 加 server 時，金鑰一律用環境變數引用（`${VAR}`），不要寫進檔案。
3. 給 agent 用的 MCP 工具，要在 agent 的 `tools` 列出；只讀的角色只給讀取類工具。
4. 會改變外部狀態的 MCP 工具（寄信、建立工單、改設定）算不可逆動作，要決策者當下同意，最好只在主 session 用。
5. 可選的 LLM 或 runtime（本機模型、其他雲端模型）也可以透過 MCP 或環境設定接上，但不要把特定客戶的部署細節寫進模版。

## 10. 改 slash command

`plugin/commands/*.md` 是 slash command，只有 4 支：`/sdlc`、`/brief`、`/event`、`/demo-check`。`init-workflow`、`add-agent`、`correct` 是 skill（`plugin/skills/<名>/`），用 `/agent-workflow:init-workflow` 這類完整名稱叫用；依 [Claude Code 文件](https://code.claude.com/docs/en/skills)，plugin skill 的指令名是 `/<plugin>:<skill>`，沒有其他指令同名時也可以省略前綴。不要新增和 skill 同名的 command，兩者會搶同一個名字。command 只負責把使用者的話整理成 `tpm-team` skill 的輸入，流程本身留在 skill 與 workflow 裡，避免兩邊不一致。

## 11. 自訂開發規範

模版只管工作流程（plan → design → build → sync → test → deliver → merge 與各閘門）。開發規範（TDD、DDD、SDD、spec 驅動…）與慣例（code style、commit 格式、分支命名、PR 大小、文件格式）由套用的團隊決定，寫在目標專案的開發規範 profile：`.claude/teams/methodology.json`。workflow、agent、rules.md 都只引用它；模版原本的做法收在 default profile，當成預設值與範例。

### profile 格式

schema：`scaffold/.claude/teams/schemas/methodology.schema.json`（init 與 build.py 都會用它驗）。

| 欄位 | 意思 | 誰用 |
|---|---|---|
| `name`、`description` | profile 名稱與一句話說明 | init 問答、CLAUDE.md |
| `stages.plan` | `artifacts`（產出文件）、`template`（沒有專案範本時的格式）、`guidance` | sdlc-plan、dev-spec-author |
| `stages.design` | `artifacts`、`requirement_style`（需求／驗收條件寫法）、`guidance`、`system_design`（選填，SA／SD 方法：`source`、`steps`、`feature_scope`、`system_scope`、`topics`、`document`；內建 profile 依 System Design Primer，見 [`系統設計方法.md`](系統設計方法.md)；`null`＝不套用） | sdlc-design、sdlc-design-revise、skeptic 的 coverage 與 system-design 檢查 |
| `stages.build` | `test_first`（布林：要不要先寫會失敗的測試）、`unit_tests`、`guidance` | sdlc-build、dev-acceptance-tester、dev-implementer |
| `stages.test` | `verification`（怎麼驗證）、`guidance` | sdlc-test、dev-verifier |
| `stages.deliver` | `review_axes`（審查重點補充）、`guidance` | sdlc-deliver、tpm-reviewer（deliver 模式） |
| `stages.merge` | `guidance` | sdlc-merge、dev-merge-steward |
| `stages.plan.required_sections`（選填） | intent.md 一定要有的節（標題含節名、節下有內容），省略＝目標、範圍、不做的事、驗收條件；`save_run.py stage plan` 檢查，缺節不能核准 | sdlc-plan、save_run.py |
| `recipes`（選填，工作流程分流） | 依需求類型決定走哪些段、派哪些角色：`description`、`stages`（一定含 plan；會產生改動的一定含 build、deliver、merge）、`plan_mode`、`research_angles`、`design_lenses`、`test`（`design_review`／`security_review`：never、auto、always；`modes`：verify、regression、equivalence、benchmark）、`deliver_axes`、`build_kinds`、`publishable`、`followup`、`split`、`small`。省略＝一律走 feature 完整流程 | 各段 sdlc workflow、save_run.py、publish.py、merge_gate.py |
| `modifiers`（選填） | 疊在 recipe 上、只會加嚴：`add_stages`、`research_angles`、`design_lenses`、`deliver_axes`、`test`、`split` | 同上 |
| `plan_modes`（選填） | 各 plan_mode 的 intent 另外要有的節（`sections`），覆寫內建值 | sdlc-plan、save_run.py |
| `parallelism`（選填，工作流程參數） | `split_threshold`（預估子任務超過幾個就拆子計劃，預設 8）、`max_sub_plans`（子計劃數上限，也是平行規劃與分片驗證的 agent 數上限，預設 4）、`shard_verification`（有子計劃時驗證是否分片平行，預設 true） | sdlc-design、sdlc-test |
| `models`（選填，工作流程參數） | 模型分級：`mode`（`auto`＝AI 建議、工具守下限；`fixed`＝只用 `defaults`，不採 AI 建議；`inherit`＝全部沿用主對話模型）、`tiers`（`light`／`standard`／`strong` 各對應哪個模型別名，`inherit` 表示沿用主對話模型）、`defaults` 與 `floors`（鍵是 `角色`、`角色@段` 或 `*`，值是等級） | 執行核心（目前是 sdlc-plan）、save_run.py |
| `limits`（選填，工作流程參數） | 讀取與派工上限：`mode`（`enforce` 擋、`warn` 只提醒、`off` 關閉）、`whole_file_lines`（超過幾行的檔一定要帶 offset／limit 分段讀，預設 400）、`read_budget`（每個 agent 可讀的位元組數：`default` 與 `roles.<角色>`，0 表示不限）、`max_agents`（一支 workflow 最多派幾個 agent，預設 40） | hook（guard-paths、guard-shell）、執行核心 |
| `knowledge`（選填，工作流程參數） | 知識層：`sources`（要索引的檔案 glob）、`exclude`、`dir`（索引與卡片放哪，預設 `_tpm/kb`） | kb.py、pack.py |
| `extensions`（選填，工作流程擴充） | 使用者自己的 agent 加進 plan／design／test／deliver 某一段：`name`、`agent`、`stage`、`instructions`；每個 agent 也要登記在 `guard.config.json` 的 `extension_agents` | 四段 sdlc workflow、build.py |
| `requirements` | 需求來源，格式同 merge_gate 的 adapter：`source`（json／command／spec-md）、`path`、`command`、`id_pattern` | merge_gate.py、sdlc-merge |
| `conventions.code_style` | `description`、`tool`、`command`（檢查指令，null＝沒有） | implementer、tpm-reviewer |
| `conventions.commit` | `format`、`examples`（docs／test／feat／fix 各一個範例）、`check_regex`（commit 標題要符合的正規式，null＝不檢查） | 各段派工單、`check_rules.py --git`（規則 R6） |
| `conventions.branch` | `prefix`（同 `BRANCH_PREFIX`）、`naming` | integrator、tpm-reviewer |
| `conventions.sync`（選填） | `strategy`：`auto`（預設；已跟上不動，未推送且無衝突 rebase，已推送且無衝突把 main merge 進來，有衝突走中轉分支）、`rebase`、`merge`、`transit`；固定值遇到做不到的情況（已推送卻要 rebase、有衝突卻要 merge）停下交人。`transit_naming`：中轉分支命名，可用 `<短名>`、`<base>`、`<YYYYMMDD>` | sdlc-sync、`sync_branch.py` |
| `conventions.pr_size` | `max_lines`、`max_files`（null＝不限，deliver 段就不量 PR 大小）、`scope`（怎麼量） | sdlc-deliver、sdlc-design-revise |
| `conventions.doc_format` | `format`、`notes` | 各段派工單 |

內建兩份：
- `default.json`：模版原本的做法（spec 驅動、驗收條件用 EARS 句型、測試先行、Conventional Commits 加 Story scope、修改既有檔 300 行或 15 檔），讓既有使用者行為不變。
- `lightweight.json`：範例。需求來自 issue（`requirements.source=command`）、不強制測試先行（實作後由 dev-acceptance-tester 補驗證測試）、commit 格式自由、不限 PR 大小。

`parallelism` 的效果（不是開發規範，只調整工作流程怎麼平行）：
- **規劃**：sdlc-design 先由 dev-spec-author 出大綱（payload `plan-outline`）。預估子任務超過 `split_threshold`，或有多個不共用檔案、可各自規劃的區塊時，拆成子計劃，每個子計劃一個 dev-spec-author 平行規劃（`specs/<epic>/sub/<id>/`），再由一個 dev-spec-author 彙整、核對介面與檔案所有權、統一 commit。子計劃範圍重疊、相依循環、彙整後默默少了子任務，workflow 都會 halted 停下交人。
- **開發**：sdlc-build 依子任務相依分層，同一層沒有相依的子任務各自 worktree 平行實作，每層由 dev-integrator 合併。跨子計劃的相依在彙整時展開成子任務的 `depends_on`。
- **測試與驗證**：有 2 個以上子計劃且 `shard_verification` 不是 false 時，sdlc-test 每個子計劃派一個 dev-verifier，另加一個整合分片（總覽 spec 的跨子計劃驗收條件＋整條 diff 的反作弊），平行驗證後彙整成 `verifier.md`，workflow 會核對彙整沒有漏條目、沒有改結果、各分片驗的是同一個 HEAD。修正時，失敗分散在多個子計劃就各自 worktree 平行修，再由 dev-integrator 合併；整合分片的失敗在合併後單獨修。

`build.test_first` 的效果：true 時 sdlc-build 走 Red 階段（先寫會失敗的測試、合進整合分支才實作）；false 時跳過 Red，實作合併後走 Tests 階段補驗證測試，測試失敗代表實作不符驗收條件，交人判斷，不改測試遷就實作。

### 依需求類型分流（recipes、modifiers）

完整 SDLC 每次約派 25–35 個 agent，修一個 bug 不需要這麼多。`sdlc-plan` 第一步先派一個 `tpm-planner` 理解需求（triage），建議 recipe；由人在 plan 閘門選定，寫進 `run.json` 鎖定，之後只能用 `save_run.py escalate` 加嚴。內建 11 個 recipe（feature、bugfix、change、hotfix、refactor、deps、docs、test-only、perf、spike、revert）與 5 個 modifier（ui、security、migration、public_api、large），表格見 README〈依需求類型分流〉。

自訂方式：
- **改內建 recipe**：直接改專案 `methodology.json` 的 `recipes.<名>`，再跑 `build.py`。例如團隊的 bugfix 也要 design：在 `stages` 加 `design`、`design_lenses` 加 `coverage`、`plan`。
- **新增 recipe**：在 `recipes` 加一個鍵；triage 會讀 `description` 判斷什麼時候用它。`plan_mode` 只能選內建的 8 種（feature、diagnose、impact、invariants、changelog、baseline、research、revert），每種 mode 的 intent 必要節可以用 `plan_modes.<mode>.sections` 覆寫。
- **不能省的部分**（schema 與工具強制，改 profile 也拿不掉）：每個 recipe 都有 plan 段（intent）；會產生改動的 recipe 都有 build、deliver、merge 段；plan 一律由人核准；每張派工單引用 `rules.md` 與輸出語言；每個 agent 都留執行紀錄。
- **diff 反查**：`publish.py` 推送前、`merge_gate.py --recipe <run.json>` 判定時，用實際 diff 檢查 recipe 夠不夠：`build_kinds` 沒有 code 卻改了程式、碰到 migration 卻沒有 design 段與 rollback lens、改了依賴宣告或鎖檔卻沒有一定做安全審查、spike 要推送，都拒推／hold。
- **舊 profile**：沒有 `recipes` 時一律當成 feature（行為和 0.2.0 一樣）。`init.py --upgrade` 會列出缺少的 `recipes`、`modifiers`，加 `--adopt-new-fields` 才補上。
- 解析規則有 Python（`tools/recipe.py`）與 JS（`tools/snippets/recipe.js`）兩份，`golden-set/recipes/*.json` 兩邊都跑，`tests/check_recipes.py` 比對結果一致；改規則要兩邊一起改並補 golden 案例。

### 執行紀錄與 run_brief

- **每個 agent 都留紀錄**：每張派工單最後一行指定 `<run_dir>/<段>/<label>.md`，agent 自己寫任務摘要、做了什麼、指令與結果、結論、不確定的地方。`save_run.py stage` 依 workflow 回傳的 `trace` 產生 `<run_dir>/<段>/執行紀錄索引.md`，紀錄檔缺了算缺件、不能政策核准。tpm-reviewer、tpm-skeptic、dev-release-watcher、tpm-planner 因此有 Write，但 hook 只准它們寫 runs_dir 底下的 .md；dev-merge-steward 仍沒有 Write，紀錄由 save_run 依信封代寫。
- **run_brief.py**（Read less）：`python3 .claude/teams/tools/run_brief.py --log <run_dir>/<段>/logs/<label>.log -- <指令>`。完整輸出寫進 log，終端只印結束碼、失敗的測試（最多 20 則）、最後幾行與 log 路徑，結束碼原樣傳回。認得 pytest、jest／vitest、go test、unittest。做法參考 [caveman](https://github.com/juliusbrussee/caveman)（Apache-2.0）的 Read less，自己實作、只用標準庫。
- **信封上限**：summary 400 字、evidence 12 則、每則 result 300 字；細節寫在檔案。
- **token 預算**：`python3 tests/check_budget.py` 乾跑量各 workflow 的派工數與派工單字數，超過 `golden-set/token-budget.json` 基準 10% 失敗；確認是預期的變多後用 `--update` 更新。乾跑量不到 agent 實際讀寫的 token。

### 省 token：模型分級、讀取預算、知識層與資料包

起因：實測一個 plan 段要 21～29M token，其中 95% 是 context 重讀——agent 整檔讀大檔，之後每一輪都把它重讀一次；而且每個 agent 都用最貴的模型。0.4 起用四個機制處理，都是 profile 的工作流程參數，不是開發規範。

**模型分級（`models`）**
- 等級只有三個：`light` < `standard` < `strong`。內建對應 `haiku`、`sonnet`、`inherit`（沿用主對話模型）；要換模型改 `tiers`。
- `mode: auto`（預設）：triage 會回傳 `model_plan`（各角色建議的等級與理由），design 可以給子任務標 `complexity`。工具取 **max(AI 建議或 `defaults`、`floors`、modifier 的 `model_floors`)**，所以 AI 只能在下限以上選。
- 內建下限（profile 蓋不掉，只能再加高）：`dev-merge-steward`、`dev-security-reviewer`、`tpm-skeptic@merge`、`dev-spec-author@plan` 是 `strong`，`tpm-skeptic@plan` 是 `standard`。modifier `security` 把 `tpm-skeptic` 拉到 `strong`、`large` 把 `dev-spec-author` 拉到 `strong`（內建 modifier 的下限，profile 把 `model_floors` 拿掉也照樣生效）。
- `tiers` 的對應不能倒掛：`strong` 不能對到比 `standard` 弱的模型（已知別名 haiku < sonnet < opus < inherit），否則 profile 驗證不過。
- 使用者自己的 agent（擴充 agent）不指定模型，沿用它 frontmatter 的設定。
- **失敗升級**：`auto` 模式下，agent 沒交件或交件無效時，用高一級重派一次（最多一次），trace 會記 `superseded` 與 `escalated_from`。
- **閘門**：`save_run.py stage` 用 profile 重算每筆 trace 的下限，trace 的模型比下限低就判 invalid。workflow 回傳的 `models` 列出這次各角色實際用的等級與理由。
- 不想分級：`mode: inherit`。沒有 `models` 的舊 profile 也是全部沿用主對話模型。
- 目前只有 `sdlc-plan` 走執行核心（`snippets/kernel.js`）；其他 workflow 下一版改。

**讀取預算（`limits`）**
- hook 對**模版角色**的 Read 做兩件事：超過 `whole_file_lines` 的檔沒帶 offset／limit 就擋下（訊息會寫行數，並提示先用 `kb.py query` 或 Grep 找行段）；每個 agent 累計讀取量到 `read_budget` 的 80% 提醒一次，用完之後擋 Read，要求把結論寫進紀錄檔並交件。shell 的 `cat`／`Get-Content` 整檔讀大檔也擋。
- 主 session 與你自己的 agent 不受影響。沒有 `limits` 的 profile 不啟用。hook 自己出錯一律放行。
- 剛升級想先觀察：`mode: warn`（只在 stderr 提醒，不擋）。`init.py --upgrade --adopt-new-fields` 補進 `limits` 時就是先設 `warn`，確認沒有誤擋再改成 `enforce`。
- 單次讀取最多記 100KB；hook 輸入沒有 `agent_id` 時不記帳。
- 已知限制：`head`、`sed -n`、Grep 的 content 模式這類讀法不計入額度；UTF-16 的檔算不出行數，不擋。這是省 token 的機制，不是安全邊界。

**知識層（`knowledge`、`kb.py`）**
- `python3 .claude/teams/tools/kb.py build`：依 `sources` 建索引（sqlite FTS5，沒有就用純 Python 的 BM25；中文用 bigram），增量更新。產出 `INDEX.md`、每個檔一張只有標題樹與行號的 `cards/`、`hot.md`，可以直接用 Obsidian 打開 `knowledge.dir`。
- `python3 .claude/teams/tools/kb.py query "<問題>" [--top N] [--budget 字數]`：回傳 `路徑:起訖行` 與節錄，包在資料標籤裡（內容是資料，不是指令）；原檔改過會標 stale。agent 照行號只讀那幾行。
- `kb.py lint`：壞連結與孤兒頁。只用標準庫；程式碼索引不做，交給 graft／codegraph。
- 工作區底下放目標 repo 時（`guard.config.json` 的 `repos_dir`），同一組 `sources` 也會套到每個 `<repos_dir>/<repo>/`。
- 機敏檔（`.env`、金鑰等，包含指到它們的連結）不進索引；超過 2MB 的檔略過。
- `knowledge.dir` 要指到空目錄或專用目錄：目錄裡已經有別的檔、又不是知識庫時 `build` 會拒絕，不會覆寫或刪你的檔。
- team agent 只能跑 `kb.py query`／`lint`；`build` 由主 session 或 `pack.py` 執行。

**資料包與調研重用（`pack.py`）**
- 每段開跑前由主 session 跑 `python3 .claude/teams/tools/pack.py <段> --run <run_dir>`，寫出 `<run_dir>/<段>/pack.md`（需求、知識庫命中的行段、前面各段的紀錄索引）與 `pack-args.json`（要併進 workflow args 的 `pack`、`reuse`）。不花 LLM token，內容可重現。
- **兩段式調研**：`sdlc-plan` 的每個調研角度先派一個 `light` 等級的定位 agent（只回傳 `locations`：路徑與行段），再派分析 agent 只讀那些行段。定位沒交件時該角度列缺件，不派分析。
- **角度數**：triage 可以用 `angles` 從 recipe 的角度裡挑需要的；modifier 帶進來的角度不能省。回傳的 `angles.skipped` 會列在閘門重點。
- **重用**：plan 存檔後，`<run_dir>/plan/reuse.json` 記下每個角度讀過的來源檔 sha1。plan 重跑、或同一個 epic 另開 run（`--reuse-from <舊 run_dir>`）時，來源檔沒變的角度直接沿用、不派工；`save_run.py stage plan` 會重新核對 hash，不符判 invalid。需求改了（需求是檔案時看檔案內容）預設全部重做，確認不影響調研才加 `--keep-research`（會記在 `reuse.json`，閘門才認）。沒做完的結論（blocked）不記也不沿用。
- 重用的判斷是「上次定位到的檔沒變」：repo 裡**新增**的檔不會觸發重做。新增了會影響結論的文件時，不帶 `reuse` 重跑（刪掉 `pack-args.json` 裡的 `reuse`，或刪 `reuse.json`）。
- `pack.md`、`reuse.json`、`pack-args.json` 只由主 session 產生：team agent 不能寫這些檔，也不能執行 `pack.py`。

**量成本**：`python3 .claude/teams/tools/awf_cost.py --project . --run-dir <run_dir>` 讀 Claude Code 存的 workflow transcript，依角色與模型加總 token、時間、平均 context。transcript 格式官方沒承諾穩定，讀不懂時會明說並 exit 0；它不參與任何閘門。

### 新增 profile

1. 複製 `scaffold/.claude/teams/methodologies/default.json` 成新檔（檔名就是 profile 名稱），改內容；範例一律用虛構的「示範客戶 ACME」。
2. golden-set 會把 `methodologies/*.json` 全部當正例驗：`uv run --no-project --with jsonschema python3 scaffold/.claude/teams/golden-set/run.py`。
3. 要改 schema 時，同時在 `golden-set/valid|invalid/methodology*.json` 補正反例（範例檔寫 `"schema": "methodology"` 而不是 `payload`）；schema 表達不了的規則寫在 `schemalib.methodology_errors`。
4. 不想改模版也可以：把 profile JSON 放在任何地方，init 時 `METHODOLOGY=<路徑>` 或答案檔 `"methodology": "<路徑>"`。

### init 問答與答案檔

`init.py` 互動模式在佔位符問答之後逐項詢問（每題有預設值，Enter 直接用）：開發規範 profile、要不要測試先行、code style 工具或指令、commit 格式與檢查 regex、分支前綴、PR 大小上限（行數、檔案數，0＝不限）、文件格式。在 Claude Code 裡可以用 `/agent-workflow:init-workflow`，它會先在對話中問完再寫答案檔。

非互動用 `--answers <答案檔>`（JSON；沒寫的鍵沿用 profile）：

```json
{
  "methodology": "lightweight",
  "test_first": false,
  "code_style": {"description": "提交前跑 ruff", "tool": "ruff", "command": "ruff format --check ."},
  "commit": {"format": "<type>: <摘要>", "examples": {"feat": "feat: <Story> 實作"}, "check_regex": "^(feat|fix|docs|test|chore): .+"},
  "branch_prefix": "feature/",
  "pr_size": {"max_lines": 400, "max_files": null},
  "doc_format": "Markdown",
  "requirements": {"source": "json", "path": "_tpm/requirements.json"},
  "overrides": {"stages": {"test": {"guidance": "示範客戶 ACME：先跑 make verify"}}}
}
```

- `methodology`：profile 名稱或 JSON 路徑（蓋過 workflow.config 的 `METHODOLOGY`）。
- `code_style`、`doc_format`：字串或物件；`commit` 給字串時只改格式說明，profile 的範例與 `check_regex` 會清掉。
- `branch_prefix`：同時改 `BRANCH_PREFIX`（workflow 的分支名）並加進 `ALLOWED_BRANCH_PREFIXES`。
- `pr_size`：`null` 或 0 表示不限。
- `sync_strategy`：分支落後 main 時怎麼跟上，`auto`（預設）、`rebase`、`merge`、`transit`，寫進 profile 的 `conventions.sync.strategy`。
- `overrides`：深層合併進 profile，可以改任何欄位。
- `main_session_push_merge`：你既有的 skill 或習慣會不會在主 session 直接 push main、合併 PR。`true` 時 `guard.config.json` 的 `main_session_git_rules`、`main_session_github_rules` 設成 false（見〈套用到既有專案〉）；不寫或 `false` 維持預設。互動模式最後也會問這一題。

優先順序：答案檔 > 互動回答 > workflow.config 的 `METHODOLOGY`；`--defaults` 且沒有答案檔時一律用 default。合併後的結果先用 schema 驗，再寫成 `.claude/teams/methodology.json`（已存在時保留專案自己的那份，`--force`、`--upgrade` 也不覆寫；要整份換掉加 `--overwrite-user-files`），最後跑 build.py。

### 需求來源和 merge_gate 共用

`merge_gate.py` 讀需求清單的順序：`guard.config.json` 的 `requirements` 有設 `path` 或 `command` 時以它為準（auto_merge 的設定走 PR＋CODEOWNERS，所以優先）；沒設時讀 `methodology.json` 的 `requirements`；都沒有就只能靠 `--requirements`，仍沒有就判 hold。CI 範本（`agent-merge-gate.yml`）從 base 分支 checkout 後跑同一支 gate，讀的也是 base 分支上的這兩個檔。

### 改了 profile 之後

workflow 不能讀檔，profile 是由 build.py 用標記 `/*@methodology*/ … /*@end*/` 內嵌進 `sdlc-*.js` 的。改了 `.claude/teams/methodology.json` 一定要重跑：

```bash
python3 .claude/teams/tools/build.py          # 內嵌
python3 .claude/teams/tools/build.py --check  # 驗證：profile 與 workflow 不一致時 exit 1
```

沒有 `methodology.json` 時（例如模版本身的 scaffold），標記保留 `null`，workflow 改用中性指引（依目標 repo 既有慣例），測試時機沿用測試先行。

## 12. 套用到既有專案

`init.py` 可以直接套用到已經有 `.claude/`、`CLAUDE.md`、CI 的專案。原則是**只新增模版自己的檔案，使用者的檔案不覆蓋**；使用者原本的 agent、skill、command 與設定都照常能用。

### 會新增哪些檔

- `.claude/teams/`：rules、schemas、methodologies、tools、golden-set、`guard.config.json`、`methodology.json`、`VERSION`（套用的模版版本）、`workflow.config`（這次的佔位符值，`--upgrade`、`--force` 沒給 `--config` 時沿用），以及 `agent-workflow.CLAUDE.md`（模版的工作流程說明，見下）。
- `.claude/workflows/` 裡模版的 `sdlc-*.js`、`event-*.js`（同名檔案是使用者的就保留，見下）。
- `--hooks project` 時的 `.claude/hooks/`（`awf_hook.py`、`guard.py`、`awf_config.py`、`envelope_hook.py`、`tests/`）。
- run 目錄（`{{RUNS_DIR}}/README.md`）、`.mcp.json.example`。
- `.github/workflows/agent-merge-gate.yml` **預設不放**，加 `--with-merge-gate` 才放：沒有設好 gate App 時它會讓每個 PR 失敗。

### 不會動哪些檔

| 檔案 | init 的做法 |
|---|---|
| `.claude/agents/`、`.claude/skills/`、`.claude/commands/` | 一律不碰（模版的 agent、skill、command 由 plugin 提供，不複製進專案）。 |
| `CLAUDE.md` | 不覆蓋。模版內容寫成 `.claude/teams/agent-workflow.CLAUDE.md`，再在 `CLAUDE.md` 結尾追加兩行：一行註解標記、一行 `@.claude/teams/agent-workflow.CLAUDE.md`（Claude Code 的 import 語法）。已經引用過就不再追加，重跑 init 不會重複。換行字元沿用原檔（CRLF 的檔案追加的也是 CRLF）。 |
| `.claude/settings.json` | 深度合併：使用者已有的值一律保留（`permissions.allow` 這類清單也不改），只補上模版有、使用者沒有的鍵；`hooks` 依事件合併，使用者自己的 hooks 原樣保留，`awf_hook.py` 的每個模式（guard-shell、guard-paths、envelope）只註冊一次，重跑時就地更新指令（例如換了 Python 路徑）。不是合法 JSON 時不動，印提示請你手動補。 |
| `.mcp.json`（`--with-mcp`） | 同上，深度合併。 |
| `.claude/workflows/`、`.claude/hooks/`、`.github/workflows/` 裡的同名檔 | 內容看得出是模版產生的（含 `agent-workflow`、`agent-merge-gate` 或 `/*@schema:` 標記）才當成模版檔；否則當成使用者的檔案保留，列在「保留 N 個使用者的檔案」清單。 |

`--force` 只覆蓋模版自己的檔案；你的設定照〈升級已 init 的專案〉的規則保留（`methodology.json`、`guard.config.json`、rules.md 的〈專案規則〉、CLAUDE.md 的〈專案特定〉不整份覆寫）。上表的使用者檔案即使加 `--force` 也照上表處理，不整份覆蓋。真的要整份換成模版版本，另加 `--overwrite-user-files`。分成兩個旗標的理由：更新模版是常做的事，重設使用者檔案很少做而且不可逆，不該被同一個旗標順手帶上。更新已 init 的專案建議用 `--upgrade`，見下一節。

### 命名空間怎麼避免衝突

- plugin 的 agent、skill、command 都帶 `agent-workflow:` 命名空間（例如 `agent-workflow:dev-implementer`、`/agent-workflow:brief`），不會覆蓋使用者同名的東西。使用者自己有 `/brief` 時，打 `/brief` 用的是使用者的版本，plugin 的版本用 `/agent-workflow:brief`。
- 守門 hook 只把「命名空間在 `team_agent_namespaces`（預設 `["agent-workflow:"]`）而且角色名以 `team_agent_prefixes`（`dev-`、`tpm-`）開頭」的 agent 當成模版角色。使用者自己的 `.claude/agents/dev-helper.md`（agent_type 是沒有命名空間的 `dev-helper`）不套角色規則：可以 push 功能分支、寫任何檔、交件不需要信封，規則和主 session 一樣。
- 例外：角色名和 plugin 的模版角色**完全相同**（`dev-implementer`、`tpm-writer` 等 14 個核心角色，加上 2 個舊名，共 16 個，見 `awf_config.RESERVED_ROLES`）的 agent，不論有沒有命名空間都套模版角色規則（fail-closed）：它多半是模版 agent 的複本，或是冒用模版角色名。所以自己的 agent 不要取和模版角色一樣的名字；合併、寫凍結檔仍比對完整 agent_type，冒用不會因此放行。
- 想讓沒有命名空間的 `dev-*`／`tpm-*` 也套模版角色規則（舊版行為），在 `team_agent_namespaces` 加空字串：`["agent-workflow:", ""]`。agent 放在專案 `.claude/agents/`、`AGENT_NS` 設成空字串時，init 會自動填 `[""]`。
- `auto_merge.merger_role`、`freeze_writers` 比對完整 agent_type，也要是模版角色；使用者的同名 agent 不能合併、不能寫凍結檔。

### 主 session 的開關

使用者自己的 skill 在主 session 跑。有 `guard.config.json` 時，主 session 預設也不能 push 受保護分支、不能 `gh pr merge`、不能核准、`gh` 寫入要帶 `--repo`。如果你的 skill 或習慣本來就會在主 session 直接 push main、合併 PR：

- init 問答會問「你既有的 skill 或習慣會不會在主 session 直接 push main、合併 PR？」，答會（或答案檔寫 `"main_session_push_merge": true`）時，把下面兩個鍵設成 false。`--defaults` 兩個都維持 true。
- 也可以事後自己改 `guard.config.json`：
  - `main_session_git_rules: false`：主 session 不檢查分支前綴、force push、`--no-verify`、push 受保護分支。
  - `main_session_github_rules: false`：主 session 可以 `gh pr merge`、`gh pr review --approve`、用 REST 合併或核准，`gh` 寫入不必帶 `--repo`。
- 例外（不論開關）：上游與禁止的 repo 一律擋；`auto_merge.enabled` 為 true 時，主 session 一律不能合併、核准、直接 push 受保護分支（信任模型要求合併只走 merger_role＋gate）。agent 的限制不受這兩個開關影響。

### 升級已 init 的專案

plugin 與專案裡的 scaffold 檔案分開更新。新版發佈後依序做：

1. **更新 plugin**：`claude plugin update agent-workflow@agentworkflow`，或在 `/plugin` 介面更新。只跑 `/plugin marketplace update agentworkflow` 只會更新目錄清單，不會更新 plugin。
2. 在 Claude Code 裡執行 `/reload-plugins` 載入新版。
3. **更新專案的 scaffold**，在每個已 init 的專案跑：

   ```bash
   python3 <AgentWorkFlow>/init.py --target . --upgrade
   ```

4. 看 `--upgrade` 列出的「profile 缺少的新欄位」，要採用時加 `--adopt-new-fields` 再跑一次：

   ```bash
   python3 <AgentWorkFlow>/init.py --target . --upgrade --adopt-new-fields
   ```

5. 跑 `python3 .claude/teams/tools/build.py --check` 確認內嵌一致，再照 `CHANGELOG.md` 該版的〈升級步驟〉處理破壞性變更（例如舊角色名改新名）。

`--upgrade` 做什麼：

| 檔案 | 做法 |
|---|---|
| 模版檔（`.claude/teams/` 的 schemas、tools、methodologies、golden-set，模版產生的 workflow 與 hook） | 一律換成這版，包括你改過的工具檔；要保留的修改先 commit，再用 git 比對 |
| `.claude/teams/methodology.json` | 不動。列出這版內建 profile 新增、你的 profile 還沒有的欄位與預設值；加 `--adopt-new-fields` 才補進去，只補缺的，既有值永遠不改，補完驗 schema 並重跑 `build.py` |
| `.claude/teams/guard.config.json` | 你的值一律保留，只補上這版新增的鍵；說明文字 `_說明` 換成新版 |
| `.claude/teams/rules.md` | 「## 專案規則」段（含 correct skill 維護的對照表）之後保留，前面的通用規則更新 |
| `CLAUDE.md`（init 產生的）與 `.claude/teams/agent-workflow.CLAUDE.md` | 「## 專案特定」段之後保留，前面更新 |
| 使用者的檔案（自己寫的 `CLAUDE.md`、`settings.json`、`.mcp.json`、非模版的同名檔） | 照〈不會動哪些檔〉處理 |

兩個記錄檔：

- **`.claude/teams/VERSION`**：套用的模版版本，內容等於 plugin 的 `plugin.json` 的 `version`。`--upgrade` 會顯示「舊版 → 新版」。有模版檔沒更新到時（例如沒加 `--upgrade` 也沒加 `--force` 重跑），init 不寫 VERSION，避免謊報版本。
- **`.claude/teams/workflow.config`**：init 時用的佔位符值。`--upgrade`、`--force` 沒給 `--config` 時都沿用它，不再詢問；只有給了 `--config`、值本來就取自它、或還沒有這個檔時才會重寫；佔位符的值要改，就改這個檔或另給 `--config`。

`--upgrade`、`--force`、`--overwrite-user-files` 的差別：

| 旗標 | 模版檔 | 你的設定（methodology、guard.config、〈專案規則〉、〈專案特定〉） | 使用者的檔案 |
|---|---|---|---|
| `--upgrade` | 更新 | 保留，只補新鍵；列出 profile 新欄位 | 不整份覆寫 |
| `--force` | 更新 | 保留規則和 `--upgrade` 相同 | 不整份覆寫 |
| `--overwrite-user-files` | 更新 | **整份覆寫** | **整份覆寫** |

`--overwrite-user-files` 只在想重設時用；要換 profile 時搭配 `--answers`。

### 怎麼移除模版

1. 刪掉 `CLAUDE.md` 結尾那兩行（`<!-- agent-workflow：… -->` 與 `@.claude/teams/agent-workflow.CLAUDE.md`）。
2. 刪掉 `.claude/teams/`、模版的 `.claude/workflows/*.js`（看檔頭的 `const NS =` 與 `/*@schema:` 標記）、run 目錄的 README.md；用過 `--hooks project` 的話刪掉 `.claude/hooks/` 裡的 awf 檔案，並從 `.claude/settings.json` 的 `hooks` 拿掉指令含 `awf_hook.py` 的項目。
3. 放過 merge gate CI 的話刪掉 `.github/workflows/agent-merge-gate.yml`。
4. 在 Claude Code 跑 `/plugin uninstall agent-workflow@agentworkflow`。
init 合併進 `settings.json` 的權限（`permissions.deny` 等）如果不需要，也一併刪掉；用 git 比對 init 前後最清楚。
