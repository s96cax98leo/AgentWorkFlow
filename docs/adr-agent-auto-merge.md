# ADR：讓 agent 審查並自動合併 PR

- **狀態**：已決定（2026-10-24 決策者拍板，見〈決策〉；部分決定與下方原建議不同，以〈決策〉為準）
- **日期**：2026-10-24
- **適用範圍**：AgentWorkFlow 模版（plugin 與 scaffold），以及套用模版的專案

## 決策

決策者的核心要求：**要有一個可以合併 PR、而且可信任的 agent。** 可信任的意思是：它逐條對照需求與驗證結果，確認兩者一致才合併；不一致就開出新需求要求調整，並退回 PR。

1. **新增可信任的合併 agent（`dev-merge-steward`）與合併後監看 agent（`dev-release-watcher`）。**（取代原建議 4）
   - steward 的信任來源是「需求與成果對照」：把每一條需求，對到驗證報告、測試與程式位置，逐條判定一致、不一致或缺證據；diff 裡對不到任何需求的改動也要列出。對照結果綁定 head SHA。
   - 全部一致，而且確定性 gate（`merge_gate.py`）也通過，才合併。gate 會再機械檢查對照表是否涵蓋需求清單的所有項目，agent 說服不了它。
   - 有任何不一致、缺證據或範圍外改動：產出新需求（說明哪一條需求、期望、實際、要怎麼調整），並退回 PR（request changes、轉回 draft）。新需求的文件由文件 agent 寫，steward 本身沒有 Edit／Write。
   - steward 永遠不 approve。守門比對完整的 agent 名稱，防止同名 agent 冒充。
2. **上游取得授權後開放。**（取代原建議 1）上游 repo 要有上游 org owner 的書面授權、安裝我方 App 並設好 ruleset，設定檔 `upstream_authorized_by` 填入授權人後才放行；沒填一律擋。上游無法由我方 revert，所以上游只靠合併前的對照與 gate。
3. **fork 通道 required approvals 設 0**，由綁定來源 App 的 gate check 把關。
4. **新增確定性推送工具**（推分支、開 PR），fork 端 ruleset 禁止直接 push 到 main。
5. **不綁定開發規範。** TDD、DDD、SDD 等由套用模版的團隊自行決定。需求清單與驗證證據採中性格式，來源可設定（內建 spec.md 範例、JSON，或團隊自己的腳本，例如從 issue、Story 轉出）。
6. 其餘待拍板事項先套用建議的預設：規則改為依風險分級、只在最低風險等級啟用並依 PR＋CODEOWNERS 升級（3）；App 由組織擁有（6）；plan 閘門保留人工、可批次核准（7）；revert 先只產出提案並凍結自動合併（8）；合規確認前照「有」處理（9）；gate 先上並開始記錄（10）；設成本與併發上限（11）。

## 背景

### 目標

- 讓 AI-native SDLC 無人值守跑完：plan → design → build → test → deliver → 合併。
- 讓 agent 審查並合併 PR，範圍原本包含上游 repo。原因是人類審查的速度跟不上 PR 開出來的速度。

### 現況（已查證）

- 規則寫明 agent 不合併，核准與合併只能由人做。
- 守門 hook 是 client 端程式，有幾個缺口：
  - 只擋 `tpm-*`／`dev-*` 角色，主 session 帶 `--repo` 就能 merge 或 approve。
  - 只註冊 Bash 工具，Windows 的 PowerShell 工具不經過。
  - 只比對 `gh` 指令字串，curl 直接打 API 不在範圍。
- GitHub 允許任何有 write 權限的身分設定任何 status check。required check 沒有綁定來源 App 的話，綠燈可以被偽造。
- 目前沒有 CI、`.github/`、合併稽核紀錄或 revert 機制。
- 閘門的「政策核准」只看 agent 自己回報的狀態，不看審查與驗證的實際內容。
- build 段中途失敗時，可能被記成完成。
- 沒有任何元件負責「推分支、開 PR」。無人值守會停在 deliver 之後。

### 評估方式

四個觀點互相挑戰後收斂：
- 職責分離：作者、審查者、合併者分開，加上確定性 gate。
- 事後防線：合併後監看，出錯就 revert，並追溯戰績。
- 人工合併基準線：專門挑戰上游授權。
- 角色與 team 完整性稽核。

## 考慮的選項

| 選項 | 做法 | 代價 | 前提 | 需要決策者配合 | 什麼情況下才對 |
|---|---|---|---|---|---|
| 一、職責分離＋伺服器端強制 | 合併前跑確定性 gate；gate 結果由專屬 GitHub App 回報到綁定來源的 required check；通過後由 GitHub auto-merge 合併，合併路徑上不放 agent | 要建 gate、CI 範本、GitHub App 與 ruleset；每個專案要保管 App 私鑰；CI 執行成本 | 目標 repo 有可信 CI；能管 repo 設定；低風險路徑可列舉；merge 與 release 脫鉤 | 拍板 ruleset 形狀、每個 repo 的風險上限與每日上限、建立 GitHub App | PR 量高且多為低爆炸半徑變更、有 CI、團隊能控 repo 設定 |
| 二、事後防線 | 前置只留輕量確定性 gate；合併後監看 main CI，出錯就開 revert PR；寫合併稽核紀錄；依戰績升降可自動合併的風險上限 | 要先建 CI 與合併後訊號；失誤時 main 會壞一段時間；戰績要累積樣本 | 可乾淨 revert；有可靠的合併後訊號；我方有 write 權限；merge 與 release 脫鉤 | 核准自動合併政策並定期看稽核摘要 | 我方 fork、PR 小、沒有外部使用者直接追 main。對資安變更、惡意改動、上游都無效，只能當第二道防線 |
| 三、人工合併基準線 | agent 預審、跑 gate、做摘要卡，把 PR 整理到一鍵可合；人批次核准後交給 GitHub auto-merge | SDLC 只能做到「全自動到可合」；人仍是吞吐上限；批次核准有只看摘要就按的風險 | 瓶頸在讀 diff，不在按鍵；決策者能固定撥時段。目前沒有量測資料 | 固定批次核准時段 | 上游、冷啟動期、有 SLSA／SOC2 稽核要求時。單獨無法達成無人值守到合併 |

以上三者不是互斥的：
- 辯論結論是組合使用。合併前用確定性 gate，合併後用事後防線；上游與高風險變更維持人工。
- 無論選哪一種，下方「前置必修」都要先完成。

## 建議決策與理由

### 1. 上游 repo 第一版不做自動合併（原建議，已由〈決策〉2 取代）

- 合併上游，需要上游維護者授予 write 權限，或由上游 org owner 安裝我方 App。我方決策者無法代上游授權。
- 依 GitHub 服務條款，bot 行為的責任歸帳號擁有者（我方）。
- 部分開源專案明文要求 human in the loop，例如 LLVM 的 AI tool policy。
- 上游出錯時我方無權 revert，壞的 commit 也可能已被下游拉走。

上游維持 agent 預審加人工合併。往後若要開放，要同時具備：上游維護者的書面授權（連結、範圍、到期日）、上游安裝 App、上游 ruleset 設定 required check。

### 2. 信任邊界放在 GitHub 伺服器端，本機 hook 只是輔助

- 本機 hook 可被其他工具、直接呼叫 API、主 session 或同名 agent 繞過。
- 真正的強制來自兩樣東西：ruleset，以及綁定來源 App 的 required check。

所有方案的共同必要條件是以下 ruleset 基準線：
- Do not allow bypassing，bypass list 留空；
- dismiss stale approvals；
- require approval of the most recent push；
- workflow 建立或核准 PR 維持關閉。

「合併者是人」本身不保證有人審過，因為 admin 預設可以不經核准就合併。保證來自 ruleset。

### 3. 自動合併只在我方 fork 的最低風險變更上啟用

啟用條件，全部成立才開：
- 只改文件，或只新增測試；
- diff 小；
- 不碰 CI、release、版本檔；
- 可乾淨 revert；
- merge 與 release 脫鉤，也就是 push 到 main 不會自動發佈；
- gate check 綁定來源 App。

以下變更一律交給人：動到 `.github/`、`.claude/`、gate 本身、hooks、依賴與 lock 檔、migration、release 與版本檔、publish workflow、tag、auth、CODEOWNERS。

樣本數未達門檻前，風險上限固定在最低等級。升級要累積樣本，降級立即生效。

### 4. 合併由確定性元件執行，不新增「合併守門人」agent（原建議，已由〈決策〉1 取代；被說服的顧慮改由 gate 複核對照表處理）

- 合併守門人 agent 能做的每一項判斷，確定性 gate 都做得到。
- 這個 agent 會讀 PR 內容，可能被藏在 diff 或說明裡的指令說服。
- GitHub 權限也切不出「能 merge、不能 approve」。

改由 gate 通過後的 `gh pr merge --auto` 或 gate App 的 workflow 合併。合併後監看同理，做成確定性檢查，不必新增 agent。

### 5. 合併通道的審查規則：不確定就停

- 現行的反駁審查（skeptic）不確定時判「不成立」。這是為了減少給人看的誤報。
- 放在自動合併路徑上，被推翻的重要發現會被丟掉，等於失效時放行（fail-open）。

合併通道改成：
- 不確定就停（hold）；
- 重要與阻擋級的發現不得被推翻；
- agent 的審查只能讓結果變嚴，不能變寬。

### 6. 前置必修（不論選哪個方案）

- 政策核准改由確定性工具讀審查與驗證的實際內容，不只看 agent 回報的狀態。
- build 段中途失敗時記為未完成。
- 新增一條確定性的「推分支、開 PR」路徑：先做機敏值掃描與政策判定，再推送與開 PR，並寫稽核紀錄。
- 擋下主 session 的直接 merge、approve，以及直接 push 到預設分支。
- 審查結果綁定 commit SHA；合併時的 head 必須和審查時相同。
- gate 從受保護的 base 分支執行，不執行 PR 自帶的 gate。
- 稽核紀錄除了寫在本機，也寫成 GitHub 上的 check 或留言。

## 後果

### 好處

- 低風險變更可以無人值守地合併，人只處理高風險變更與上游。
- 判斷集中在確定性 gate 與伺服器端設定，agent 被說服也改變不了合併結果。
- 合併稽核紀錄與戰績可以回查，之後擴大範圍時有資料可依。

### 代價

- 每個套用模版的專案都要建立並保管 GitHub App、設定 ruleset，並要有可信的 CI。前提不成立的專案，自動合併預設關閉。
- 「規則：核准與合併只能由人做」等通用規則要改寫成依風險分級，並寫明核准人。
- 上游 PR 的吞吐問題，第一版沒有解決。
- 事後防線只能縮短誠實錯誤的復原時間，不能防惡意改動。
- 不宣稱達到 SLSA Source L4。agent 合併屬於組織明文授予的 Trusted Robot 例外。

### 未能確認

- 一般 GitHub App 的核准是否計入 required approvals。
- 政策式核准是否符合 SOC2 CC8.1 的授權要求。
- 自動 revert 研究的誤 revert 率。
- 人類審查實際落後多少，目前沒有量測資料。

## 待拍板事項

每項列出選項、代價與建議。前六項會擋住後續實作，後五項可以先套用建議的預設。

### 會擋住後續實作

**1. 上游 repo 是否納入第一版自動合併**
- 選項 A：不納入，上游維持人工。代價：上游吞吐仍受限於人。
- 選項 B：取得上游書面授權並由上游安裝 App 後，對授權範圍開放。代價：要上游配合，並逐一查各上游的 AI 政策。
- 選項 C：只憑我方授權就開放。代價：技術上做不到，也可能違反上游政策，責任全在我方。
- **建議：A。** 累積 fork 上的戰績後再向上游提 B。

**2. fork 自動合併通道的 required approvals 設 0 還是 1**
- 選項 A：設 0。由綁定來源 App 的 gate check 把關，只有合併用的 App 能更新分支，高風險路徑由 CODEOWNERS 要求人審。代價：沒有原生的「有人核准」保證；要建兩個 App 並保管私鑰。
- 選項 B：冷啟動期設 1，由人批次核准；達樣本門檻後改 0。代價：門檻前不是無人值守，但留下人類授權紀錄與量測資料。
- 選項 C：設 1，並把合併用的 App 放進 bypass list。代價：bypass 會略過所有規則，App 金鑰外洩等於 admin 合併權。
- **建議：A**，搭配「樣本未達門檻前只開最低風險等級」與每日上限。
- 辯論中有一方主張 B，理由是冷啟動期由人留下授權紀錄。在最低風險等級上，兩案的實質差異只有這一點。

**3. 是否把「核准與合併只能由人做」等規則改為依風險分級，並採用上述啟用條件**
- 選項 A：改，只在 fork 最低風險等級啟用。代價：自動化覆蓋較低。
- 選項 B：改，fork 上所有非資安路徑都啟用，依戰績升級。代價：初期誤合併機率較高。
- 選項 C：不改，只做 gate 與事後監看。代價：人仍是瓶頸。
- **建議：A。**

**4. 合併執行者與合併後監看要做成 agent 還是確定性元件**
- 選項 A：確定性元件，不新增 agent。代價：要先設 ruleset 與 App；合併理由的可讀說明改由文件 agent 寫。
- 選項 B：新增 agent，但只准執行 gate 與合併指令。代價：多一個可被 PR 內容說服的元件，守門要開例外。
- 選項 C：兩者都要。代價：重複維護兩份邏輯。
- **建議：A。**

**5. 無人值守時由誰推分支、開 PR**
- 選項 A：新增確定性推送工具，只在啟用自動合併時可用；fork 端 ruleset 同時禁止直接 push 到 main。代價：多一條自動寫入路徑，要補守門測試。
- 選項 B：新增推送用 agent。代價：agent 讀得到 PR 內容，可能被說服。
- 選項 C：維持每次推送都由人當下同意。代價：無人值守到不了合併。
- **建議：A。**

**6. GitHub App 的擁有者、撤銷權與事故責任人**
- 選項 A：App 由決策者所屬組織擁有，由決策者簽核擁有者、撤銷人與事故聯絡人。代價：責任明確落在我方組織。
- 選項 B：沿用個人 token。代價：責任落在個人；無法綁定來源 App，與建議決策 2 衝突。
- **建議：A。**

### 可以先套用預設

**7. plan 閘門（需求解讀的核准）是否保留人工**
- 選項 A：保留，允許批次、非同步核准。代價：不是完全無人值守。
- 選項 B：全部改政策核准。代價：需求解讀錯誤會一路做到合併。
- 選項 C：依需求來源區分，上層系統發的任務自動核准。代價：要定義並驗證可信來源。
- **建議：A。** design、test、deliver 在前置必修完成後可改政策核准。

**8. revert PR 由誰合併、用什麼身分**
- 選項 A：監看只產出 revert 提案並凍結自動合併，推播決策者處理。代價：復原時間取決於人。
- 選項 B：專用 revert App，走快速通道：diff 必須恰好等於 revert 該 commit，有衝突或不穩定就交人。代價：多一條自動寫入路徑，快速通道的 gate 尚未驗證。
- **建議：A 起步**，戰績穩定後評估 B。

**9. 是否有 SLSA、SOC2 等職責分離的稽核要求**
- 選項 A：有，自動合併只用在書面核准的例外類別。代價：範圍很窄。
- 選項 B：沒有，依風險分級開放。代價：日後補合規可能要回頭收緊。
- **建議：確認前照 A 處理。** 請合規窗口確認政策式核准是否被接受。

**10. 是否先量測 PR 產量與審查瓶頸**
- 選項 A：先量測，再決定。代價：延後上線。
- 選項 B：gate 與人工基準線先上，同時開始記錄。代價：人類瓶頸短期不解除。
- 選項 C：直接上自動合併。代價：沒有基準可比。
- **建議：B。** gate 各方案共用，先上不會浪費。

**11. 成本與併發上限**
- 選項 A：設上限，包括每次執行的 agent 數、每日執行數、每日合併數、每層平行數，超過就暫停並通知。代價：要定預設值，太低會頻繁暫停。
- 選項 B：不設上限。代價：無人值守時沒有煞車。
- **建議：A。**

## 範例

示範客戶 ACME 的 fork `acme-fork/app` 啟用後：
- 只新增測試的小 PR，通過 gate 後由 GitHub auto-merge 合併。
- 改到 `.github/workflows/` 的 PR，被判為高風險，交給人。
- 上游 `acme-up/app` 的 PR 一律由人合併。
