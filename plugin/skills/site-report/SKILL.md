# Site Report — 總指揮與合成

## 使用時機
單一面向的問題直接用對應 skill；需要**跨面向、可交付的完整報告**時才啟動這套流程。

## 階段一：定範圍（先問，別猜）
確認四件事，缺一不可：
1. **目標資產**：主站？控制台？API？全品牌組合？
2. **讀者與用途**：內部技術評估 / 競品簡報 / 合作評估 / 供應鏈機會盤點——決定深度與語氣
3. **深度**：快掃（~30 分）/ 標準（~2 小時）/ 深度（含多地量測與財報）
4. **地區基準**：定價與延遲都因地而異，先釘死一個基準地區

## 階段二：平行派工
一次 dispatch，不要串行（各 agent 互不依賴）。以 plugin 安裝時，`subagent_type` 要帶命名空間前綴（預設 `agent-workflow:`，例如 `agent-workflow:tech-architect`）：

| Agent | 產出檔案 |
|---|---|
| `tech-architect` | `artifacts/<target>/tech-stack.md` |
| `infra-analyst` | `artifacts/<target>/infrastructure.md` |
| `biz-analyst` | `artifacts/<target>/business-model.md` |
| `perf-auditor` | `artifacts/<target>/performance.md` |
| `competitor-scout` | `artifacts/<target>/competitive.md` |

派工 prompt 必須包含：目標網域、基準地區與幣別、深度、被動觀測邊界、輸出檔案絕對路徑、來源分級要求（A/B/C/D）。
原始證據（標頭、DNS、量測輸出）一律存到 `artifacts/<target>/raw/`。

## 階段三：交叉驗證（這一步不能省）
各 agent 獨立作業必然產生矛盾。逐項核對：
- 技術判定的 CDN／雲供應商，與基礎設施的 ASN 歸屬**是否一致**
- 效能量到的 TTFB 與 PoP，是否支持基礎設施宣稱的節點分布
- 商業模式推估的單位成本，與基礎設施推估的單機經濟**是否收斂**
- 競品的規格對標，與技術面實測到的實際交付**是否相符**

矛盾處理原則：**不要強行調和**。並列雙方證據，說明分歧原因與哪一邊證據更強。矛盾本身往往是最有價值的發現（例如「宣稱 NVMe，實測 I/O 表現不符」）。

## 階段四：合成
寫 `artifacts/<target>/REPORT.md`，結構：
1. **執行摘要**——5-8 條，每條一個可行動的結論，不是描述
2. 架構全景圖（mermaid，把技術層 + 基礎設施層 + 金流層畫在一起）
3. 技術架構
4. 基礎設施與底層資源
5. 商業模式與單位經濟
6. 效能實測
7. 競品定位
8. **綜合洞察**——只放跨面向才看得出來的結論（單一 agent 看不到的）
9. 風險與機會（依讀者用途調整；供應鏈讀者 → 硬體採購切入點）
10. 方法論、來源分級、量測條件、未解問題

### 綜合洞察怎麼寫（報告的價值集中在這節）
把技術選擇對應到商業約束。例如：
- 「大量共享運算 + 極低入門價 + 高續約溢價」是同一個模式的三個面向，不是三個獨立事實
- 邊緣供應商的選擇如何限制或支撐其定價空間
- 自建 vs 租雲的取捨如何決定它能打到多低的價格
每條洞察都要能追溯到至少兩個不同 agent 的證據。

## 階段五：交付
合成完成後產出 Artifact（先載入 `artifact-design`；有圖表時另載 `dataviz`／`artifact-diagramming`），把 REPORT.md 做成可分享的網頁，交回連結。

## 鐵律
- 執行摘要裡不得出現未在內文佐證的主張
- 全報告統一來源分級標記，D 級（推估）必須附算式與假設
- 明列「未能查證」的項目——誠實的缺口比虛構的完整性有價值
- 報告與派工 prompt 用專案 `.claude/teams/rules.md` 設定的輸出語言（沒有設定時用繁體中文），技術名詞保留原文
